Answer first

Your instinct is mostly right

Pi should be made compatible at the edge. Mission Control does not need a new workflow engine or a Pi-specific queue.

Yes: use a Pi extension

Pi extensions can observe session and agent lifecycle events, read Pi's session identity, and make network requests. That is enough to bridge Pi into Mission Control's existing authenticated hook endpoint.

No: installation alone is not sufficient today

Mission Control explicitly declares Pi hooks and work queues as unsupported. Even a correctly posting extension would be ignored until a small Pi hook specification and capability declaration are added.

Practical interpretation

This looks like a narrow compatibility package with a narrow MC adapter, not a major MC-side redesign. The adapter is still real work, but the common transport, authentication, session overlay, work-cycle normalization, Foreman logic, and Workflow trigger already exist.

Declared limitation

Why it fails now

The visible message comes from a deliberate preflight check. Before dispatching a task with an after-work Workflow, Mission Control requires both a hook definition and a Foreman work-queue definition for the selected harness. Pi currently has neither, so dispatch stops before the work begins. See workflow manager, lines 695-712.

The block is intentional. Foreman will not infer queue progress from silence or from transcript content alone.

The capability registry states the reason directly: Pi pushes no hooks, so Foreman has no signal for pickup or finish and cannot verify a queue. It adds that Pi's rich transcript may prove work happened, but not the authorship of the pickup. See harness capabilities, lines 667-672.

The queue state machine enforces the same rule. A session that has never reported a hook cannot supply either boundary, so the queue cannot advance. See Foreman queue machine, lines 343-358. Task-level after-work bindings are always pinned to the foreman_complete trigger, so there is no weaker fallback hidden behind the UI. See workflow manager, lines 760-785.

New evidence

Pi now exposes the boundary MC was missing

Mission Control's existing comments were measured against earlier Pi versions and correctly record that Pi uses in-process TypeScript extensions rather than Claude-style shell hooks. The locally installed Pi is now version 0.84.2, and its current extension API includes a higher-level agent_settled event.

before_agent_start

Occurs before an agent run and includes the prompt. This is a strong candidate for “work picked up.”

agent_settled

Occurs after the run has fully settled, with no automatic retry, compaction, or queued continuation left. This is the best candidate for “work completed.”

Session identity

The extension context exposes getSessionId(), getSessionFile(), and the working directory, which are enough to associate events with the launched MC session.

Network bridge

An extension runs in process and can use fetch. It can post lifecycle events to the loopback daemon with MC's existing hook token.

These capabilities are documented in Pi's current extension documentation and extension event types. The same settled event is exposed by Pi's RPC mode, but an extension can receive it without making Mission Control own a full RPC process.

Why agent_settled, not only agent_end?

An agent run may still be followed by retry, compaction, or queued continuation. Pi declares agent_settled only after those automatic paths are exhausted, which matches the semantic boundary Foreman needs much more closely.

Important distinction

The missing “hooks” are not dormant APIs that appear when any plugin is installed. They are a protocol agreement between a Pi extension and Mission Control. Both ends must agree on event names, identity, authentication, and work-cycle meaning.

Proposed seam

The smallest compatible design

Pi-specific code lives at the two edges: an extension inside Pi and a small event mapping inside the harness registry.

Pi-side extension responsibilities

  • On session_start, perform an awaited registration handshake carrying agent: "pi", Pi's session ID, session file, working directory, and terminal identity.
  • Map before_agent_start or agent_start to work started. The former also carries the prompt.
  • Map agent_settled to work completed.
  • Report session_shutdown with its reason so MC can distinguish extension reload and session replacement from actual process termination.
  • Read the existing local hook token and post to the existing loopback route with a short timeout. In a Workflow-required launch, keep a local ready flag false until registration succeeds and use Pi's input event to handle the positional task prompt without invoking the model if registration failed.

Mission Control responsibilities

  • Add a Pi HookSpec that maps those lifecycle names to the existing session states and normalized work-cycle signals.
  • Declare Pi's workQueue capability once the bridge is available.
  • Provide a stable installation or launch path, preferably an explicit --extension path controlled by MC so availability can be checked before launch. A global package needs an equivalent package-resolution preflight.
  • For an after-work Workflow, fail before launch if that preflight cannot resolve the bridge. After launch, wait for the bounded session_start registration before arming the Workflow. Do not require a hook before launching Pi. If registration fails, the extension's input guard consumes the positional task prompt without model work and MC fails the launch.

The receiving route already accepts a vendor-neutral hook payload and authenticates POST /hooks/:event with x-harness-token. See shared hook protocol, lines 158-213 and server route, lines 2595-2606. The registry already converts a harness-specific hook spec into shared session state and work-cycle signals. See registry hook application, lines 2180-2279.

Pi event and reason                         Normalized meaning
session_start: startup | reload             extension_ready; bind current Pi identity
session_start: new | resume | fork          rebind Pi identity; keep terminal session alive
before_agent_start                          work_started
agent_settled                               work_completed
session_shutdown: reload | new | resume     runtime_replacing; await next session_start
session_shutdown: fork                      runtime_replacing; await fork session_start
session_shutdown: quit                      exit_intent only; process lifecycle confirms exit
session_shutdown is not a process-exit event

Pi emits it whenever the current extension runtime is torn down, including /reload, /new, /resume, and /fork. The bridge must carry event.reason. Reload and replacement reasons keep the MC terminal session alive and wait for the following session_start; even quit is only exit intent until the existing terminal or process lifecycle confirms termination.

Recommended next move

Prove the thin bridge before considering RPC

  1. Build a local proof extension. Load it with pi -e first. Have it report session start, run start, settled, and reason-bearing shutdown events.
  2. Add the minimum Pi hook mapping in MC. Reuse the generic hook route, token, registry, and normalized work-cycle machinery. Do not add a second Pi-only queue or completion path.
  3. Test identity and absence behavior. Verify the launched --session-id is the ID Pi reports. Verify an absent extension fails the pre-launch check, and a failed startup registration makes the extension consume the positional prompt without invoking the model while MC fails the launch.
  4. Test runtime replacement. Exercise /reload, /new, /resume, and /fork. Each shutdown/start pair must preserve the live MC terminal session while updating only the Pi runtime identity that changed.
  5. Run one real end-to-end Workflow. Exercise pickup, one ordinary tool-using turn, settlement, Foreman Complete, and after-work execution.
  6. Escalate only on evidence. If agent_settled is not stable enough under retries, compaction, or queued follow-ups, then revisit the larger RPC driver plan.
Preferred packaging

A global Pi package is the best fit for operator-started and MC-started sessions. A project-local package makes coverage depend on repository trust and configuration. An MC-supplied --extension path is also viable if MC should own the exact bridge version.

Confidence and gaps

What this investigation did not prove

  • No custom extension was installed or executed, and no after-work Workflow was run end to end.
  • Pi's official 0.84.2 docs and installed type declarations define agent_settled with the desired semantics, but its behavior was not stress-tested against every retry, compaction, extension, and queued-follow-up combination.
  • No existing Mission Control bridge package was found in targeted searches. That is evidence of absence in the places checked, not proof that no private or unpublished implementation exists.
  • The wire shape for the two-stage health contract still needs design: resolve the extension before launch, then require its bounded session_start registration before Workflow arming. The extension-side input guard must be proven against Pi's positional launch prompt.

These are appropriate spike risks. None requires a major MC change before the extension path can be tested.
