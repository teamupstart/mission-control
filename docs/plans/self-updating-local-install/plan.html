Self-updating local install

A user clones the repository and runs one install command. The installed app then keeps itself current: the Electron main process asks the gh CLI whether a newer GitHub Release exists, prompts, and rebuilds itself from that tag in a clone the updater owns.

Supersedes the distribution half of issue #642

Recommendation

No Homebrew. No UMT, no Jamf, no private tap, no hosted update feed, and no signed artifact origin. The evidence for removing each is recorded in the phased plan page and in the plan source.

0new credentials or hosting
0Apple developer dependencies
1repository, one install command

Two properties make this cheaper rather than merely different. gh is already a hard, already-authenticated dependency of this application, so the updater inherits that property instead of weakening it. And a locally built app is ad-hoc signed and never crosses a download quarantine boundary, so signing and notarization drop out entirely - the longest-lead item in the original plan.

What changed, and why

Issue #642 proposed a private Homebrew Cask plus electron-updater against a generic HTTPS feed. Internal investigation disproved the premises that plan rested on. The distribution topology collapses from five moving parts to two.

The apply flow

The app cannot replace itself while running. The apply step therefore runs as a detached process that outlives the app, and it is copied to a temporary location before it starts, because both the app bundle and the updater-owned clone are rewritten during the swap. A helper executing from either location would be replaced mid-run.

Any failure at step 6 or 7 restores the backup and relaunches the previous working app, which then surfaces the failure. That is the only way a failed rebuild becomes visible, because the app reporting it is the old app.

Security and failure rules

  • Only this repository's releases are trusted; the slug is not user-configurable in v1.
  • Never install a version lower than the running one.
  • One check and one apply at a time; a repeated action returns the live operation.
  • Verify the packaged app's version equals the target tag before swapping.
  • Keep the previous bundle until the swap succeeds, and restore it if any step fails.
  • The updater is independent of daemon health: a broken daemon must not prevent repairing the app.
  • Never send raw gh stderr, exception stacks, or filesystem paths across the preload bridge.
  • Preserve asar: false, the files allowlist, skills/, and the daemon state directory.

Known boundaries and non-goals

Not the LaunchAgent. scripts/install-service.mjs runs a daemon from a repository clone via tsx. Updating the app bundle does not update a LaunchAgent pointed at a different clone. v1 documents this rather than unifying it.

Not the user's dev worktree. The updater never pulls, stashes, or rebuilds it.

Not Intel. electron-builder.yml pins arch: arm64, so the install refuses on a non-arm64 host with a clear message rather than silently producing a broken build.

Not a downgrade path. Recovery is a higher patch version. No Windows or Linux. No telemetry beyond a local rotating log.

Definition of done

  • A clean supported Mac installs by cloning the repository and running one documented command.
  • The install writes a receipt naming the updater-owned clone and the installed version.
  • The packaged app checks GitHub Releases through gh with no stored credential.
  • An eligible update produces an accessible in-app prompt, and a native path when the window is hidden.
  • Accepting rebuilds, swaps, and relaunches; a failed build leaves the previous app working.
  • The quit ordering is not trapped by hide-on-close and the daemon shuts down cleanly.
  • The updated app reopens the existing Mission Control database.
  • Release Please owns the version, lockfile, generated CHANGELOG.md, tag, and release.
  • Typecheck, lint, unit, Electron, build, smoke, and E2E pass at their appropriate gates.
