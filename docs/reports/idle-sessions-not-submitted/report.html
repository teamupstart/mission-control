Why idle sessions stopped reaching their pipelines

Four dispatched sessions sat idle with their Workflow bindings correctly armed and no run ever started. Two independent deadlocks are responsible. The one that accounts for most of them is a regression: since 2026-08-18 a dispatched Agent SDK launch has been captured into the Goal pipeline twice, and the duplicate is reconciled as an amendment that cannot pass its safety check - which pauses automatic completion for the life of the session.

The answer

Nothing is wrong with the Workflow bindings, the Foreman worker, or the dispatch path. All four idle sessions carry a workflow_bindings row with trigger_mode = 'foreman_complete' and state = 'active', and the Foreman worker is running and acting. What fails is the last gate before the claim.

Root cause A - the regression

A dispatched Agent SDK launch enters the Goal pipeline through two doors that cannot see each other: the supervisor captures the operator's request when the conversation binds, and the harness prompt hook then reports the composed prompt built from it. Both open a prompt revision. The refiner is then asked to reconcile Mission Control's own contract sections as though the human had amended their own request - and when it answers amend, a strict preservation check rejects it and parks the revision unresolved with no retry.

Root cause B - already known and owned

The fourth session got past the intent gate, was judged incomplete by the generic verifier (its durable objective says “open a reviewable pull request”, which the ship handoff had just forbidden it to do), and the resulting hold consumed the work-cycle generation anyway. Every later tick then skips it as already handled. This is described in docs/plans/foreman-ship-shepherd/plan.md, approved 2026-08-21, and a task is already implementing it.

What is actually broken, and what is not

One correction to the framing first, because it misdirects the search: task.pipelineRun being null on these tasks is not the symptom. That field is the Conductor provider-run link and is only ever set for kind: "pipeline" tasks (src/server/dispatcher.ts:245). A Workflow run for a ship task has no field on Task at all - it lives in workflow_runs, hung off a binding keyed by the session's note key. The real symptom is the absence of that row.

Why the duplicate is fatal rather than untidy

The refiner reconciles revision 2 against the objective established by revision 1. Because revision 2 is revision 1 plus several paragraphs of added directives, the model frequently answers amend. An amendment then has to survive a mechanical preservation check: 

// src/server/goal/refiner.ts:156
function amendmentPreservesObjective(current: string | null, proposed: string): boolean {
  if (!current) return false;
  const prior = comparableObjective(current);
  const next = comparableObjective(proposed);
  if (!prior || !next.startsWith(prior)) return false;                    // literal prefix
  const addition = next.slice(prior.length).trim();
  if (!/^(?:[.;,:+-]\s*)?(?:also\b|additionally\b|and\b|plus\b)/.test(addition)) return false;
  return !/(?:\b(?:but|except|instead|drop|remove|…)\b|…)/.test(addition);
}

The proposed objective must begin with the previous objective verbatim and continue with also, additionally, and, or plus. A model rewriting an objective to fold in platform contract text essentially never produces that shape. The failure branch is the problem:

There is one escape, and it explains why one of the four sessions healed while this report was being written. The failure key includes the queue tail: 

// src/server/goal/refiner.ts:144
return `${pending.prompt.revision}:${pending.prompt.prompt ?? "<lost>"}:${pending.goal.promptRevision}`;

so a new human instruction changes the key and buys the blocked head exactly one more attempt. That is why the deadlock is invisible when someone is watching a session and typing into it, and total when nobody is. An unattended dispatched task receives no further input by design - which is precisely the population that was reported as stuck.

Cause B - the verifier hold, already known and owned

One session reached the verifier and was still not submitted. Its durable objective ends “…and delivered through a green pull request”, while the ship completion handoff had explicitly instructed it not to open one during its initial turn (src/server/task-contract.ts:65). The generic verifier is asked whether the full objective was satisfied, has no field for the completion contract, and answers no. The plan states the consequence directly:

This one is not touched by the change accompanying this report. It has an approved two-phase plan and a task already implementing Phase 1 - a task which was itself stuck behind cause A, which is worth noting: the regression was blocking its own fix.

The fix that shipped with this report

Cause A only. The launch is now recognized when it comes back through the hook, and refused a second revision.

The obstacle was that the existing launch marker fingerprints the delivered prompt byte-exactly, while the hook path hands over text that Claude's substantivePrompt has already stripped of injected scaffolding and flattened with .replace(/\s+/g, " "). The two can never match - verified directly against live data before writing any code, which is what ruled out the obvious one-line version of this fix.

The recognizer was then validated against the real launch this report's own session was dispatched with: the delivered prompt was reconstructed from the stored task intent through withTaskKindContract, and confirmed correct by its byte-exact fingerprint matching the persisted marker. FileChange

Both conjuncts in the guard are load-bearing. The fingerprint is what makes it this launch rather than something shaped like it; the existing-revision requirement is what keeps a terminal or Pi launch - which has no supervisor door and whose hook is the only capture - from losing its Goal entirely. Every failure mode of the guard degrades to the duplicate that shipped before it, never to a dropped human instruction.

That second conjunct also makes the guard ordering-dependent, and deliberately so. It suppresses an arrival only once a revision exists, so whichever door lands first is the one that enters the queue. On a dispatch that is the supervisor's, measured at 238 of 238 on this machine with a minimum gap of 84 ms, because the bind arrives on the driver's init frame and the prompt hook cannot fire until the agent already holds the prompt. If that ever inverted, the composed prompt would establish the objective and the operator's request would follow as revision two - not the wedge above, but a narrower ask against a broader objective, which is the ordinary steer the reconciler handles. So the accurate claim is that a dispatched launch is counted once, not that only the operator's request can ever be the one counted.

Six tests were added to test/launch-presentation.test.ts, covering the SDK double capture, the hook-only launch, the inverted ordering just described, a genuine follow-up, a pre-migration row loaded with a null fingerprint, and the normalization boundary itself.

Those sit at the Registry seam, and a prompt revision is four modules away from a run row. So test/dispatched-launch-reaches-workflow.test.ts drives the whole chain the operator was watching, against a real Registry, QueueManager and WorkflowManager over a real SQLite database: a ship task is composed through withTaskKindContract, the launch marker is persisted before registration, the conversation binds, the operator's request is captured as revision one, the delivered prompt is pushed back through substantivePrompt and Claude's UserPromptSubmit hook, the agent works and parks, and Foreman's completion is claimed over POST /api/sessions/:id/workflow-completion - the same route its out-of-process worker calls. The assertion is the durable row: exactly one workflow_runs record, read back from SQLite, hung off that binding.

This matters because each of those four steps re-derives the intent guard from its own source, and the last one - WorkflowStore.claimForemanCompletion - re-reads session_goals out of the database rather than trusting anything the caller passed. A guard that held in memory but not on disk would satisfy the narrow test and still strand the session.

The second test in that file is the regression itself rather than a mutant. Before the fix isSeededLaunchEcho did not exist and every hook prompt was captured, which is byte-for-byte what a marker carrying no echo_fingerprint produces today, so the pre-fix path is still reachable from HEAD. It asserts the failure at the exact step the operator saw: revision two unresolved, decidePromptedWrapup answering skip - the latest instruction has unresolved intent, the binding still armed, and zero workflow_runs rows. Reverting the guard in registry.ts and re-running reproduces that same skip from the live code path, not from the nulled column.

What this did not establish

  • Two links of the chain are stubbed, not run. The integration test above reaches a real workflow_runs row, but it does not spend model tokens, so two steps are supplied rather than executed: Tier 2's reconciliation is seeded as the output the refiner writes for a first prompt it could classify (the reconciler's own behaviour belongs to test/goal-refiner.test.ts), and the prompted verifier's claude -p verdict is assumed complete rather than asked for. The Foreman worker also runs in-process here; test/prompted-wrapup-worker-e2e.test.ts is the file that runs the real worker binary, and it is about loop timing rather than this chain.
  • No browser spec, and the e2e layer cannot see this bug. The second door is Claude Code's own prompt hook, which e2e/fixtures/fake-agents.ts replaces - no spec posts a UserPromptSubmit hook and the fake never fires one, so a dispatched e2e session only ever takes the supervisor door and produces one revision either way. The change also has no rendered surface of its own: it removes a spurious row, and the Goal line a card draws is the refiner's output before and after.
  • The amend-versus-steer split is not quantified. Whether a duplicate strands a session depends on a model classification. 14 of roughly 75 goal rows touched since Aug 19 stranded, but that denominator includes rows updated for unrelated reasons, so it is not a clean rate.
  • Cause B is diagnosed but not verified by re-running it, and is not fixed here. The consumed-generation evidence and the plan's own account agree, which is why it is reported rather than investigated further.
  • Live state moved during the investigation. One session self-healed when a new instruction arrived, and the stranded count fell from 16 to 14. The mechanism is understood (the failure key includes the queue tail) but it means any single snapshot here is a point in time.
  • The guard's own strictness was left alone. A rejected amendment still dead-ends with no operator-visible signal beyond an “unclear” relationship on the card. Removing the duplicate removes the common trigger, not the sharp edge; making that branch recoverable or visible is a separate, defensible piece of work.
