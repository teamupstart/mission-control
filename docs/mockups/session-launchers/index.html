Open a terminal, or the agent's own CLI, on a session

Design archive. These pages preserve the four placement alternatives that were reviewed, including questions and proposals that were later resolved. Option 01 was selected; the implemented behavior is owned by the session-launchers plan and the user-facing README.

Two controls on the conversation pane. Terminal opens a shell in the session's worktree. Claude Code / Codex - labelled with whichever harness this session actually runs - opens that CLI in the same worktree, resumed on this session's conversation. Separate buttons, one shared popover vocabulary, modelled on the files toolbar's Open in menu.

Each option is clickable: open either menu, pick a row, watch what it reports. Every page has a layout switch so you can see the same control drawn by the Console detail pane and by an expanded grid card - the two components that show a conversation.

The one design idea worth agreeing on first. Both buttons open the same list, because the choice a human is making is the same one - which terminal. What differs is only the argv that terminal is handed: a shell, or claude --resume <id>. So this is not a new registry. It is launchHome({ cwd, argv }), which already exists and already knows about tmux, cmux, WezTerm and Ghostty, called with two different argvs from one new route. The rows below are those four real backends, not invented ones.

What I need you to decide with the placement

These came out of reading the code rather than the mockups, and each one changes what gets built. My recommendation is on each - happy to be overruled.

1. What does the agent button do to a session that already has a terminal?

For an embedded session (runtime: "sdk") this is settled: the route already exists as Continue in terminal - it stops the driver and hands the conversation to a real CLI. There is exactly one conversation throughout.

For a session already running in a tmux pane, opening claude --resume <id> starts a second process on the same conversation. Two agents writing one session file is a corruption risk, and the existing focus action already raises the pane the session is in.

Recommend: the agent button focuses a pane-backed session (what you almost certainly want) and only resumes when there is no live pane - an embedded session, or one whose agent has exited. Same button, and it says which of the two it will do before you press it.

2. Resume argv is coupled to the wrong capability

At design time the argv that resumed a conversation lived on SdkSpec.resumeArgv. That coupled an interactive CLI capability to an embedded driver and left pi unable to declare the --session behavior its CLI already supported.

The honest fix is that resuming is a harness capability, not an embedded-driver one. Lift resumeArgv out of SdkSpec onto the harness proper, so a terminal-run Codex session can answer it too, and a harness that genuinely cannot resume declares null and gets a sentence.

Recommend: lift it, and measure Codex's real flag against an install before declaring it - the tui: null lesson in AGENTS.md is exactly this mistake.

3. tmux on its own opens nothing you can see

spawnDetached creates a detached tmux session - correct for a dispatched agent, useless for "open me a terminal". Making it visible means handing tmux attach -t <name> to an installed emulator, which is the walk focus already does.

Recommend: a tmux row is offered only when some emulator can raise it, and it says so on the row ("New session, raised in WezTerm") - otherwise it carries the sentence explaining why not. Never a button that appears to work and leaves nothing on screen.

4. Only four terminals exist to Mission Control

tmux, cmux, WezTerm and Ghostty. Terminal.app, iTerm2, Kitty and Alacritty are not "off" - there is no adapter, which is why the mockup shows iTerm2 as a greyed row with that exact sentence rather than hiding it.

Recommend: ship with the four that exist and let the greyed row advertise the extension point. If iTerm2 or Terminal.app matters to you day to day, say so and I will scope an adapter as its own phase - it is a real piece of work (an AppleScript backend, the way Ghostty is), not a line in a list.

5. Sessions with no checkout

Session.cwd is nullable and genuinely null sometimes - discovery could not read the process's cwd and no pane reported a path.

Recommend: both buttons render disabled with "this session has no checkout to open" rather than disappearing, so the control does not flicker in and out as discovery settles.
