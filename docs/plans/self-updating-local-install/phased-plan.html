Phased implementation plan

Self-updating local install

Three serial merge units let a cloned repository become an installed macOS app that keeps itself current through the gh CLI, with no Homebrew, no hosted feed, no stored credential, and no Apple signing dependency.

Decisions resolved · scheduling after publication

Approved decisions

Install: clone the repository and run one install script. No Cask, no private tap, no Jamf, no UMT.

Update transport: the gh CLI against this repository's GitHub Releases.

Update mechanic: rebuild from source at the release tag, then swap the app bundle.

Source clone: the updater owns a private clone; the user's own worktree is never touched.

Rollout: no percentage rollout in v1. Recovery is a fix-forward patch release.

Signing: Developer ID signing and notarization are out of scope for v1.

Why three phases

The estimate is far above the single-phase threshold, so more than one phase is permitted. Three are justified and a fourth is not. Phase 1 defines the receipt and release identity that Phase 2's controller reads. Phase 2 is the highest-risk work in the plan, a process that outlives the app and replaces its own bundle, and it needs to be reviewable and revertible alone. Phase 3 is a genuine vertical slice whose parts are not observable separately.

1,100–1,500estimated non-test production lines
3serial reviewable pull requests
1repository; no cross-repo phase

No concurrency groups. The chain is strictly sequential and that is a real constraint, not a presentation order: Phase 2 consumes Phase 1's receipt schema and needs releases to exist to test against, and Phase 3 consumes Phase 2's state union and IPC names.

What the new architecture removes

The change is almost entirely subtractive. Because the app is built on the user's own Mac, it never crosses a download quarantine boundary, so the longest-lead item in the original plan disappears.

Final audit

Every source-plan requirement and approved decision is owned by exactly one phase. Every consumer follows its prerequisite. No concurrency is claimed, because none holds.

One defect found and fixed rather than deferred. Documentation had been scoped only into Phase 1, which would have left the updater and the banner undocumented and broken the definition of done. docs/desktop-and-packaging.md is now scoped into Phases 2 and 3 as well, recorded in both phases' audit records.

Two risks are carried openly in Phase 3 rather than resolved on paper: the flat-versus-namespaced preload shape, and the topbar geometry interaction with a new full-width banner. Both are decisions the implementing agent should make against the code, with reasoning recorded in its pull request.
