# Phase 5: The Mission Control Datadog dashboard

Source plan: [plan.md](plan.md), section "The Datadog dashboard". Index:
[phased-plan.md](phased-plan.md).

## 1. Outcome and value

A **Mission Control** Datadog dashboard is kept as code at
`observability/datadog/dashboards/mission-control.json`. It reads only what the `datadog-lean`
shape actually sends. A unit test fails the build if any widget queries a metric, label or
span attribute that the shape does not export, so the dashboard cannot silently go blank after
a catalog or shape change.

Applying it to Upstart's Datadog organization is an outward-facing step for a person. This
phase produces and validates the definition; it does not apply it.

## 2. Entry criteria and dependencies

- Direct phase dependency: **Phase 2**. The validator reads `exportedInstruments("datadog-lean")`,
  and there must be no second copy of the lean rules.
- It can run concurrently with Phases 3, 4 and 6. It adds new files only, plus one section in
  `docs/observability-dashboards.md`.

## 3. Scope and non-goals

In scope:
- the dashboard JSON;
- its validator test;
- documentation of what each group shows and how to apply the dashboard.

Non-goals:
- applying the dashboard;
- monitors or alerts;
- Grafana changes;
- metrics the lean shape does not send, including the cohort gauges.

## 4. Repository findings and inherited contracts

Findings. Line numbers were taken on 2026-09-28.

**Grafana precedent.**
- The Grafana dashboards are generated by `scripts/observability/dashboards.ts` and checked for
  drift by `test/telemetry-dashboard-definitions.test.ts`.
- That test asserts that every panel source is a key of `TELEMETRY_METRICS`, that every
  expression carries `$environment` and `$installation`, and that there is no `or vector(0)`.
- It does not check group-by labels against dimensions, so this validator is stricter than
  its model.
- **Do not reuse** `metricName()` or `promMetricName()`. Those produce Prometheus names, and
  Datadog keeps the dotted OTel name unchanged, as the validation point showed.

**Tags.**
- Datadog tags seen on the validation point: `service`, `version`, `env` (both `corp` and the
  local value), `service.instance.id` (lowercased), data-point attributes,
  `instrumentation_scope` and `host`.
- Under `datadog-lean`, `host` is the constant `mission-control`.

**Spans.**
- Spans carry every event attribute as `mission.<key>`, plus `mission.actor.*`
  (`src/server/telemetry/projection.ts:153-165`).
- Span names come from `TELEMETRY_EVENTS[...].span.name`.

**Costs.** `datadog.estimated_usage.metrics.custom.by_metric` is Datadog's own metric, and the
cost-watch widget uses it.

Inherited from Phase 2:
- `exportedInstruments(shapeId)` returns each exported name, its exported kind and its labels.

## 5. Implementation steps, in order

1. **Dashboard JSON (`observability/datadog/dashboards/mission-control.json`).**
   - `layout_type: "ordered"`, with a title and a description stating the source and the shape.
   - Template variables:
     - `env`, default `corp`;
     - `version`, default `*`.
   - Every widget filters `service:mission-control` and `$env`, and excludes `env:test`,
     `env:local` and `env:development`.
   - Groups, from the source plan:
     - **Adoption:** distinct installations over 1, 7 and 28 days.
       - Use `count_nonzero` over `mission.telemetry.health.observed_at` by
         `service.instance.id`. That gauge's value changes every cycle while the daemon runs,
         so it is sent every cycle, and Phase 1's catalog heartbeat guarantees at least hourly
         reporting even without events.
       - Add a span-based alternative on the session spans.
     - **Sessions and dispatch:** started and ended sessions by agent, runtime and task kind;
       dispatch outcomes; p50 and p95 of `mission.session.turn.duration` and
       `mission.dispatch.duration`.
     - **Usage:** `mission.usage.tokens` and `mission.usage.cost` by `model_id` and
       `usage_origin`, with a note that this is API-equivalent and never subscription billing.
     - **Outcomes:** `mission.task.outcomes` by status and completion evidence, and
       `mission.pr.observations` by fact.
     - **Workflows and Personas:** runs started and finished, node dispositions, persona
       verdicts, and finding categories.
     - **Reliability:** `mission.errors` by component and code, and `mission.action.count` by
       feature and outcome.
     - **Telemetry health:** pending, oldest pending age, and last accepted, per installation.
     - **Cost watch:**
       `datadog.estimated_usage.metrics.custom.by_metric{metric_name:mission.*}`, divided by
       distinct installations, with a marker at 150.
2. **Validator (`test/datadog-dashboard-definition.test.ts`, new).**
   - Load the JSON and walk widgets recursively, including group widgets' `definition.widgets`.
   - Collect every query string, from `requests[].queries[].query` and any legacy `q`, and
     parse `aggregator:metric{filters} by {tags}` plus formula references.
   - **Every metric must resolve:** each metric name is either an `exportedInstruments("datadog-lean")`
     name, or one on an explicit allowlist that is exactly `datadog.estimated_usage.metrics.custom.by_metric`.
     Nothing else resolves.
   - **Tags:** every filter and group-by tag is either one of that metric's exported labels,
     or one of the resource tags `service`, `env`, `version`, `host` and `service.instance.id`.
   - **Required filters:** every query includes `service:mission-control` and `$env`.
   - **Template variable:** `env` defaults to `corp`.
   - **Spans:** span queries (`data_source: "spans"`) reference only span names from
     `TELEMETRY_EVENTS` and attributes that exist on those spans.
   - **Hygiene:** widget ids are unique, there are no duplicate titles within a group, and no
     query references `mission.analytics.v1.`.
3. **Docs (`docs/observability-dashboards.md`).**
   - A "Datadog dashboard" section: what each group shows, that it is built for the
     `datadog-lean` shape, and that its numbers are organization-wide aggregates with
     per-installation drill-down.
   - How a person applies it: Datadog's dashboard JSON import, or the Datadog API. State that
     the repository never applies it automatically, and that an agent may apply it only when a
     person explicitly authorizes that write.

## 6. Data, API and compatibility

- No runtime code changes, and no persisted data.
- The dashboard JSON is data. A catalog or shape change that breaks it fails the validator,
  which is the intended coupling.

## 7. Tests and verification

```sh
node --test --import ./test/setup-state.mjs --import tsx test/datadog-dashboard-definition.test.ts
npm run typecheck
npm run lint
npm test
```

- Include a negative self-test in the validator: a fixture widget that queries a dropped label,
  and one that queries `mission.analytics.v1.runs.eligible`, must both be refused.
- No e2e spec: this adds no dashboard UI to Mission Control.

## 8. Merge and exit criteria

- The JSON validates, and the validator's negative fixtures are refused.
- The docs describe it and how to apply it.
- The suite is green.
- Applying the dashboard is listed as a rollout step, not done here.

## 9. Downstream handoff

- The dashboard path and its validator. Phase 6's pilot may use the cost-watch group, but
  does not depend on it: Phase 6 queries Datadog directly.
- A later change to the lean shape must keep this validator green, and the validator is where
  that coupling is enforced.
