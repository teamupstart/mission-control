Why Test Evidence Auditor rejects so often

“Investigate why the Test Evidence Auditor constatly rejects sessions for lack of test evidence. Why does it happen? What is are the most common issues? Finally, lay out recommendations on how we can modify the workflow or session prompt to increase the likelihood sessions will have sufficient test evidence and are less likely to have test evidence rejected.”

The auditor was usually not rejecting tests. It was rejecting an evidence packet that could not show the tests ran or the UI rendered. At the time of this snapshot, agents executed checks in tool calls, but Mission Control’s normalized transcript dropped tool-result bodies and the initial session appendix described only optional screenshots. A strict, intentionally fail-closed Persona then saw a diff, prose claims, and a broad check tail, but often no task-specific run output and no pixels.

Post-analysis status, 20 Aug 2026: This page records the pre-change baseline that motivated the implementation. The shipped session appendix is now a “Workflow evidence readiness” contract that explicitly documents direct commandOutputs, rendered images, and existing UTF-8 artifacts. The measurements below predate that change and should not be read as the current prompt contract. Recommendation 03, the pre-Persona readiness gate, was intentionally excluded from the implementation.

The failure is produced by the handoff between execution and review

In the measured pre-change workflow, the evidence channel was capable but the initial prompt did not tell the agent to use its text half, and the ordinary transcript could not carry tool output as a fallback. The shipped readiness contract now closes that prompt gap.

The auditor is designed to fail closed

Its guidance says unit tests alone are insufficient, generic pass lines and prose claims do not count, UI-facing changes require reviewer-visible pixels, and absent evidence is a fail even when the code looks correct. That is deliberate behavior, not a random model tendency.

Source: personas/test-evidence-auditor.md:8, :38, :47, :59.

The delivery prompt understated the obligation

In the analyzed snapshot, the ship-task appendix was titled “Optional visual workflow evidence.” It explained screenshots only and ended by calling registration optional. That historical mismatch was the basis for this finding. The shipped appendix now instructs sessions to use direct commandOutputs, images, or existing UTF-8 artifacts as appropriate.

What the local history shows

Read-only SQLite snapshot taken at 2026-08-20 20:40 local time. It covers 134 Test Evidence Auditor attempts across 45 runs and 44 conversations from 2026-08-13 through 2026-08-20.

Native evidence support helped, but did not solve first-round readiness. Attempt failures fell from 76.0% under the legacy guidance snapshot to 55.9% under the current native-evidence guidance. Yet 14 of 17 current-guidance runs still failed their first auditor submission. Thirteen of those 17 initial packets had no image, and all 17 had no text artifact.

Recommendations from the pre-change analysis

These recommendations explain the implementation this report motivated. The workflow and session-prompt fixes were shipped, except recommendation 03, the pre-Persona readiness gate.

  1. Replace the optional visual appendix with an evidence-readiness contract P0

    Tell every workflow-bound ship session, before implementation starts, exactly what the reviewer can and cannot see. Cover both images and artifacts. State that ordinary tool output, prose summaries, PR comments, and unregistered local files do not enter the Persona packet.

    • For UI changes: require one runtime capture for each materially distinct state named in the intent, plus the focused browser-test output.
    • For API, CLI, lifecycle, and logic changes: require a focused test or reproducible request/response transcript tied to the acceptance criterion.
    • Require the agent to register the final successful output and captures before ending its task turn, with captions that name the behavior demonstrated.
    • Keep code/tests and proof separate: evidence files remain gitignored and uncommitted.

  2. Make repair packets evidence-channel specific P0

    The current suffix says only “verify the work.” When Test Evidence fails, append a deterministic recipe based on the requested evidence kind: use artifacts for a test transcript and images for a visual, register it after the final run, then stop. Warn that merely rerunning and summarizing will reproduce the same verdict. Keep Mission Control’s engine as the owner of resubmission.

  3. Add a pre-Persona evidence readiness gate P1

    Before spending a Test Evidence model call, surface the immutable packet inventory: image count, text-artifact count, Check commands, retained bytes, omitted bytes, and acceptance criteria. Block or explicitly warn when a UI-facing change has zero images, or when a behavior change has neither a focused artifact nor a detailed task-specific Check. Prefer an explicit evidence map from the agent over filename heuristics.

  4. Give focused command output a first-class capture path P1

    Do not rely on normalized conversation transcripts for tool output. Either add a small “run and register evidence” Mission tool that records command, exit code, HEAD, and bounded stdout/stderr atomically, or make the session helper create and register a gitignored UTF-8 log. Preserve head plus tail so the command and selected test names survive alongside the footer.

  5. Align the Persona guidance with the actual transport P1

    Remove “evidence artifacts committed alongside it,” which conflicts with the repository’s no-evidence-commit rule and the task appendix’s “do not commit.” Explicitly say PR attachments are not Persona transport. Add a proportional matrix: focused regression output may settle pure logic; request/response settles API behavior; runtime pixels plus focused browser output settle UI behavior. Keep the fail-closed standard, but stop inviting impossible or downstream proof.

  6. Instrument evidence readiness and audit overreach P2

    Track first-pass rate, staged image/text adoption, rejection reason, evidence omission bytes, and repair rounds by workflow version. Flag verdicts that ask for PR, CI, Inspector, or merge proof before those stages unless the original human intent explicitly requires it. This catches the small but real class of auditor overreach without weakening valid evidence failures.

Shipped evidence-readiness excerpt

## Workflow evidence readiness
Before completing the task, make sure the next Persona can inspect evidence for each material
acceptance criterion. Personas receive the diff, bounded transcript, upstream Check results,
and evidence registered through Mission Control. They do not receive ordinary tool-result
bodies, unregistered files, or later pull-request comments and checks.

Use submit_workflow_evidence to close those visibility gaps: pass commandOutputs with the exact
completed focused command, exit code, output, repository scope, and a precise caption; pass
images with a checkout-relative gitignored PNG, JPEG, GIF, or WebP when the claim concerns
rendered UI. Existing gitignored UTF-8 logs may instead use artifacts.

Capture evidence after the final relevant run, check that registration succeeded, and keep it
proportional. One focused artifact may prove many tests or acceptance criteria; do not submit
one output per test or dump an entire large suite when a focused run demonstrates the behavior.

Do not commit evidence artifacts. Native registration carries proof to the Persona and does not
replace focused tests or verification.

Recommended rollout and success measure

First: prompt and packet wording

This is the smallest, safest change and directly targets the zero-of-17 text-artifact adoption in initial current-guidance submissions. Ship it with reason telemetry and compare the next 30 runs.

Then: readiness gate and capture helper

If first-pass failures remain above 30%, add the gate and atomic command capture. Target at least 70% first-pass acceptance, at most 1.5 auditor attempts per run, and zero UI first submissions with an empty image manifest.

Do not “fix” this by weakening the auditor to accept green summaries. The useful contract is that the demonstrated behavior, not merely the implementation, reaches review. The repair is to reliably transport proportionate proof and reject impossible/downstream requests.

What this did not establish

  • This is one operator installation and 45 runs over seven days, not a cross-installation product sample. Thirty runs used No-Mistakes Review v8 and 15 used v10; guidance and evidence support changed during the period.
  • The report did not independently decide whether every rejected change actually worked. It evaluated what the immutable reviewer packet contained and why the Persona rejected it.
  • Keyword categories summarize recurring wording and can misclassify nuance. The current first-failure split is stronger: all 14 requested changes classified cleanly as 11 visual artifacts and 3 executed-test/output artifacts.
  • The proposed prompt and workflow changes were not A/B tested. The suggested targets are rollout criteria, not measured outcomes.
  • The measurements predate the shipped readiness contract. This report does not establish its post-rollout adoption or rejection rate.
  • The raw database snapshot was intentionally not included because it contains unrelated operator and session data. Only bounded aggregates are archived here.
Historical scout finding: Test Evidence Auditor exposed a proof-transport gap. The shipped readiness contract now makes task-specific command output, images, and existing text artifacts explicit completion evidence; post-rollout effectiveness remains unmeasured here.
