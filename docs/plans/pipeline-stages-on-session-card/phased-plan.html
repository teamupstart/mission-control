Phased implementation plan

Pipeline stages on a session card

One phase, one implementation task: the phase meter, its hover popover, and the Tooltip widening it needs, shipped as a single vertical slice.

The feature is entirely browser-side. There is no schema, migration, route, or SSE frame to land first, so there is no foundational phase to sequence - and the only natural split is a small preparation phase the sizing rules forbid.

Findings that changed the shape of the work

No new data path, so no early phase

The source plan claimed the run is already in the browser. Confirmed concretely: useEventStream holds pipelineRuns keyed by run identity, App.tsx derives pipelineRunByKey and passes it down, BoardView already reads that map, and pipelineRunKeyOf accepts a SessionPipelineLink structurally - so no adapter.

A plan with no persistence, no wire change, and no migration has no natural early phase to put first. That is the single biggest reason this is not split.

One correction to the source plan

Widening Tooltip is not only a prop change. .tooltip is text-align: center with its own padding and a 260px cap, so the component must also mark the bubble as rich for CSS to switch layout. Recorded in Phase 1, step 1.

Also confirmed: the bubble is already aria-hidden and pointer-events: none, so rich content is safe for accessibility and cannot steal hover from the segment that opened it - but it must stay non-interactive, which the design is.

Why one phase

The estimate is above the 200-line one-shot threshold, so the default of one phase has to be justified rather than assumed.

Nothing to land first

No schema, migration, persisted field, route, SSE frame, or MCP tool. The usual reason to phase - a contract consumers must wait for - does not exist here.

The only split is a forbidden one

Carving out the Tooltip widening is roughly 35 lines and would deliver an unused API arm with no user-visible behavior - precisely the small preparation phase the sizing rules exclude. It would also leave the popover unbuildable until the second phase merged.

A layer split would be a dead surface

A meter with no popover, or a registry entry with no region, are both half-features. The plan's own value is the hover detail.

Low risk for the size

No concurrency, no state machine, no compatibility window, no data at rest. Complexity sits in CSS geometry and one additive prop widening, both locally testable and both already covered by guard tests.

It is within a mid-tier model's reach because the hard thinking is already done: the fold exists, the tones exist, the tokens exist, .wf-tile-peek is a close precedent, and the phase file names every file and every tolerance rule. Combining is both safer and more reviewable than splitting.

Cross-phase contracts

With a single phase these are not handoffs between phases; they are the contracts a future change should inherit rather than relitigate.

  • Tooltip's label is string | TooltipContent. A future rich tooltip uses that arm; it does not add a second hover primitive, and it never puts markup in the description node that aria-describedby resolves to.
  • The meter reads pipelineStrip / pipelinePhaseStatus. Extending it to the console rail row, the detail band, or a managed Pipeline host is a rendering change at the leaf's call sites - not a new fold, and not a wire change.
  • SessionPipelineLink stays as it is. The pattern for "the card needs more about a run" is the client-side join, not a wider session frame.
  • The board-card registry id is the persisted operator preference (hiddenDisplayItems stores ids), so renaming it later is a preference migration.
  • The tolerance rules are load-bearing: geometry from run.steps, unknown steps counted in the total, out-of-band steps never given a segment.

Final verification strategy

Owned by Phase 1 and listed in full in its file.

  • Fold tests over a mid-run, halted, all-skipped S-tier, stale/kicked-back, unknown-step, one-step-phase, and empty-step-list run.
  • A test asserting segment tones come from pipelinePhaseStatus - what stops a second fold appearing later.
  • board-tile-render, board-card-items and tooltip-coverage stay green.
  • A new Tooltip node-arm test asserting the description node is plain text.
  • A required e2e/ spec: the meter appears for a correlated session, hovering a segment reveals that phase's status, and the Settings row hides it.
  • No data-testid, no model tokens, no new hex in styles.css.
  • npm run typecheck, npm run lint, npm test, npm run build, npm run test:e2e.
  • Visual evidence on a real board card in the built dashboard - running and halted, normal and narrow columns - attached to the PR and never committed.

The final state matches the source plan with no cleanup deferred to anything outside Phase 1.
