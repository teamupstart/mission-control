Guided setup - phased implementation

Three merge units. Phase 1 ships the whole read-only feature - catalog, detection, and the Setup panel. Phase 2 adds the one thing that executes, on its own reviewable boundary. Phase 3 adds the onboarding surface. Phases 2 and 3 are concurrent.

Repository findings

Investigated against this checkout before the boundaries were drawn. Two of these changed the design; all of them belong to a phase.

  1. Every probe the catalog needs already exists, and each is the function the refusing path itself calls: agentBinPresent (src/server/dispatcher.ts:2243), binPresent with TMUX_BIN / CMUX_BIN / WEZTERM_BIN / GHOSTTY_BIN, terminalTargetViews, resolveBinPath and onPath, ghBin() (src/server/config.ts:236), installedPlugins(), and the conductor provider's binForPresence() / probe(). Phase 1 writes no new detection mechanism.
  2. Detection must resolve through the env-override chain, not by probing a bare name. resolveBinSpec reads MISSION_ then FLEET_ then HARNESS_; resolveBin reads a backend's own spec.env; ghBin() reads MISSION_GH_BIN. A probe that asked onPath("gh") directly would report the operator's real machine while dispatch used the override - and would make the e2e spec in finding 4 impossible. Hard contract on Phase 1.
  3. The install path already exists and is the model to copy, not to invent. POST /api/pipelines/install (src/server/routes.ts:5627) takes provider, checkout, and backend from the browser, resolves argv through the provider, wraps it in a hold-open shell that prints the exit code and waits for a keypress, and hands it to terminalLauncher. GET /api/terminal-targets (routes.ts:2791) already answers which backends can open a window, pair-aware.
  4. The e2e harness can already arrange installed-versus-missing for four of the five families. e2e/fixtures/daemon.ts:285-325 redirects the three agent binaries, CMUX_BIN, MISSION_GH_BIN, and MISSION_CONDUCTOR_BIN - and already has a startsMissing mode pointing the conductor override at a not-yet-installed path, which is exactly the missing-row case. But WEZTERM_BIN and GHOSTTY_BIN are not overridden, so those rows would read "installed" on a laptop and "missing" on CI. Phase 1 adds both overrides.
  5. The tour is a bigger artifact than it looks, and part of it is generated. src/web/tour/content.generated.ts is written by scripts/tour-content.ts from tours/*.md via npm run tours. A tour also needs a TourId union member, a stage file (335 and 415 lines for the two shipped tours), a TourEntry, a target namespace, and target refs registered by the components it spotlights. This is most of why the banner and tour are their own phase.
  6. The settings surfaces a new category has to satisfy are already pinned by tests. SETTINGS_CATEGORIES is read by the router, the page, the search index, the dots, and settings-sidebar-render.test.ts, which fails on a duplicate data-anchor or an anchor whose prefix is not a category.
  7. SettingsStatus is not the channel for this. It is a fixed struct of the daemon's own config, emitted on config writes and folded into registry.snapshot(), and settings-dots.ts derives every dot from it. So the Setup category ships without a rail dot in v1; the Phase 3 banner is the attention surface instead.

Why three phases. The estimate is far above the 200-line one-phase threshold, so the only question is where the boundaries fall.

  • Phase 1 alone is already a complete, useful feature - every dependency, its status, what it unlocks, and a link or copyable command. Nothing in it is a dead surface awaiting a later phase.
  • Phase 2 must not be folded into Phase 1. It is the only phase that makes Mission Control execute anything on the operator's machine, and the one place a mistake is a remote code execution rather than a wrong label. Inside a ~900-line panel diff, the argv ownership rule would be reviewed as a detail of a UI change; alone it is a ~300-line diff whose entire subject is that boundary.
  • Phase 3 must not be folded into either. ~500 lines of onboarding surface with a generated artifact and a five-file tour registration, sharing nothing with the install path but the panel it points at. Combined with Phase 2 it would mix a security-critical route with tour copy.

Concurrency. Neither Phase 2 nor Phase 3 reads a file, route, schema, or decision the other introduces. Their one shared file is SetupPanel.tsx, and the seam is stated in both phase files: Phase 1 ships the panel with a per-row remedy action slot and per-family section elements carrying stable ids, so Phase 2 edits inside the row action while Phase 3 attaches tour refs to the section wrappers and hoists the checks hook to App. Disjoint regions, so neither breaks the other's behavior; the hoist does change the panel's prop signature, so whichever merges second rebases through a mechanical prop-wiring change. Phase 1 keeps that state and its recheck prop-passable so the hoist is a move rather than a rewrite.

Cross-phase contracts

Owned by Phase 1, relied on by the others, and not to be changed by them:

  1. SETUP_DEPENDENCY_IDS is append-only and ids are the natural key. Later phases may read an id; neither renames, reorders, nor removes one.
  2. The full SetupRemedy union - link, command, provider-installer, skill - is defined in Phase 1, including command.argv, even though Phase 1 only renders it as copyable text. Phase 2 therefore adds a route and a control and changes no shared contract.
  3. SetupStatus has exactly four states. A phase needing a fifth states the case in its audit record rather than overloading unknown.
  4. Every probe resolves its binary through the same override chain the launcher uses.
  5. GET /api/setup/checks computes per request and caches nothing - not durably and not in memory; cost is bounded by concurrency plus a per-probe timeout instead. No phase puts setup detection on a poll tick, in SettingsStatus, or in the registry snapshot.
  6. Panel structure: one section per family with a stable element id, one row per dependency carrying data-anchor="setup/<slug>", an accessible name, and a remedy action slot. Anchor slugs derive from the discriminated row id, so no two sources' ids can collide.
  7. SetupRowId / SetupRowView / ENVIRONMENT_ROW_METADATA: one row shape produced from three sources (catalog dependencies, folded environment checks, and derived rows such as the terminal pair), discriminated by source and all present in the single SetupChecksView.rows list. Rows are added by adding catalog data, never by branching on an id at a render site. requirement sits on the row, so a family can be required through a derived row while each of its members stays optional - and any consumer asking about "every required row" must iterate that one list rather than the dependency catalog.
  8. The daemon never installs anything in-process. Phase 2 is the only phase that may cause execution, and only by handing vetted argv to a visible terminal. The one path-shaped value it accepts, a provider installer's checkout, is a selection the daemon re-verifies against its own enumerated candidates.

Final verification

After Phase 3 merges:

  • npm run typecheck, npm run lint, npm test clean.
  • npm run build and npm run smoke, since routes and browser surfaces changed.
  • npm run test:e2e with the three specs the phases add, plus dispatch-environment-warning still green - the environment check keeps its own registry and its dispatch-form note.
  • A manual pass on a real machine: open Settings → Setup, confirm the statuses match what the machine actually has, follow one link, copy one command, and run one remedy in a terminal.
  • Docs read back correctly: docs/setup.md, docs/ui.md, docs/skills-and-settings.md, docs/harnesses-and-terminals.md.
