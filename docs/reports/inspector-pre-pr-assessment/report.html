Inspector is four systems wearing one name

Would moving Inspector before PR creation be as simple as cloning it into a Persona and keeping a “GitHub Inspector” setting?

Answer: yes for a safe dual-mode rollout, no for a full replacement.

A built-in Persona can move the model review and repair loop before PR creation. The current Inspector also owns adopted-PR observation, GitHub thread lifecycle, exact remote-head review provenance, and Shipping's clean-review gate. Those do not come with a Persona clone.

The selected lowest-risk path is a new pre-PR Code Quality Judge Persona plus the current service relabeled as optional GitHub Inspector. A strict local-only conversion needs a neutral PR observer and an exact-commit local review attestation.

4 separable responsibilities: local model review, adoption, GitHub conversation, and exact-head shipping provenance.

The load-bearing split

Persona parity matrix

CapabilityPlain PersonaEvidence
Pre-PR diff review and repairYesWorkflow capture and engine already pass local diff, transcript, standards, intent, decisions, and prior feedback into structured Persona verdicts.
Dirty and untracked workYesWorkflow capture uses the working tree and includes untracked files before PR creation.
Read-only repository explorationNoWorkflow Persona calls pass no tool grant. The current Claude Inspector alone receives Read,Grep,Glob with deny paths.
PR title/bodyNoThe PR does not exist. Workflow intent and transcript become the replacement context.
Remote push watchingNoPersona attempts are activated by workflow submissions, not GitHub head changes.
Inline review, replies, resolutionNoThe GitHub API, ownership marker, author check, and thread ledger are Inspector-specific.
Cross-push finding fingerprintsDifferentWorkflow attempts and requested changes are durable but do not use Inspector's GitHub-thread fingerprint state machine.
Verified PR action remote proofNoThe action reads adopted PR head/state written by the Inspector poll. A neutral observer must keep this current.
Current Shipping authorizationNoShipping requires a live published review for the exact remote head, zero Inspector findings, and current GitHub gates.
The settings point: the current enable switch is already the proposed GitHub Inspector toggle in substance. Renaming it is easy. Using a global setting to add or skip a local Persona is not: published workflow graphs are immutable and runs are pinned to them.

Options and effort

Recommended

A. Dual mode

Add the pre-PR Code Quality Judge Persona and a new built-in workflow version. Relabel the existing optional remote reviewer as GitHub Inspector.

  • Small to medium
  • About 300 to 600 non-test lines
  • One implementation phase/PR
  • Preserves Shipping and old workflows
  • Duplicates review when both modes are on
Strict local-first

B. Split observer

Remove active GitHub review behavior, retain a neutral adopted-PR observer, and add exact-commit review attestations for Shipping.

  • Large
  • About 900 to 1,500 non-test lines
  • Two or three implementation phases
  • No Inspector comments
  • New persistence and shipping proof
Highest fidelity

C. Privileged stage

Create a first-class local Inspector evaluator with the current read-tool grant, plus the observer and attestation work from B.

  • Very large
  • About 1,300 to 2,100 non-test lines
  • Three or four implementation phases
  • Surrounding-file exploration
  • New persisted workflow contract

Limits of this investigation

The effort ranges are architectural planning estimates, not measured diffs. They exclude tests and generated Persona payloads. No prototype or runtime experiment was performed, no GitHub API call was made, and no current persisted database was inspected. A phased implementation plan should re-estimate the selected option against exact file-level work and merge boundaries.
