Mission Control · design options

Showing a bound workflow, as it executes, on the card

A workflow run gets a whole embedded strip on the card: a named stage, a segmented rail, a ticking clock, findings and the buttons to answer a gate. A bound workflow run gets one pill in the header that says Preview · R2, and everything else lives two clicks away on the Runs page. These four options close that gap. Each one draws the same four run states so they can be compared like with like, and each states what it would cost to build.

A

Gate rail

The workflow ladder, applied verbatim, with the Inspector as its own segment.

One segment per stage, full width, exactly as a board tile already draws a workflow run. Above it, the stage name and position; below it, one line of why. The move that makes this more than a copy is the terminal gate segment: the Inspector wait is drawn as a place in the pipeline, set off by a hairline, rather than as a sentence underneath. A run parked at the gate looks parked.

A stage where nothing actually ran is hatched, not green. Today the built-in workflow records unconfigured checks as skipped-and-passed, and a flat green segment would tell the operator a gate held when no command was run.

What A costs

  • WorkflowRunSummary gains a bounded stages: { name, status, degraded }[] plus stageIndex and startedAt. Everything else it already carries.
  • One new leaf in session-bits.tsx (WorkflowStrip), one CSS section, one SESSION_FIELD_COMPARATORS entry if the summary ever moves onto Session (it does not have to: the browser already joins runs to sessions by id in App.tsx).

  • Weakness: the rail is anonymous. Which of the three reviewers failed only appears in the list underneath, and with four or more parallel reviewers that list clamps.
B

Reviewer roster

Named members instead of anonymous segments.

A workflow's stages are not interchangeable steps the way lint and ci are. They are named judges with opinions, and which one objected is the single most useful fact about a failed round. B spends the vertical space that A saves on saying so: every member is a chip carrying its own name, its own state glyph and its own tone, wrapping across stage seams.

Checks are dashed, matching how the pipeline editor already distinguishes them, and a check that did not actually run says NOT RUN on its face rather than wearing a tick.

Detail is where B is best: the roster stops wrapping at ~520px, so all six members sit on two lines and every requested change is readable without the +2 more fold.

What B costs

  • WorkflowRunSummary gains a bounded members: { name, kind, state, degraded, changeCount }[]. That is the biggest addition of the four options, and it needs a cap plus a documented collapse rule, or a fifteen-persona workflow makes one card taller than the viewport.
  • Needs the collapse rule to be a real design decision, not a slice: passed stages become counts, the current stage keeps names. Write it down or every future stage count re-litigates it.
  • Weakness: at the grid's 330px minimum, six members wrap to three lines. The strip is roughly 30% taller than A in the running state, on the card that needs the least attention.
  • Strength: it answers "who objected" without a click, which is the question a failed round actually raises.
C

Repair loop

Rounds as the primary axis, stages as the secondary one.

A workflow run is a line: nine steps, one direction, done. A workflow run is a loop. Any fail returns the submission to the session and the whole pipeline runs again, up to maxRepairRounds. A and B both draw the loop as if it were a line and put the round in a corner.

C inverts that. The top rail is the rounds, one segment each, spent ones tinted by how they ended and unspent ones hatched; the thin rail underneath is the current round's stages. That makes the two facts that actually need a human legible at a glance: how many attempts are left, and whether it is failing the same way every time. The repeat-offender line is only computable on this axis.

The tile rail becomes the round rail. Six red segments is a very loud, very cheap signal, and it costs the tile nothing it was not already drawing.

harness-9 ⍉ ≈$
Console / board detail

Detail can afford both rails plus the per-round reviewer names, which is very close to the Runs page round scrubber. That overlap is worth deciding deliberately rather than growing into.

What C costs

  • WorkflowRunSummary gains rounds: { round, outcome, blockingMember }[] (bounded by maxRepairRounds, which is already capped at 20) plus the current round's stage states.
  • The repeat-offender sentence is a genuine server-side derivation, not a projection: "the same member failed N rounds running". It belongs beside compactGate in workflows/store.ts, computed once, never in the browser.
  • Weakness: two rails means two things to read, and in the common healthy case (round 1, sailing through) the round rail is five hatched segments saying nothing.
  • Strength: it is the only option that surfaces a repair loop burning money without converging, which is the failure mode that costs the most and is currently invisible until someone opens the Runs page.
D

Stage ladder

Vertical, for the Console and Board detail panes, where height is the cheap axis.

The other three fight for horizontal room on a 330px card. The detail pane has neither that constraint nor that shape: it is a tall column, and the thing worth showing there is the whole pipeline with the failing stage opened in place. D is a spine with one rung per stage, reviewers nested under theirs, and the rejected verdict expanded inline where you are already looking.

D is not an alternative to A/B/C so much as their detail-pane companion. It is drawn here as a standalone option because it could also ship alone, with the collapsed card keeping only today's chip.

An uncertain delivery is the one workflow state that is genuinely dangerous to guess about, and it is the state a chip can least afford to reduce to one word. D gives it its own rung with the exact shipped sentence.

How D degrades into the other three session drawings

Grid card, collapsed

D does not fit a collapsed 330px card and should not try. Shipping D alone means the grid keeps today's chip; shipping D beside A means the ladder is what the chevron expands into.

Board tile

Unchanged from A: one gate line plus a rail. A tile is 7px gaps and two-line clamps; a ladder there would double every column's height.

Console rail

Unchanged: a toned ⍉ glyph.

What D costs

  • Needs per-attempt detail the SSE summary deliberately does not carry, so it is an HTTP fetch on open (the Runs page detail endpoint already returns exactly this), not a widening of WorkflowRunSummary. That is the cheapest server change of the four and the most expensive client one.
  • Overlaps the Runs page. If D ships, decide out loud whether the Runs page pipeline strip stays as-is or becomes this; two drawings of one run is how they drift.
  • Strength: it is the only option with room for the actual objection, in the reviewer's own words, without a click.

The pairing worth considering

  • A on the collapsed card and tile, D in the detail pane. A reuses a vocabulary operators already read fluently and costs the smallest summary widening; D uses the axis the detail pane actually has. Neither duplicates the other, and the four session drawings each get the version that fits them.
  • Take C's one derivation regardless of which shape wins. "The same member has failed N rounds running" is the signal that a repair loop is burning tokens without converging, and it is currently invisible on every surface. It is a sentence, computable in workflows/store.ts, and it can sit in A's .wf-line slot without any of C's second rail.
  • Do not tint a degraded stage green in any of them. The shipped built-in records unconfigured checks as skipped-and-passed. Whatever ships has to keep saying so.
