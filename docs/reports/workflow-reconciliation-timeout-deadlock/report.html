Mission Control · workflow runs · 11 September 2026

The run was not stuck on the repository. It was stuck on a 45 second timeout that nothing could outlast.

Run 52de186f (No-Mistakes Review v15) blocked in evidence_reconciliation_error: the Haiku call that maps the session's coverage claims onto the workflow's acceptance criteria timed out at exactly 45 seconds on four consecutive attempts, so capture never finished and no reviewer ever started. Every action the page offered landed back in that same blocked phase, and each failed in a different way: one was refused before it captured anything, one spent the run's only repair round and could not even reach the provider because it inherited an exhausted attempt budget, and only the third actually called again, straight into the same cap. That is why clicking changed nothing. The red line about the repository was a stale client-side message from a click 31 minutes earlier and had nothing to do with the block. With the cap lifted, the same payload returned a complete mapping in 88.5 seconds.

Read this as a post mortem, not a live incident. That run is over: it was cancelled at 00:15:59Z, after this investigation and after its last failed attempt. Its workflow_runs row now reads status: cancelled, with both updated_at and completed_at at 2026-09-12T00:15:59.272Z, and the event log closes on run_cancelled at that instant. Nothing below is an action to take on it, and none of its recovery buttons exist any more. The findings are about the code path, which is unchanged and will do the same thing to the next run that reaches it.

What actually blocks the run

The run's stages all read “Not started” because the graph never began. The failure is in capture, upstream of Stage 1.

Before a submission can be reviewed, capture compacts the session's context into canonical acceptance criteria, then reconciles them: an LLM call that matches each coverage claim the session registered against each canonical criterion. This run had 13 coverage claims against 7 canonical criteria, a 5,462 character prompt. Reconciliation ran on claude-haiku-4-5 and returned nothing within the cap, twice, and reconcileWorkflowCoverage allows exactly two attempts (src/server/workflows/context.ts:568).

With reconciliation incomplete and readiness reporting missing_coverage, capture marks the submission failed and blocks the run (src/server/workflows/manager.ts:6834):

  "Workflow criterion reconciliation failed: Error: Claude Agent SDK one-shot timed out"}

Why the message on screen is about something else

The red line in the screenshot

“The repository has not changed since round 1; confirm an unchanged resubmission to review it anyway” is the rejected response body from the 23:36:53 click, not a description of the run's state. The run's phase at the time of the screenshot was evidence_reconciliation_error, and round 1 in that sentence only ever made sense before round 2 existed.

It persisted for 31 minutes because two independent error slots are drawn through one paragraph (src/web/workflows/WorkflowRuns.tsx:5071): 

{(error || actionController.error) && (
  <p className="wf-run-error" role="alert">{error ?? actionController.error}</p>
)}

error is the page's own slot. actionController.error is held by the shared run action store, which clears a held error only when it dispatches another action (src/web/workflows/run-action-store.ts:52). The refused resubmission arrived through the store. The override that answered it does not go through the store, because it replays a request id derived from the refused submission that a fresh dispatch cannot mint, so it posts on its own and cleared only the page slot. A server-pushed state change clears neither. The refusal therefore outlived the move that answered it, and then outlived the round that went on to block for an unrelated reason, sitting above the header as the most prominent thing on the page.

The shape of the dead end

The loop is deterministic, not flaky, and it is closed at three different points rather than one. The repository probe refuses a fresh round outright while nothing has been committed. A round that is forced through anyway cannot retry, because the prompt is a pure function of the criteria and the claims, both frozen in the submission, so its fingerprint is unchanged and the exhausted attempt count comes with it. That leaves the recovery segment as the only move that reaches the provider at all, and it re-sends the same bytes to the same model under the same cap and gets the same answer. No route out is left, which is the property that makes this a dead end rather than a slow retry.

Where the time actually goes: not the input

The obvious reading of the table above is that this run sends too much context for the model to chew through. That reading is wrong, and three timed calls through the identical runner, job id and schema say so.

The number that matters

5,462 characters is a trivial prompt. A 130 character prompt through the same path still costs 5.2 s, so roughly 5 s is fixed overhead that the input does not move. Subtract that floor and the remaining time tracks output almost exactly linearly: 304 characters cost about 26 s and 716 characters cost about 57 s, both near 80 ms per output character. That is a generation rate of roughly 12 characters per second, on the order of 3 tokens per second, which is one to two orders of magnitude slower than this model should generate.

So the block was never about sending a lot of data. It happened because this call path emits its answer extremely slowly, and a reconciliation with 13 claims to map simply has more to emit. Input size is a proxy for output size here, not the cause.

What this diagnosis recommends

Nothing here is applied

This turn is diagnosis and handoff, so no fix ships with it. Each change below was written, measured, and then reverted, so the working tree carries no source change at all. The measurements are kept because they are what identifies the cause; the patch is kept out of the repository and can be reapplied by the task that owns the fix.

1. The real defect: the generation rate, not the timeout

Roughly 80 ms per output character, about 12 characters per second, is the finding to act on. At that rate any reconciliation with more than a handful of claims exceeds any cap that is reasonable to put on a capture step, so raising the cap buys time without removing the problem. What has not been established is where that time goes inside the Claude Agent SDK one-shot path, and that is the investigation this report recommends first. A fixed overhead near 5 s per call is separately worth knowing about, since capture makes two of these calls in sequence.

2. The mitigation, measured but not applied

Compaction summarises one packet and its cost barely moves with the work under review. Reconciliation is an N×M semantic match whose output grows with both the claims and the criteria. Sharing one constant is what turns slow into unreviewable, so giving reconciliation its own budget, WORKFLOW_RECONCILIATION_TIMEOUT_MS beside WORKFLOW_CONTEXT_TIMEOUT_MS in src/server/workflows/context.ts, lets this run finish. Measured at 180 s: the same payload that timed out four times returns a complete mapping on the first attempt. It is a mitigation, and it should not be mistaken for the fix.

3. A separate, unrelated UI defect found on the way

The refusal alert outliving the move that answered it is its own bug and has nothing to do with the timeout. The unchanged resubmission is the one route that answers a refusal without dispatching through the shared run action store (src/web/workflows/WorkflowRuns.tsx), so the store's held error survives it; the store clears a held error only on its next dispatch (src/web/workflows/run-action-store.ts:52). Exporting a clear and calling it from that route fixes it.

What the prototype measured before it was reverted

  • A unit case reading timeoutMs off the calls themselves pinned compaction at 45 s against reconciliation's 180 s. 19 tests passed across the two files. With the prototype reverted those files are back to 17 passing tests.
  • A browser spec drove refusal then override in one page life and asserted the alert was gone once the round opened. It failed with the clear removed (toHaveCount expected 0, received 1, across 44 resolutions) and passed with it, so it is a real regression test rather than a passing decoration.
  • The stuck run's own payload reconciled in 88,477 ms on the first attempt under a 180 s budget, against two 45 s timeouts under the shipped cap.
  • typecheck, lint, build and smoke passed with the prototype applied, and typecheck, build and the two unit files pass again now that it is reverted.

What this means for the run in the screenshot

That run is closed and has no recovery path. It was cancelled at 00:15:59Z, after the investigation, and is now terminal: workflow_runs.status is cancelled and completed_at is set to 2026-09-12T00:15:59.272Z. A cancelled run offers no actions at all. “Retry criterion mapping”, the resubmissions and the repair budget it had left are gone with it. Do not go looking for a button on it.

What was true up to the cancellation, and is the answer to the question asked, is that while it was open no action on that page could clear it. Its four timed-out reconciliation calls were split across the initial round and one recovery segment; the single repair round it spent in between made no call at all, because an identical prompt fingerprint carried the exhausted attempt budget forward with it. It ended with 4 of its 5 repair rounds unspent and no way to use them.

The code path is what carries forward. It is unchanged, so the next submission with a comparable number of coverage claims blocks the same way. On a future run in that state, and only once a build carrying a larger reconciliation budget is actually running, “Retry criterion mapping” is the cheap move, since it reconciles without opening a repair round.

What this did not establish

  • Where the slow generation comes from. The rate is now measured, about 12 output characters per second over a fixed overhead near 5 s, but nothing here explains it. Whether it is the Agent SDK one-shot wrapper, the structured-output schema, the provider, or something in between was not traced, and no comparison against a plain API call was run. That trace is the recommended next step, and until it exists the 180 s budget is a number chosen to clear the observed worst case rather than one derived from an understood cost.
  • Where the run-state claims come from. The cancellation, its timestamp and the completed_at value are read from the complete workflow_runs row, which is printed column by column in the state-snapshot artifact registered with this report rather than summarised from a selected few. The snapshot is a single read taken while writing this; if the run is touched again afterwards, that row is what moves.
  • Whether the rate is constant or was a bad window. The three scaling calls and the reproductions all ran inside one evening on one machine. A slow provider window would produce the same shape. Re-measuring the floor on another day would separate the two, and was not done.
  • Whether 180 s is enough for every payload. Three timing samples on one prompt (69.0 s, 88.5 s, and one run that exceeded 45 s twice). The budget scales with nothing, so a submission with substantially more claims could still exceed it. A cap derived from the packet size would remove that risk and was not attempted.
  • The five other timeouts in the window. Runs dd4ee40c, 8584d4ec, 2d2a530c and 6deb0a87 hit the same cap on smaller prompts. They are consistent with a cap that has no headroom, but each was not investigated on its own terms.
  • The exact click sequence in the browser. The server's event log fixes what was requested and when; which surface each click came from, and whether the page was reloaded in between, is not recorded. The persistence mechanism was established by reading the code and then reproducing it in a browser, not from the operator's session.
  • Why the two unmatched criteria did not match. The completed mapping leaves criteria 1 and 7 with no claim. Whether that is a genuine coverage gap in the session's work or a mapping miss was not examined.
