Console detail - reclaiming vertical space for the conversation

Today the transcript starts ~300px down the pane. Five stacked bands of chrome, each flex:none, and the transcript takes what is left. Every frame below is the same height (600px) and holds the same conversation, so the gain is the number of turns you can actually read, not a number I am asserting.

Three facts drive most of these. The working-copy path is rendered twice (PATH in row 2, WORKTREE in row 5). There is 36px of pure separator between the activity line and the first transcript line (13px gap + 12px margin + 1px border + 10px padding). And the task pill is almost entirely duplicate: dispatcher.ts:430 sets a dispatched session's name to task.title, so the pill's title is the same string as the h2 two rows above it, and the SHIP badge beside it is a constant - every automated writer defaults to ship, and the MCP create_task tool cannot produce a scout at all.

So every option below drops the SHIP badge and the duplicate task title, keeping only what the pill uniquely carried: the outcome PR link and the schedule-origin chip, both usually absent. The baseline is left exactly as it ships, as the control. Nothing here invents a new control - the rest rearrange, merge, or defer what is already there.

In scope, new: the permission-mode chip (auto⌄) moves up to lead the right-hand cluster - auto · Opus 5 · context · cost. It reads first because the posture governs the whole session, where model, context and spend are all consequences of running under it. It is not a new component - ModePicker already ships on session cards, board tiles, and in this very pane's footer (ConsoleDetail.tsx:619). This promotes it into the header cluster, where the other live per-turn facts already are. Marked with a dashed outline in every frame below; the baseline keeps it in the footer, where it is today.

Two corrections to the earlier drafts came out of this. The cost chip ships in the header today (ConsoleDetail.tsx:404) and I had not drawn it. And I had not drawn the footer at all, so every conversation number before this was ~40px too generous. Both are now in all seven frames, which is why the pixel counts here are lower than the ones I quoted earlier - the ranking is unchanged.

Live status - a placement study

The band holding Let me attach secondary repositories… and running Bash is two different things wearing one costume, which is why no option above placed it well. The objective (session.goal.text) is a refined, durable statement of what the session is for - it changes rarely, and it is denormalized onto cards precisely because a card has no transcript. The activity (session.activity, "free-form one-liner from the last hook") is per-turn and changes constantly. One is an anchor, the other is a heartbeat. Stacking them in a fixed block 36px above the transcript serves neither: the durable thing takes prime space it does not need, and the live thing sits as far as possible from where new content actually appears.

C is the one to take, and it keeps both halves. A live signal belongs next to live content, so the heartbeat becomes the tail of the log and costs nothing - it occupies space the transcript was already going to use and disappears the moment the real turn lands. The objective is the opposite kind of fact, so it joins the identity block under the title, where the other durable facts already are. That costs about 18px of head-row height and retires an 86px band: roughly 68px net, with nothing hidden and nothing behind a hover.

An earlier draft of C sent the objective to the title's tooltip instead, which is where this note previously said "the objective stops being visible." That was over-applying one idea to two different problems - the tail-of-log insight is about the heartbeat, and it says nothing about where a durable objective should live. B remains the fallback if you would rather not add any height to the head row at all: it folds the heartbeat into the working badge for free and keeps the objective on its own line.
