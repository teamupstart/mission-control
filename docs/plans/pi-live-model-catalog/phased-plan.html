Why two phases

The server work owns a security-sensitive JSONL subprocess, validation bounds, concurrency, caching, and a new aggregate route. The browser work owns a broad React source-of-truth cutover, long-list presentation, fallback UX, and Playwright infrastructure. Combining them would be difficult to verify in one implementation session.

Phase 1 is independently testable while the UI remains entirely static. Phase 2 then changes every visible consumer atomically. Splitting Phase 2 again would leave different pickers showing different catalogs for the same stored id.

Findings that changed the proposed route

  • The browser needs every harness catalog at once, so the plan uses aggregate GET /api/harnesses/models rather than a per-agent route family.
  • The daemon cannot know every current off-catalog value. Each browser consumer retains its own current value, matching today's safety behavior.
  • The source investigation missed ModelField. Foreman's Pi backlog-default picker is a dispatch-time consumer and joins the atomic Phase 2 cutover.
  • The browser architecture forbids polling. The root provider fetches once; Retry reuses the same bounded route explicitly.
  • The current e2e Pi stub must become an RPC-only fake that still refuses every model launch.

Cross-phase contracts

  • One harness owner: every server harness declares model behavior; generic layers never start Pi by id check.
  • Safe wire: validated ids and bounded presentation metadata only; no auth, cost, raw objects, stdout, or stderr.
  • No model work: no session, prompt, tools, or project-local resources during discovery.
  • Deterministic cache: one in-flight probe; stale successful data before shipped fallback; memory only.
  • Aggregate API: one exhaustive catalog per AgentType; no SSE model event.
  • Existing writes: catalog quality never changes model persistence or launch validation.
  • One browser source: every old UI helper call moves in one phase.
  • Complete mirroring: all safe Pi rows, grouped in first-seen provider order.
  • Retained selection: discovery absence is not revocation.
  • Usable degradation: loading, failure, and retry never disable a writable picker.
  • Zero-token tests: fake Pi accepts only catalog RPC and refuses agent launches.

Verification bar

Both phases run focused tests, typecheck, lint, the full unit suite, build, and smoke. Phase 2 also runs focused and full Playwright gates. The final e2e path proves a fake-only model appears under its provider, persists as the exact id, remains visible across reload, and survives a fresh-daemon discovery failure without any real provider call.

Non-goals

No dynamic Claude or Codex discovery, SQLite catalog persistence, per-model effort redesign, human table parsing, browser polling, model prompt, or selected-model storage change.
