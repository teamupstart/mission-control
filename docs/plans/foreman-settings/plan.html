Plan: Foreman settings - repo picker + move Tier

A repository picker for the live allowlist, and Tier moved off the topbar popover into the settings panel.

Decided · picker = known repos + manual add · popover = summary + link

Why

Two problems with today's ForemanBar popover:

  1. The allowlist is a paste-a-path textarea. To make Foreman live in a repo you type or paste its full realpath, one per line (ForemanBar.tsx:217-240). It only appears in Live mode, it's easy to typo, and there's no help picking a valid repo root - even though the dashboard already knows every session's repo.
  2. The popover is overloaded. Enable, Mode, Auto-approve, Tier, Work queues, On-drain, and the allowlist all stack in one dropdown. Tier (the cheap-tier posture) is a configure-once policy, not a thing you flip in the moment.

Now that settings live in navigable categories, Foreman gets a category, and the durable configuration moves there.

Adding/removing is the existing update({ repoAllowlist: [...] }) call - the daemon and persistence are unchanged; only the input changes from free text to a picked value. Candidates are the repo roots the fleet already knows (SessionRow.repoRoot, types.ts:121 - the same value the server gates live sends on), deduped and minus what's already listed.

Decision 1 - where the picker's candidates come from

A. Live-session repos + manual addRecommended

Candidates are the distinct repoRoots across current sessions (derived on the client from data the dashboard already holds), plus a text field to add a repo with no active session, validated server-side so a typo can't enter a non-repo path. Covers the common case with zero new data and still lets you add a cold repo deliberately.

B. Live-session repos only

The same client-derived list, no manual field. Simplest, no backend at all - but a repo with no session on the grid right now can't be added, so you're stuck configuring a repo before its first session.

C. Filesystem directory browser

A new daemon endpoint lists directories so you can navigate and pick any folder, validated as a git root. Most flexible, most surface: a browsing API, its own UI, and path-traversal care - heaviest for a list that is usually 1-3 entries.

Decision 2 - what the popover says about the allowlist after the move

A. Read-only summary + linkRecommended

In Live mode the popover shows "Live in N repos - manage in Settings," so it still answers "is this repo covered?" at a glance without being an editor.

B. Nothing

Drop every mention; the allowlist lives only in Settings. Cleanest popover, but you lose the at-a-glance "am I actually live here" that Live mode wants.

Implementation sketch

  • ForemanSettingsPanel.tsx (new) - the Foreman category: the Tier radios (moved verbatim), then the allowlist manager (list + picker). Takes a ForemanState, like SkillsPanel takes SkillsState.
  • SettingsModal.tsx - add a foreman entry to SETTINGS_CATEGORIES + a case; lift useForeman into the modal (as useSkills already is); pass the app's sessions for candidate repos.
  • ForemanBar.tsx - remove the Tier fieldset and allowlist textarea; add the Live-mode summary per Decision 2.
  • Server - only for option A/C: a small validated "resolve path to repo root" endpoint reusing the existing resolveRepoRoot / realpathSync logic dispatch already uses (routes.ts:982-989). No schema or persistence change - repoAllowlist is already an array of strings.

Sequencing

This builds on the two-pane settings panel (mancej/settings-sidebar), still in validation. Implement on a follow-up branch based on that work once it settles, so the in-flight run isn't disturbed.

Out of scope

  • Any change to how repoAllowlist persists or how the server gates live sends.
  • Moving Enable / Mode / Work queues / On-drain (they stay in the popover, by request).
  • Auto-approve access and the Tier model id (triageModel) - unchanged.
