Feature plan · backlog scheduling

Explain the trust hold on the task itself.

The scheduler already knows why these tasks will not move. This plan carries that exact repository-trust reason to every place the queued task is read.

Outcome: a persistent amber warning names the missing repository grant, preserves manual launch, and routes the operator to the existing Trust matrix.

Existing seams

  • backlog-machine.ts refuses the queue through taskReposAllowlisted before capacity.
  • allowlist.ts owns the path and multi-repo rules, but exposes only a boolean today.
  • App.tsx already holds tasks, Foreman config, worker status, and the allowlist.
  • DeadBlockerButton supplies the existing shared task-alert interaction.
  • openSettingsAnchor("trust", "trust/matrix") already owns the remedy route.

No database migration, new endpoint, wire field, or automatic trust grant is required.

When the warning speaks

The task-level projection requires loaded state, a running live Foreman, armed autopilot, an enabled error-free backlog-compatible task, and at least one repository outside the allowlist.

One quiet alarm

Amber means operator action; danger remains reserved for stopped work. The closed state stays icon-sized so a phased backlog does not become a wall of repeated copy. The opened dialog names the repository, says manual launch still works, and offers one route to the Trust matrix.

Manage trust
  • Reuse the existing outlined warning triangle and popover interaction.
  • Use existing attention, panel, border, text, shadow, and focus tokens.
  • Do not use role="alert" for persistent multi-row state.
  • Keep Trust as the only place that edits and confirms repository grants.

Data and request flow

Existing server projections meet in App. A pure browser helper then feeds the same shared control to all three task surfaces. Only the remedy navigates.

Implementation map

  1. Name the gap once. Add a missing-task-repositories helper to src/shared/allowlist.ts and define taskReposAllowlisted from it.
  2. Project the UI state once. Add backlogTrustHold and singular/plural copy helpers to src/web/lib/backlog-copy.ts.
  3. Build one shared control. Add BacklogTrustAlert beside DeadBlockerButton and share popover geometry with an amber modifier.
  4. Wire all three surfaces. Thread one nullable view from App through Board, Backlog drawer, and Sitrep, with one Trust deep-link callback.
  5. Document the contract. Update README.md, docs/dispatch-and-backlog.md, docs/ui.md, and aligned Foreman copy if needed.

Acceptance criteria

  • All four enabled, error-free calendar-buddy phases show the warning, including dependency-blocked phases.
  • The dialog names calendar-buddy, preserves manual launch, and routes to Trust.
  • Granting Foreman access removes every affected warning after normal refresh.
  • Multi-repo tasks name only missing grants and require all repositories.
  • Parked and launch-error tasks keep one existing explanation, not two alarms.
  • No new persistence, endpoint, alert-center event, desktop notification, scheduler rule, or automatic grant exists.

Out of scope

  • Changing scheduler precedence or allowlist policy.
  • Granting trust directly from a task card.
  • A queue-wide banner instead of task-local warnings.
  • Desktop, sound, toast, or Away-digest notifications for this persistent condition.
  • A general server-side reason protocol for every possible backlog hold.
