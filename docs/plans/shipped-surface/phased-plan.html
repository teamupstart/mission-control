Shipped surface - phased implementation plan

Implementation index for the approved Shipped-surface plan (source of truth: plan.md). Each phase links its detailed implementation file.

Source plan and incorporated decisions

  • Surface: Drawer + ship log (A then B). Clicking Shipped opens a Shipped drawer in The Line; the drawer escalates to a new cross-repo Ship log page.
  • Data: store PR titles on the adoption ledger. Per-PR cost approximation and the embedded merge matrix were not adopted.
  • Follow-up: this phased plan.

Investigated findings

Discrepancies between the source plan and the repository, resolved as explicit decisions:

  1. No title exists at adoption time. The adoption signal carries only the PR URL and session context, and the hook-ingest path is guarded against anything slow or fallible. The Inspector's per-tick poll already fetches PrSnapshot.title. Decision: the observer patch writes the title at zero extra network cost; it is null until the first poll, and every renderer falls back to the branch name.
  2. The drawer frame has no footer. All three existing drawers escalate via the header actions slot. Decision: "Ship log →" lives there.
  3. The existing PR read is wrong for this surface (50 rows by review recency). Decision: Phase 1 adds an adoptedSince parameter on the same route - an adoption-ordered, uncapped window - rather than a second route over the same rows.
  4. The click target flips once, not twice. The flip invalidates a pinned test and a committed e2e evidence transcript. Decision: Phase 2 ships the page without touching the stage click; Phase 3 performs the single flip.
  5. e2e seeding for adoption exists, indirectly: the production adoption signal is POST /hooks/:event with prCreated/prUrl, which specs can drive; title-specific rendering is asserted with route fulfillment.

Dependency graph and concurrency

Phase 1 (server + shared foundation)
   |
Phase 2 (Ship log page; stage click unchanged)
   |
Phase 3 (Shipped drawer; the one click flip; escalates to Phase 2's page)

The graph is a chain; there are no concurrent phases. Phase 3's dependency on Phase 1 is transitive through Phase 2. Merge order: 1, then 2, then 3. Every phase leaves the repository valid and testable: after 1, the ledger carries titles nothing yet renders; after 2, the Ship log exists at #/shipped while the Shipped click still routes to completed runs; after 3, the approved behavior is complete.

Cross-phase contracts

Fixed by Phase 1, consumed by 2 and 3:

  • InspectorPr.title: string | null; null means "not yet polled since the column existed"; renderers fall back to headRefName.
  • GET /api/inspector/prs?adoptedSince=<epoch ms> returns InspectorInspection[] filtered adopted_at >= since, ordered adopted_at DESC, uncapped; parameterless behavior unchanged.

Fixed by Phase 2, consumed by 3:

  • MissionRoute member { page: "shipped" }, hash #/shipped.
  • The page's h2 heading "Ship log".
  • The PR-standing helpers' shared location (merged / open / gone mapping), lifted out of the settings panel.

Phase 3 consumes both sets and changes neither.

Final verification strategy

Per phase: npm run typecheck, npm run lint, npm test, plus npm run build && npm run smoke where build or runtime surfaces change, and npm run test:e2e with specs for every UI-visible change (phases 2 and 3). Phase 3 additionally regenerates the Line evidence transcripts. After Phase 3 merges: Shipped click opens the drawer, the drawer escalates to #/shipped, titles render with branch fallback, and no surface still routes Shipped to workflow runs.
