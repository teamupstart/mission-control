Native Conductor onboarding

Two merges to a permanent front door.

First make installed Conductor engines native to Settings and repository setup. Then add the broader trust boundary: launching an upstream interactive installer from a verified local main checkout.

Approved outcome

Conductor is always discoverable. An installed engine gains a native Register and observe path. A missing engine gains a guided, visible installer terminal from a verified checkout. Runs and Dispatch remain gated by active observation of the exact repository.

Ownership stays intact. Mission Control invokes provider CLIs and terminal launchers, but never writes Conductor-owned files, accepts browser-authored commands, or downloads executable source silently.

Incorporated human decisions

  1. Guided terminal installation. Use a verified local ai-conductor main checkout and fall back to instructions when none exists.
  2. Register and observe. Register first, save Mission Control consent second, and expose recoverable partial success.
  3. Phased delivery. Publish these artifacts, schedule dependency-linked tasks, and release them through the merged planning pull request.

Investigated findings

  • The Settings availability abstraction exists solely to hide Conductor and crosses the rail, deep-link fallback, keyboard walk, palette, and tests.
  • SettingsStatus.pipelines.present must remain wire-compatible, but its slow row-visibility cadence can disappear. pipelines.observing remains the Runs gate.
  • The missing repository inventory already exists in /api/repos, and resolveRepoRoot() is the canonical main-root authority.
  • useConductor already serializes whole-config writes and rejects stale polls.
  • PipelineProvider already owns CLI composition and output validation.
  • conduct-ts register is a bounded, noninteractive sanctioned mutation. The upstream installer is interactive and may change several user-level locations and global tools.
  • The terminal target registry, launcher, and disposable E2E Conductor fake are reusable seams.

Sizing and phase count

Estimated non-test production change: 700 to 1,050 lines. Roughly 300 to 450 lines cover discovery, registration, hook orchestration, candidate merging, and base commissioning UI; 250 to 400 cover verified installer discovery and terminal launch; 150 to 200 cover styles and documentation-facing support.

Two phases are the fewest safe units. Combining them would mix a bounded provider registry command with an interactive installer that can mutate user configuration and global packages. A third phase would create a dead API or inert UI: Settings, registration, consent, Dispatch, documentation, and tests are one vertical slice.

Final verification strategy

Each phase runs focused tests, typecheck, lint, build, and its Conductor Playwright spec. Phase 2 closes with the full unit suite, smoke suite, and full E2E suite.

  • Conductor visible with no engine.
  • Copyable fallback with no eligible checkout.
  • Verified checkout confirmation and faked terminal launch.
  • Installed engine with an unregistered workspace repository.
  • Register and observe success plus exact-repo Pipeline dispatch.
  • Provider-registered but observation-failed recovery.
  • Wide, narrow, keyboard, and non-color status evidence.

Final cross-phase audit

  • Every source requirement is owned once: Phase 1 owns registration and consent; Phase 2 owns installer trust and launch.
  • Phase 2 consumes Phase 1's provider-neutral setup seam without replacing it.
  • No unsafe concurrency is claimed; the direct edge matches shared files and contracts.
  • Both merges leave an operable repository. Phase 1's instructions fallback is complete on its own.
  • The final state implements all approved decisions with no cleanup phase.
