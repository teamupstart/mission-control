Context menus

Right-click gives you the actions that belong to the thing under the cursor. A link offers Copy and Copy URL; a file path offers Copy path and Copy absolute path; a message offers Copy message and Quote in reply.

Every menu on this page is live. Right-click the transcript, the session card and the diff below and the real proposed menu opens with the real proposed items, resolved from what you actually clicked. Choosing an item really writes your clipboard and shows you what it wrote.

The transcript is drawn with the shipping .turn / .turn-text / .tool-chip CSS lifted verbatim from src/web/styles.css. The written proposal is plan.md beside this file.

What right-click does today

The two builds do not agree, and the packaged one does nothing

There is no onContextMenu handler anywhere in src/. In a browser that is survivable, because Chromium's own menu carries Copy and Copy Link Address. In the desktop app it is not: Electron ships no default context menu, and an app that does not build one has none. src/main/menu.ts installs an application menu and src/main/tray.ts a tray menu; neither is a webContents context menu. So the build the product is packaged and shipped as has no right-click Copy, no Paste, and no Copy Link Address anywhere.

Two rules, and the menu falls out of them

Which is why there is no per-component right-click code

Actions stack by specificity. A link inside a message inside a card is three targets at once, so the menu resolves the hit into a target chain and concatenates each target’s actions, most specific first. That is exactly the request - a URL offering both Copy and Copy URL - generalized, so it never has to be special-cased per element. The chain is capped at two tiers: the thing under the cursor, then the container it lives in. Every menu in this document is six items or fewer because of that cap.

The label names its payload. A bare Copy that copies something the reader did not choose is worse than no item at all. So Copy appears only when there is a real selection to copy; with no selection the item is named for what it will write - Copy message, Copy code, Copy branch. Nobody has to paste to find out what they got.

One consequence worth naming, because it looks like a bug otherwise: identical payloads collapse. A bare autolinked URL has link text equal to its href, so Copy and Copy URL would write the same string, and the duplicate is dropped. On a markdown link reading “the failing job” both survive, because both are real choices. That is one general dedupe rule the stacking already needed, not a special case. You can see both behaviours in the next section: right-click the bare URL, then the worded link.

Also in the registry, not drawn: Shift+F10 and the Menu key open the same menu at the focused element. Both are unbound today (src/web/lib/keybindings.ts), and without them the whole feature is mouse-only.

    Four behaviours to exercise, in this order:
    1. Select a phrase, then right-click inside it - the first item is Copy, hinted selection, and Quote in reply quotes exactly what you selected.
    2. With that selection still live, right-click outside it - the selection clears and the menu falls back to Copy message, because a Copy offered there would copy something you did not choose. This is what every browser already does, and it is what makes rule 2 honest.
    3. Select across two turns - Copy gives you the raw text, and Quote in reply attributes each speaker, because a quote that silently merges two voices into one is a quote that misleads.
    4. Flip to Terminal and repeat 1-3. Same menu, different markup.
    Right-click the composer too - it is inside the live region. A field's selection is its own: window.getSelection() is empty inside a <textarea>, which is the same two-kinds-of-selection distinction chordYieldsToSelection already documents in src/web/lib/keybindings.ts. So the field reads selectionStart/selectionEnd instead, and captures them before the menu takes focus.

    And this is where a DOM menu is genuinely worse than an OS one. Paste needs navigator.clipboard.readText(), which requires the clipboard-read permission - already granted in the Electron renderer, but prompted on first use in a browser tab. Try it here and you will most likely get the honest fallback rather than a paste. It is the single strongest argument for the native-menu option in section 7, and it is worth exactly one item: ⌘V works regardless, and every other item on this page is unaffected.

    Row density · A or B

    The same menu, drawn in each of the app’s two popover vocabularies

    The app already speaks two popover dialects. .wf-pipeline-item-menu-pop is terse, label-only rows at 176px. .open-in-pop is a label plus a one-line blurb at 268px, because “Open in” is a thing you do rarely and may not know the targets of. A context menu is the opposite kind of surface: you open it constantly and you already know what Copy does.

    A · dense recommended

    B · blurbs

    Measured in this page: the same five rows are 147×196 in A and 250×258 in B - B is 70% taller. At a cursor that decides how often the menu has to flip above the pointer near the bottom of a window, which is the one placement move a reader actually notices. A keeps the payload visible where it is genuinely ambiguous - the selection hint on the right of row one - without paying for a blurb on Copy URL, which nobody has ever needed explained.

    Does this replace the browser’s own menu?

    The one decision with a real cost either way

    In the desktop build there is nothing to replace, so the answer is free. In a browser, taking over right-click costs the reader View Source, Save Image As, and Inspect - and this product’s users are developers running it on localhost, which is exactly the audience that uses them.

    a

    Custom everywhere, Shift+right-click falls throughrecommended

    One menu in both builds, one implementation, and the Firefox convention keeps the native menu one modifier away. This page behaves this way - try Shift+right-click on the transcript above and you get your browser’s menu instead.

    b

    Custom in Electron only

    Closes the hole where it is worst and touches nothing in the browser. The cost is that the two builds diverge in behaviour, and the browser - which is where npm run dev and every e2e spec live - never gets Quote in reply or Copy message at all.

    c

    Custom everywhere, no escape hatch

    Simplest to describe and to test. Takes Inspect away from a local developer tool on the surface those developers most want to inspect.

    A separate question, same section. Electron can build a real OS menu in the main process (Menu.buildFromTemplate over IPC, the way src/main/tray.ts already does). It would look native and get spellcheck for free. But it only exists in Electron, so the browser build needs the DOM menu regardless - choosing it means building and maintaining both, and the OS menu cannot render the app’s own tokens or reach React state for Quote in reply without another round trip. Recommended: one DOM menu for both builds. The flow diagram for this is in plan.html.
    8

    Recommendation

    What to build, and what to sweep up on the way

    Build the registry and the DOM menu, option A above, dense rows, and scope v1 to the transcript, the composer, and the session card / tile / rail row. That covers the ask, the two actions worth the whole feature (Quote in reply and Copy message), and the triage-board copying the codebase has already written a comment wishing for. Diff and Files are one registry entry each afterwards, with no new plumbing.

    Three fixes come along because this work touches the same code and leaving them is not defensible: PersonaEditor.tsx:396 and ReportPanel.tsx:250 call navigator.clipboard.writeText directly instead of src/web/lib/clipboard.ts, whose entire reason for existing is the Electron renderer’s execCommand fallback - so both are quietly unreliable in the desktop build, the one this plan is about. And FileWorkspace.tsx:466 (“Copy local”) gives no feedback at all. One useCopyFeedback() hook over copyText() replaces seven hand-rolled 1600ms label flips and fixes all three.

    Two constraints go in on the first commit rather than after the bug report. The menu class joins the .is-desktop no-drag allow-list at styles.css:1438-1470, whose own comment notes that every entry was added after it broke - and a menu that opens at a cursor can land under the titlebar on the very first try. And it picks one of the two documented Escape contracts: join Overlay.tsx’s topmost-wins registry, or take keys in the capture phase with stopImmediatePropagation the way OpenInMenu.tsx:86-99 explains it must.
