Approved phased implementation

Pi-managed Amazon Bedrock models

Two sequential phases: first ship a directly usable Pi SDK runtime for configured Bedrock models, then add project trust, structured extension questions, and Work Queue automation on top of its proven lifecycle events.

Why this split

Phase 1 is independently useful: an operator can choose a Pi-discovered amazon-bedrock/* model and run a durable managed session with direct controls. Phase 2 adds blocking UI and unattended queue behavior, which depends on Phase 1's exact session, activity, and turn-completion invariants.

One phase would combine provider/auth/session integration, event normalization, dialog correlation, and queue concurrency into an oversized review. More than two phases would create transport stubs or test/documentation-only merges.

Dependency graph

Concurrency: none between implementation phases. Phase 2 directly depends on Phase 1. Both tasks also depend on this planning session and remain disabled until the planning pull request merges.

Cross-phase contracts

  • Bedrock remains a Pi provider and the complete model id stays opaque to Mission Control.
  • Pi's normal agent directory owns authentication. Mission Control never accepts or persists AWS credentials.
  • The pinned Pi package is lazy-loaded behind an injected dependency boundary.
  • The existing SDK supervisor owns lifecycle and final removal still uses Registry.beginEviction.
  • Missing Pi session state is an explicit restore failure, never a new look-alike conversation.
  • Mission MCP requirements remain a hard Pi launch refusal. Permission modes and multi-repository support remain null.
  • Tests use isolated fakes only. Real Pi and Bedrock access is optional manual evidence.

Final audit

  • Complete: every approved source requirement belongs to exactly one phase.
  • Mergeable: Phase 1 is directly useful before Phase 2 exists.
  • Sequential: Phase 2 consumes and does not redefine Phase 1 lifecycle events.
  • Compatible: terminal Pi remains; no AWS credential/model schema is introduced; Claude and Codex stay on shared contracts.
  • Bounded: Bifrost, direct AWS calls, Pi MCP, permission modes, multi-repository support, and arbitrary Pi TUI presentation are excluded.
  • No cleanup tail: each phase owns its tests and documentation.
