Product behavior report

Inspector completion policy

Question: What does the Inspector completion policy do, specifically, and how can a user apply it to a custom workflow?

Answer: It is a workflow-wide, post-End approval stage. After the workflow graph succeeds, Mission Control waits for GitHub Inspector to review the exact pull request commit submitted by that run. A clean review completes the run; findings follow the workflow's configured repair policy and may keep the run waiting or blocked. A custom-workflow author can enable it under Properties → Workflow settings → Final gate → GitHub Inspector approval. It is not a node in the graph. The author must then publish the draft and bind that new immutable version for the setting to take effect.

How a user turns it on

1

Open an editable workflow

Create a custom workflow, or select Duplicate on a built-in. Built-ins are intentionally read-only, including their settings.

2

Open Properties

In the right rail, find Workflow settings. On a narrow viewport, first use the Properties drawer button.

3

Choose the final gate

Set Final gate to GitHub Inspector approval, then choose what happens after findings and when a pull request is missing.

4

Publish and bind

Publish the saved draft. Bind a session to that newly published version, or replace its existing binding. An older binding remains pinned to its older policy.

Why it feels absent: when the final gate is None there is no Inspector item on the canvas. When enabled, Pipeline view adds a fixed Inspector footer after End, but that footer is a visual projection of the policy, not an editable stage.

What happens at runtime

The stage does not accept a PR URL as proof by itself. GitHub Inspector must already have adopted the PR from Mission Control observing gh pr create. Gate entry captures the submission's committed local HEAD, waits for a fresh Inspector observation, and verifies that the PR is still open and the remote head matches. A closed PR, switched PR, mismatched head, disabled Inspector, contradictory observation, or unresolved finding can keep this separately configured approval stage waiting or blocked. That behavior belongs to the Inspector completion gate, not to the earlier Pull Request action.

Why a custom-workflow author may not find it

It is not in the node palette

The policy applies to the entire workflow after End, so it is only in the Properties rail. It cannot be dragged, connected, or deleted like a node.

The selected workflow may be built-in

Built-ins display the settings but disable editing. Duplicate the workflow to obtain an editable custom draft.

The right rail may be collapsed

Below the responsive breakpoint, Properties is a closed drawer until the user opens it.

The draft may not be the bound version

Saving changes only updates the draft. Publish creates an immutable version, and the session must be bound to that version.

The current No-Mistakes version does not use it

No-Mistakes Review version 16 sets its completion policy to None. Version 8 retains the older Inspector gate, while versions 9 onward do not. Looking at the current built-in therefore shows no fixed Inspector footer.

What this policy does not do

Not CI tracking

It consumes GitHub Inspector's review ledger. Check runs and CI completion are separate workflow concerns.

Not PR merge

Passing the gate completes the workflow run. It neither merges nor authorizes Shipping.

Not Inspector setup

The workflow policy does not enable or configure GitHub Inspector. If Inspector is disabled, the gate blocks.

What was not established

This report traces the current source, schema, runtime manager, tests, and product documentation. It did not launch the dashboard to reproduce the authoring path visually, and it does not assess whether the existing labels or layout are discoverable enough in usability testing. The source does establish that the control is available to editable custom workflows and that publication plus rebinding is required for activation.
