Resume permission loss

Why did a resumed agent lose repository permissions?

Resume rebuilds a session from its stored configuration but never replays the repository grant, so the relaunched session starts with an empty permission allowlist. Every resumed session loses repository writes at its first tool call, and the failure surfaces as a generic refusal rather than a missing grant.

Evidence

StepGrant presentSource
Initial launch yes dispatcher.ts:214
Stored config yes harness.db tasks.grants
Resume no registry.ts:412

The grant survives the write and the read. It is dropped at the point where the rebuilt session is handed to the harness, which constructs a fresh permission set from defaults instead of the stored one.

What we ruled out

  • Grant expiry - the stored record carries no TTL and the row is unchanged after resume.
  • A harness-specific bug - the same loss reproduces on claude, codex, and pi.
  • Worktree identity drift - the repository path and digest match across both launches.

Limits

Only single-repository sessions were traced. A session attaching more than one repository may lose the grants in a different order, and that path is untested here.
