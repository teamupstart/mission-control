The Line - fixing the Review drawer

The strip is the Line (LineStrip.tsx, aria-label="The Line"); the panel that expands under a stage is that stage's drawer. Rows come from ReviewDrawer.tsx.

The two complaints are one bug wearing two hats. The row's bold title is (run.sessionId && named.get(run.sessionId)) || run.noteKey (ReviewDrawer.tsx:154) - it resolves a name only from live sessions and falls back to the raw conversation GUID otherwise. And in the live database every one of the 31 blocked runs sits at phase = "session_disappeared". The session died, so the name went with it and the run stopped forever. You are seeing GUIDs because the runs are blocked.

Neither missing fact needs new plumbing. The durable title is already in workflow_bindings.session_name ("Fix Busy State for Diff Link"), and WORKFLOW_RUN_SUMMARY_SELECT already joins that table - it just selects note_key and not session_name. The reason is already on the wire as WorkflowRunSummary.phase; the drawer prints runStatusLabel(status) and drops it.

Today

the bug

Real rows from the running daemon. Four columns: who, the chip ladder, a state word, and one control. The identity is a GUID, the state is the word "Blocked" with no cause, and the only control leaves the drawer.

Option A - name it, say why, offer the one move

smallest change

Same four columns, same 58px row, same chip vocabulary. Only the content changes. Who becomes the durable binding title with the harness's colour. State becomes Blocked · <reason> from a phase → sentence map, the sibling of the GATE_WAIT_SENTENCES and ACTION_WAIT maps that already exist in run-model.ts. Ops leads with the remedy that this phase actually takes - each one is an existing route.

Cost. One column in WORKFLOW_RUN_SUMMARY_SELECT, one optional append-only field on WorkflowRunSummary, one Record<phase, sentence> with a replaceAll("_"," ") fallback (phase is a free string, not a union), and a remedy descriptor per phase next to the existing run-actions.ts. It does break the drawer's stated "no action" rule - see the note under Option C.

Option B - group by reason, act on the batch

best at 31

Option A still leaves you scrolling 31 rows that say the same sentence. When runs share a phase, fold them into one bar: the reason once, the count once, one control for all of them. The individual rows are still there behind the caret. This is the only option that scales with the number of blocked runs rather than against it.

The count in the strip changes meaning too. "32 waiting on you" becomes "1 needs you · 31 stalled", which is the difference between a fleet that owes you 31 decisions and a fleet with one decision and a pile of dead runs. Grouping is a pure client-side fold over phase - the same shape as line-summary.ts's existing folds.
Watch out for. "Dismiss all" cancels 30 runs from a strip drawer - it needs a confirm step with the count echoed, the way DELETE /api/ensembles/:id already demands a confirmId. And a group of 1 should render as a plain row, not a bar with a caret.

Option C - the row opens where it stands

keeps the "no action" rule

ReviewDrawer.tsx:19-21 states a deliberate rule: "No fetch, no run detail, and no action - everything that CHANGES a run stays on the run page." A and B both break it. This option keeps the collapsed row at exactly 58px and scannable, and lets one row expand in place to explain itself. The remedy still lives here, but it is behind an intentional second click rather than sitting on every row.

The trade. The expanded body is the only place in the drawer that would want data the summary does not carry (which reviewers were cancelled, how long ago) - that is a GET /api/workflow-runs/:id per opened row, which is the "no fetch" half of the rule. Fetching for one deliberately opened row is a much smaller concession than fetching for all 32, and the drawer's three-row cap means only one is ever open in view.

How they stack

They are layers, not rivals. A is the floor and should land regardless - a row that shows a GUID and the bare word "Blocked" is wrong at any count, and the fix is one SQL column plus one lookup map. B is what makes 31 blocked runs survivable and is a pure client-side fold on top of A. C is the escape hatch for the reasons whose remedy needs context before you can choose it - it is worth building only after A proves which phases people actually hit.

One question A forces and the others do not: the drawer's "no action" rule was written on purpose. A puts Reattach… and Dismiss on the row and breaks it. The alternative is to keep the drawer read-only and let the reason text alone do the work - honest, but it still leaves 31 rows you can only look at.
