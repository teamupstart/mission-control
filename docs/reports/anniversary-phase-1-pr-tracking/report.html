Why Phase 1 failed after its pull request opened, and what changes now

Question: Why did the workflow show “Could not run” after the pull request was successfully created, why did it miss Inspector findings, and what does the Inspector completion policy do for a custom workflow?

Finding

The pull request and CI succeeded. The old Pull Request action then compared the published tree with the tree previously reviewed by Personas. They differed, so it converted a successful publication into an action error. The web UI rendered that generic error as “Could not run.”

The action session tracked CI correctly, but no component owned the Inspector findings. It watched the PR’s exact head until verify passed and then stopped as instructed. Inspector had already stored three findings. The bound No-Mistakes v16 workflow had completionPolicy: none, while its blocked status kept Foreman’s separate review follow-up suppressed.

The Pull Request stage is now simpler. Once Mission Control durably observes the opened PR, repository, branch, ref, state, and content disagreements are warnings. The action completes, activates its downstream route, preserves the warning and observed PR, and offers the normal “Run this review again” action. A mismatch no longer blocks Inspector or later stages.

What the Inspector completion policy does

It is a workflow-wide approval stage after End, not a node that authors place in the graph. End records that the authored graph succeeded, and the run waits until GitHub Inspector has reviewed the intended adopted PR head. A clean review completes normally; findings follow the workflow's selected repair policy and can keep the run waiting or blocked. It uses the existing Inspector poller rather than starting a second GitHub watcher. See docs/workflows.md:2043-2089.

Available to authors

Where custom workflows configure it

Open the custom workflow, select Properties, then under Workflow settings set Final gate to GitHub Inspector approval. Publish a new immutable version and bind that version to the session. The controls are defined in src/web/workflows/WorkflowProperties.tsx:74-143.

Easy to miss

Why it is not visible in the graph

The gate is deliberately projected as a fixed Inspector footer after End. It does not appear in the stage palette, cannot be wired to selected branches, and is absent from run detail when the policy is none. This makes it look unavailable even though it is an author setting.

Enabling the stage reveals two author choices:

  • After findings: Restart all Personas sends a repair packet and requires a full workflow rerun; Repush and recheck GitHub Inspector only waits for a different pushed head and rechecks Inspector without rerunning Personas.
  • Missing PR: Wait, Offer Prepare PR, or Prepare PR automatically. Preparation still happens through a session handoff; the gate itself does not push or open a PR.
Important distinction. The Pull Request action completes from durable adoption and does not inspect or block on Inspector findings. If the workflow author separately enabled the Inspector completion gate, that later stage retains its own approval contract and may wait, request repair, or block.

Implemented behavior

  • The completion label is now Pull request is opened. Durable PR adoption and observed provenance remain required; agent prose or a transient URL is not enough.
  • A wrong repository, branch, pushed ref, closed or merged state, missing comparison proof, or changed content tree produces the durable warning pull_request_review_mismatch. These conditions do not block the action.
  • The completed attempt retains the PR identity and warning, emits a warning event, and seeds the complete continuation in the same transaction. See src/server/workflows/session-action-adapters.ts:331-516 and src/server/workflows/store.ts:7650-7714.
  • Run detail shows an amber PR opened with warning notice, the adopted PR link, and the observed ref. It does not call the segment “verified shipping.” See src/web/workflows/WorkflowRuns.tsx:384-466 and src/web/workflows/run-model.ts:513-530.
  • After completion, the existing Run this review again action lets the operator capture the published state in a fresh workflow run. The behavior is documented in docs/workflows.md:500-551.

What this report did not establish

  • It did not judge whether the three historical Inspector findings were correct. It established that they existed, were open, and were not delivered to the action session.
  • It did not mutate the historical blocked run or PR #1. Existing durable history remains an accurate record of the old behavior.
  • The new PR action may show Awaiting PR only until Mission Control durably adopts the creation. It no longer waits for later provider comparison metadata.
  • A custom workflow’s separately configured Inspector stage can still wait, request repair, or block according to its selected findings and missing-PR policies. This change deliberately does not weaken that gate.
  • It does not address every possible ownership gap outside the PR mismatch path. The incident’s durable mismatch no longer strands downstream work, which removes the trigger observed here.
