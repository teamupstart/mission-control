What changed after the transfer

  1. The repository previously used Blacksmith's 4-vCPU label for the four heavy jobs.
  2. PR #789 replaced Blacksmith with Frontend Platform's ubuntu-4cpu-32ram-150ssd runner. The standard gates job finished, but all four larger-runner jobs remained unassigned for 1h 23m 44s before cancellation. GitHub returned empty runner names and groups. This is direct evidence that teamupstart/mission-control was not on that runner group's selected-repository list.
  3. PR #790 restored all Linux jobs to repository-accessible ubuntu-latest and reduced CI workers to two. CI could run again, but the next green workflow took 24m 11s.
  4. Github_Org_Settings_TF PR #131 then added Mission Control repository ID 1296871890 to the selected repositories for frontend-platform, granting access to both required runner sizes.
Access gap resolved. The transfer exposed a runner-group authorization gap, and the 2-CPU fallback caused the measured performance regression. The merged Terraform change resolves that authorization prerequisite. Live CI still needs to prove assignment and elapsed time for the direct configuration.

Limits, acceptance gate, and iteration loop

The five-minute goal is not yet achieved. Runner access is merged, but no workflow has completed with the direct 8-core unit and five-shard 4-core E2E allocation. Live workflow execution and any required tuning remain external work.

Acceptance gate

  • Measure from workflow created_at to terminal updated_at, not only test-step duration.
  • Require all eight checks green with no Playwright retry or flaky-test line.
  • Require total queue-aware time at or below 5m 00s.
  • Retain Node 24 and 26 unit coverage, bundle smoke, and all five E2E shards.

Bounded iterations

  1. Run the direct 8-core unit and five-shard 4-core E2E configuration three times with warm caches, plus one cold-cache run.
  2. If E2E is over five minutes and stable, inspect shard balance and setup time before changing capacity.
  3. If four Playwright workers introduce retries or flakes, reduce workers without reducing the five-shard coverage.
  4. If unit remains over five minutes, inspect per-file balance and Node's test sharding before requesting 16 cores.
  5. Stop as soon as three consecutive queue-aware green runs are at or below five minutes. The operator authorized at most ten iterations.
