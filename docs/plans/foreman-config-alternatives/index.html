Six ways to stop the configuration column running the page

Six alternatives to the left control column in the Foreman settings pane, each drawn with the app's real stylesheet and real values read off the running daemon. All six are interactive - tabs switch, rows expand, the sheet opens, presets apply - and every pixel figure in a header chip is measured off the laid-out page rather than asserted in prose, so a claim cannot drift from what the mockup renders.

The measurement

Taken from the live pane at an 849px viewport. The control column is 1988px tall - 2.3 screens - and carries 14 interactive controls, roughly one every 142px. Beside it the ledger is 597px and scrolls inside itself, so it never grows. Everything past the first screen of scroll is form on the left and dead space on the right.

Two things follow. Seven of the fourteen controls are model dropdowns - provider, four Foreman roles, three backlog harnesses - which are set once and then never touched; they occupy about 900px, or 45% of the column. And most of the pixels are prose: every field carries a two-to-three line blurb that is load bearing the first time and noise every time after.

Corrected in this revision

Foreman has no Trust setting. The first draft gave it a "Trust" group, which invented a control the panel does not have. Foreman cannot edit the repo allowlist: it renders a read-only count and a "Manage in Trust" deep link into the separate Trust category, and that is all it may ever do here. Five of the six now render that line through one shared helper that can only produce a sentence and a link; E has to inline it, and it is the one value in that paragraph with no picker behind it.

Two related facts the mockups now get right. The model lists are provider-scoped - this snapshot runs Codex, so every Foreman role lists Codex models and changing the provider clears all four role overrides. And there is no Cheap-tier column on the ledger: that column is keyed on the Shadow posture only, and this snapshot is On, so drawing it would show a permanently empty track. Every value now comes from one verified file, mock-data.js, rather than being retyped into six pages.

The six

Each one tests a different idea about what the problem actually is. They are not six skins of the same layout.

Option A

Digest column

Change the resting state

The column becomes a readout - one line per setting, name … value - and expands into the real editor when clicked. Config doubles as the answer to "what is Foreman set to".

Option B

Grouped tabs

Paginate it

Four tabbed groups, so the column is as tall as the tallest group rather than their sum. Nothing collapses, nothing takes a second click, and the blurbs move to a hover.

557px to 729px by tab · open →
Option C

Ledger first

Take the width back

The column goes away. A 56px posture bar keeps the live readings and the cheap tier; everything set-once moves behind a Configure sheet, and the ledger takes the full width.

0px column · ledger +46% · open →
Option D

Card grid

Turn the page 90 degrees

Ledger full width on top, the six cards below as a responsive grid. Nothing is hidden and nothing takes an extra click; the settings spend horizontal space instead of vertical.

808px comfortable · 489px compact · open →
Option E

The config as a sentence

Re-express it entirely

The configuration stated as readable English, where every value is an inline token you click to change. No labels, no blurbs, no form - the sentence is the documentation.

325px · the most compact of the six · open →
Option F

Postures, not fields

Ask a smaller question

Three named postures - Cautious, Balanced, Trusting - as the resting state, with the fourteen fields as the detail behind a disclosure. Questions whether the operator should answer 14 questions at all.

If you want a recommendation

A, then C. A is the one that fixes the stated problem without betting the console pattern on it: the column stops being long, the panel gains a status readout it does not currently have anywhere, Inspector and Shipping are untouched, and it adds no persisted state. C is the better end state and the argument for it is the width rather than the height - the Asked column is being cut in half by a form nobody reads twice - but it forks the shared console layout, which is worth doing deliberately rather than as a side effect of shortening a column. The two compose: A's digest rows are the natural contents of C's sheet later.

D is the sleeper. It is nearly as cheap to build as B, hides nothing at all, and is the only option where every control stays one click from edited. Its real cost is not pixels, it is that you can no longer see a decision and the setting that produced it at the same time - which on this particular panel is most of the value.

E and F are the interesting ones to argue about, not to ship first. E is the most compact of the six by a wide margin - 325px, a sixth of today - and the least extensible: a fifteenth setting has to be written into a clause by a person. F is the only option that questions the premise, asking whether an operator should be choosing seven model ids at all, and it is also the only one that invents new persisted state and bakes in model opinions that go stale every time a model ships.

One result worth noticing before anyone falls for F. It is the option that asks the fewest questions and it is also the tallest at rest of all six: 985px, against 553px for A and 325px for E. Three posture cards that each have to explain themselves cost more vertical space than the fourteen fields they replaced, and opening the detail takes it to 2519px - taller than the 1988px column this whole exercise set out to shorten. Fewer decisions is a real improvement and it is not the same improvement as less panel. If F is attractive, it is attractive for the first reason, and it should be built knowing it makes the second one worse.
