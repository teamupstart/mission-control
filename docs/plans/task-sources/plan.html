Plan: Task sources

A shared interface for pulling work into the backlog from systems that already hold it - GitHub issues first, but nothing in the interface should know that.

Scoped · sources return candidates, the daemon writes · no auto-dispatch

The problem

Every task in Mission Control is typed by a human into the dispatch form. That is the only door. Meanwhile the work already exists somewhere: open issues, a triage board, an on-call queue, a spreadsheet of flaky tests. Re-typing it is the friction, and the re-typing is why the backlog is usually emptier than the real backlog.

The obvious fix - "add a GitHub integration" - is the wrong shape. It puts gh issue list in the middle of the dispatcher, and the second source (Linear, Jira, a cron that files a task when a nightly build fails) either copies all of it or bolts a second special case onto the same code. So: one interface, many implementations, and the daemon owns everything the implementations must not be trusted to get right.

What a task source is

A task source reads an external system on a schedule and returns candidate tasks. That is the whole contract. It does not write to the database, it does not dispatch anything, and it does not decide whether a candidate is new.

That split is the point of the design:

  • The daemon is the only writer of the DB (CLAUDE.md), and a task source is not the daemon. Returning data instead of writing rows keeps that invariant true by construction, rather than by every implementer remembering it.
  • De-duplication, normalization and caps get enforced once. A source that got dedupe wrong would re-file the same issue every sweep, forever. Making that impossible to get wrong is worth more than the flexibility of letting each source try.
  • It makes a source a pure function to test. sweep(config) -> candidates needs no database, no registry, no HTTP.

Sources never type into a pane

This is the safety boundary, and the README already has the paragraph that explains why it matters ("The daemon is no longer strictly reactive - read this before adding another autonomous writer"). The skills reload loop types into live panes on its own schedule, and needs settledIdle plus a pane read plus withPaneLock before it dares.

A task source needs none of that, because it writes backlog rows and nothing else. The worst a broken source can do is file junk into a list, which a human then reads and deletes. Nothing is provisioned, no worktree is cut, no keystroke is sent.

Auto-dispatching swept work is therefore explicitly out of scope, and not because it is hard: it is a different risk class, and it would need its own gate (an allowlist, a rate limit, a dry-run mode) of exactly the kind Foreman already carries. If it is ever wanted it is a separate change with a separate argument.

Data flow

The interface

Lives in src/shared/task-source.ts, imported by both the server and the settings UI.

/** Where a candidate came from - the identity a sweep is de-duplicated on. */
export interface TaskSourceRef {
  sourceId: string;
  /**
   * Stable id in the EXTERNAL system, e.g. "owner/repo#123". Must be stable across
   * sweeps for the same underlying item and unique within the source; it is half of
   * the de-duplication key and nothing else is.
   */
  externalId: string;
  url: string | null;
}

/**
 * One item a source proposes for the backlog. Deliberately the shape of a TASK, not a
 * passthrough of the external record - deciding what an issue's *intent* should say is
 * the part that needs judgement, and the part the source is uniquely able to do.
 */
export interface TaskCandidate {
  ref: TaskSourceRef;
  title: string;
  intent: string;
  repoRoot: string;
  kind?: TaskKind;
  agent?: AgentType;
  priority?: TaskPriority | null;
  labels?: string[];
}

export interface SweepResult {
  items: TaskCandidate[];
  /**
   * A failure NEVER retracts anything: an unreachable API means "unknown", not "there
   * is no work" - the same stance pr.ts takes when `gh` is missing.
   */
  error: string | null;
}

export interface TaskSourceImpl<C> {
  /** APPEND-ONLY - it is persisted in config. */
  kind: string;
  label: string;
  blurb: string;
  configSchema: z.ZodType<C>;
  /**
   * "Can this run at all?" - null when fine, else a sentence naming the fix. Separate
   * from sweep so settings can tell a misconfigured source from an empty one, which is
   * the difference between "nothing to do" and "silently broken for a week".
   */
  preflight(config: C): Promise<string | null>;
  sweep(config: C, ctx: SweepContext): Promise<SweepResult>;
}

Configuration

One generic wrapper around each kind's own blob, persisted in app_config under taskSources - the same schema-validated-KV pattern as harnesses.ts, which means no migration for a new key. Fields: id, kind, label, enabled, repoRoot, intervalMs (clamped), defaults (kind, agent, priority, labels), maxPerSweep, and the kind-specific config.

enabled: false by default is deliberate: adding a source is configuration, turning it on is consent, and they should be two separate acts.

Ingest - the part sources don't get to do

  1. Drop anything already seen, keyed (sourceId, externalId).
  2. Resolve and validate repoRoot through the same resolveRepoRoot the dispatch route uses.
  3. Normalize through DispatchSchema, so normalizeLabels and the priority enum apply to a machine-authored task exactly as to a typed one.
  4. Cap at maxPerSweep, and log what was dropped. A silent truncation reads as "that's all there was".
  5. Create through TaskManager.create({ …, backlog: true }) - the same path the dispatch form takes.
  6. Record the seen row, in the same transaction as the insert.

Why task_source_seen is its own table

The obvious design is to put source_id / external_id on tasks and de-duplicate against that. It is wrong for one reason, and it is the reason that matters:

A task you deleted must stay deleted. Dedupe against tasks means deleting a swept task makes it un-seen, so the next sweep files it again - the source becomes impossible to say no to, and the delete button becomes a snooze button that doesn't even snooze.

So a seen row outlives the task. The columns on tasks still exist (source_id, external_id, source_url) but they are for the link back, not for identity. Both are needed; they answer different questions.

  • Re-filing something you deleted is a deliberate act: "Forget seen items" on the source in settings.
  • Updating an already-seen item (its labels changed upstream) is not in v1. A sweep files new work; it does not reconcile old work. Re-syncing has to decide what happens when a human has edited the task since, and deserves its own design rather than being smuggled in.

The sweeper

startTaskSourceSweeper() starts in src/server/index.ts beside the eight existing pollers, following the canonical shape from discovery/poller.ts: a self-rescheduling setTimeout (never setInterval, so ticks cannot overlap), unref() so it never holds the process open, try/catch inside the tick so one bad sweep never kills the loop, and a returned stop closure wired into shutdown(). It runs in the daemon because ingest writes to the DB, and the port bind is the mutex.

The GitHub issues source

Auth is gh, and there is no credential to store. src/server/pr.ts already shells out to gh with cwd set to a checkout, letting it resolve both the repo and the user's existing gh auth. Doing the same here means this feature adds no token storage, no OAuth flow and no new secret to leak.

ConfigMeaning
repoempty = whatever gh resolves from repoRoot's origin
labelsAnymatch issues carrying any of these; empty = no label filter
assignedToMeonly issues assigned to the authenticated gh user
unassignedOnlythe "up for grabs" sweep. Mutually exclusive with the above - the schema refuses both, since together they select nothing and a filter that silently matches nothing is the worst failure for a background sweep
priorityFromGitHub label → task priority, e.g. {"P0": "blocker"}
copyLabelscopy the issue's labels onto the task

One call, with a timeout, through the existing run() helper (which never throws on a missing binary). A non-zero exit becomes {items: [], error} - never an empty success, so a broken gh cannot read as "no issues".

gh issue list --state open --limit <n> [--label …] [--assignee @me] [--milestone …]
  --json number,title,body,url,labels,assignees,updatedAt

The externalId is owner/repo#number taken from the issue URL, so it stays stable even if repo is reconfigured. Copied labels go through normalizeLabels - which is exactly why that function preserves case, since Type: Bug must still match the issue it came from.

Settings

The panel follows HarnessesPanel.tsx, with a useTaskSources() hook polling at 4s with optimistic apply and revert-on-refusal.

What ships, and what does not

In: the shared interface, the registry, the sweeper, ingest with its seen table, the GitHub issues implementation, the Settings category, README, tests.

Out, deliberately:

  • auto-dispatching swept tasks - a different risk class, see above
  • re-syncing an already-seen item when it changes upstream
  • any source other than GitHub issues; the interface is the deliverable, and a second implementation is the proof it works, which can come later
  • writing back to the external system (closing an issue when the task lands)

Tests

  • task-source-contract.test.ts - every registered kind has a unique appended id, a schema that accepts {}, and a preflight that never throws.
  • task-source-ingest.test.ts - the load-bearing one: a re-sweep files nothing; an item whose task was deleted still files nothing; a non-repo repoRoot is refused; labels and priority go through the shared normalizer; the cap is reported, not silent.
  • github-issues-map.test.ts - gh JSON fixtures to candidates, a non-zero exit becoming an error rather than an empty success, and the mutually-exclusive assignee filters being refused by the schema.
  • task-sources-panel.test.ts plus the sidebar discriminator.

Open decisions

Both are called here rather than left implicit; both are cheap to reverse.

  1. Swept tasks land in the backlog only, never dispatched. Recommended, and assumed by everything above.
  2. A deleted task stays deleted until you explicitly "Forget seen items". The alternative - dedupe against live tasks - makes delete meaningless.
