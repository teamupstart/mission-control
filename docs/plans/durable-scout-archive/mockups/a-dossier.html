Resume permission loss

Why did a resumed agent lose repository permissions?

Resume rebuilds a session from its stored configuration but never replays the repository grant, so the relaunched session starts with an empty allowlist. Every resumed session loses repository writes at its first tool call, and the failure surfaces as a generic permission refusal rather than a missing grant.

The grant is written once at dispatch and read back into the live session object, never into the configuration the resume path reconstructs from. Resume therefore reproduces every field it was taught to persist and silently drops the one field that only ever existed in memory, which is why the stored row still looks correct when you inspect it after the failure.

What we ruled out

  • Expiry. The grant carries no lifetime, and a session resumed one second after launch fails identically.
  • Worktree identity. The rebuilt session resolves the same absolute path and the same repository id.
  • Harness differences. Claude, Codex, and Pi all lose the grant at the same point in the resume path.

Limits

This was reproduced on manual resume only. Automatic resume after a daemon restart takes a different entry point and was not exercised here, so it may fail earlier or for an unrelated reason.
