Automatic test database isolation

Give every Node test worker disposable state before imports, preserve tests that own a seeded database, and make the SQLite boundary refuse unsafe paths.

Approved direction. One cohesive implementation unit. The runner bootstrap, database refusal, regression coverage, and documented commands land together.

Status and decision record

Approved for implementation and scheduling on 13 August 2026.

  • Isolate every Node test worker, including the ordinary and focused Electron suites.
  • Clear inherited MISSION_HOME and FLEET_HOME, then seed low-priority HARNESS_HOME.
  • Use one temporary state root per test file/worker, never one shared suite DB.
  • Strengthen openDb() as defense in depth, including cached connections.
  • Preserve existing file-local homes and seeded migration fixtures.
  • Keep expected suite overhead below one second on the measured 596-file suite.

Suite contract

Still convention-dependent

Each author must remember the preamble and import ordering. State resolution freezes at module load, so one omission or early value import can target operator state.

The existing openDb() refusal catches the common omission under Node's test runner, but it runs after the singleton early return and accepts a raw string-prefix relationship between the current override and frozen DB path.

An experimental bootstrap that set MISSION_HOME caused workflow-check-provider-column.test.ts to bypass its hand-built DB selected through HARNESS_HOME. The corrected low-priority bootstrap passed that test and the complete suite.

Required behavior

Automatic worker bootstrap

  1. Act only in a Node test worker.
  2. Clear inherited higher-priority state aliases.
  3. Set a fresh HARNESS_HOME fallback.
  4. Use no TypeScript or server imports.
  5. Clean only the explicit directory that worker created.
  6. Never open SQLite.

Both package test entry points and the documented focused command load the bootstrap before tsx.

Database refusal

Under Node's test runner, openDb() may open only the harness.db chosen by the current explicit state override, in a temporary test location. Validation runs before a new or cached connection is returned. Production continues opening operator state unchanged.

Steady-state checks remain normalized string/path comparisons. They do not add repeated stat, realpath, or traversal work.

Compatibility

  • File-local MISSION_HOME and HARNESS_HOME assignments still select their fixture before imports.
  • Pre-migration databases continue upgrading in place.
  • A test with no local setup uses the worker fallback.
  • Missing, late, operator-looking, and non-temp overrides fail before a DB write.
  • Concurrent files never share state or sentinel IDs.
  • Guard-regression children remain jailed under a fake OS home.

Flow change

Today, each test file must establish state before imports reach config.ts. After the change, the runner supplies a safe fallback first; a test may replace it; configuration freezes the selected path; and openDb() validates before using a connection. Production bypasses the test-only steps.

Performance interpretation.

Record full-suite wall time but compare more than one recent sample. Unchanged baselines varied by 41.7%, so one small delta is not attributable.

Non-goals

  • Do not delete polluted Bypass rows; cleanup is destructive and separately authorized.
  • Do not rewrite the 225 file-local test homes.
  • Do not share a suite DB or serialize DB tests.
  • Do not change production state precedence or filenames.
  • Do not change UI, wire contracts, persisted schema, migrations, CI concurrency, Electron behavior, or E2E isolation.

Success criteria

  • Standard and focused commands cannot mutate operator DB state.
  • Migration fixtures open their hand-built databases.
  • A future DB test without a preamble gets isolated state automatically.
  • Malformed setup fails closed.
  • Typecheck, lint, and the full suite pass.
  • No meaningful bootstrap performance regression appears.
