Design plan · decided

Pipeline stages on a session card

Render an ai-conductor run's stages on the board session card as a compact phase meter, with a per-phase hover popover carrying that phase's live status.

The card says one word about a 22-step feature today. Everything it needs to say more is already in the browser, so this is a rendering change with no wire cost. The operator selected Option A, the phase meter; options B and C are retained in the mockups as the design record.

The problem

One word, on a 22-step feature

PipelineChip renders ↸ add-widgets · Build. So the card cannot answer the three questions an operator scanning a board actually has:

  • How far along is this feature? Unanswerable.
  • Has anything failed, and where? Unanswerable - a halted run's card looks like a working one.
  • What did this run's tier or track skip? Unanswerable.

The information exists, is already in the browser, and is drawn only on a page the operator must navigate to or a pane they must open. The card is where triage happens, and it is the one surface that says nothing.

What stays fixed

  • SessionPipelineLink keeps its four fields.
  • No SSE frame widens.
  • No engine-owned file is written.
  • Gate verdicts stay detail-only.
  • No second copy of the phase fold.
  • Console rail and detail band unchanged.
  • No meter on a managed Pipeline host.

What ships

The caption row

↸ <slug>, the current phase as one word, and n/N counted over the run's own sequential steps. The slug keeps today's click target - it opens the run in Runs.

The bar

  • Five segments, one per phase, about 7px tall.
  • Width proportional to that phase's step count in this run, with a min-width floor so a one-step phase stays hittable.
  • Fill is the fraction of that phase's steps that are finished.
  • Tone from pipelinePhaseStatus, so failure outranks running and both outrank arithmetic.
  • The current phase carries a ring, findable without colour.
  • A phase that finished with skips is hatched, not solid green: "done" and "done, 2 skipped" must not be the same fill.

The popover, per segment

The phase name, its status label, one row per step with its own state glyph and tone, struck through when skipped, and a footer carrying the halt sentence or the skip reason when there is one. Drawn at rest in the "what hovering a stage opens" row of the mockups.

Why this costs nothing on the wire

The obvious first guess - that the card needs more data - is wrong, and the contract says so out loud.

The constraint, honoured

SessionPipelineLink deliberately carries only the run key plus one step, and explains itself:

a whole PipelineRun on every session frame would ship 22 step states per correlated card per sweep to say one word on a chip.

That stands. Nothing here widens it.

Why it does not need to

useEventStream already holds every run on the fleet in a map keyed by the run's own identity, seeded from the connect snapshot and kept live by pipeline_upsert. PipelineRun.steps is the full step list.

App.tsx already hands the board a pipelineRunByKey map - it is where SessionTile's existing pipelineRunObserved boolean comes from. The card joins a map it is already being passed.

Target flow

Findings that constrain the build

The derivation already exists

pipeline-run-model.ts already folds a run into what the meter needs: pipelineStrip, pipelinePhaseStatus (including degraded when a phase finished but skipped something), pipelineStepStatus for the popover rows, and pipelineEyebrow.

This is a new leaf rendering over an existing derivation. A second copy of any of it is the specific failure this plan exists to prevent.

  • pipelinePhaseStatus reads only step state, never a gate verdict - so no gate fetch.
  • Out-of-band steps have no slot in the sequence, so they never go inside a segment. Drawing one there would claim the run walked past something never on its path.

The step list is per repository, not a fixed 22

The frozen table is a display copy and never an authority. The tolerance is not theoretical: ai-conductor builds its effective step list from config, and its own config disables manual_test and inserts two custom SHIP steps. A card observing that repository sees names the table does not contain.

  • Segment widths come from run.steps. A hardcoded 22, or a hardcoded 1/1/9/5/6 split, is a bug on the repository this feature was built to watch.
  • Counters read the run's own sequential steps.
  • A step with no placeable phase still counts in n/N - it is a step the run really has. It is never silently dropped from the total.

Extending Tooltip, and what that has to respect

The argument for widening rather than adding a primitive is what Tooltip already does: a body portal, two-stage vertical flip, horizontal edge clamping with a matching caret offset, no wrapper DOM node (handlers merged onto the child, which is what lets chips stay flex items), a disabled-trigger anchor path, auto-hide, and a separate visually-hidden description for aria-describedby.

  • The accessible name stays a string. The node arm carries both the rendered content and the sentence a screen reader gets; rendering JSX into the description node would put markup into an accessible name.
  • Measurement stays in the ref callback, not a layout effect - that is what keeps the component silent under the renderToStaticMarkup every component test uses.
  • test/tooltip-coverage.test.ts stays green. No escape hatch, by design.
  • The string arm is unchanged. This is an additive widening, not a migration.

The registry entry, and where it must not go

src/web/lib/board-card.ts is the single registry of optional card items, enforced by test/board-card-items.test.ts. The meter is a body region like the existing workflow item, so it takes a DISPLAY_ITEMS entry under group: "card", and the Settings checklist grows a row.

It must not go in .tile-marks. That row means "things that want your attention", and an operator must not be able to configure themselves into missing "this session needs you". A halted run's attention signal stays where it is; the meter is progress, not an alert.

Only externally driven workers draw it

Session.pipeline is stamped only on a session Mission Control did not launch, whose working directory is inside an observed run's worktree. That is the same population that already gets PipelineChip and the driven-composer sentence, so the meter joins an existing presentation rather than starting a new one.

Session.task.pipelineRun - the managed Pipeline host - is out of scope. docs/pipelines.md records that a managed host deliberately does not borrow the externally driven presentation, so extending the meter there is a separate decision and not an omission.

Because Session.pipeline is null on every fleet with no pipeline provider enabled, and every consumer fails open, an ordinary installation draws nothing new and pays nothing.

Prior art

docs/plans/workflow-card-progress/ designed the workflow ladder already on this tile, and drew a boundary worth respecting: a vertical ladder is for the detail pane, because height is the axis a detail pane has.

The phase meter is horizontal for that reason, and it is deliberately not a ladder - the tile already has one, and a second would read as the same thing twice.

Risks

What could go wrong

  • The meter re-derives what the model already computes.
  • Hardcoded step counts break on a repository with custom steps.
  • A one-step phase becomes an unhittable sliver.
  • Widening Tooltip regresses a surface that depends on it.
  • Markup leaks into an accessible name.
  • The card gets taller and the board fits fewer sessions.

How each is held

  • The new module imports the fold; a test asserts segment tones come from pipelinePhaseStatus.
  • Widths from run.steps, plus a fixture with unknown names and a non-22 total.
  • A min-width floor, pinned by a test rather than left to flex.
  • Additive string arm, unchanged measurement path, and the coverage scan as the gate.
  • The node arm carries a separate text description; a test asserts it is plain text.
  • About 11px, and registry-toggleable like workflow.

Verification and acceptance

  • Fold tests over a halted run, an all-skipped S-tier run, a stale kicked-back run, a run with step names absent from the frozen table, and a run with a one-step phase.
  • test/board-tile-render.test.ts - markup shape, including that nothing renders when Session.pipeline is null.
  • test/board-card-items.test.ts - registry parity for the new item.
  • test/tooltip-coverage.test.ts stays green.
  • A Tooltip test covering the node arm, asserting the description node still resolves to plain text.
  • An e2e/ spec is required: the meter appears for a correlated session, hovering a segment reveals that phase's status, and the Settings checklist row hides it.
  • Select by role, label, or placeholder. Never add data-testid. Never spend model tokens.
  • npm run typecheck, npm run lint, npm test, npm run test:e2e.
