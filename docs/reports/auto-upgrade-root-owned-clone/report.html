Investigation report · 30 August 2026

Mission Control 1.3.0 crossed the privilege boundary in the wrong place

The update reached the source checkout, then failed before build or app installation. The previous 1.2.0 application is still installed and a second copy of it remains in the retained failure directory.

Root cause confirmed

A root-owned nested directory blocked Git

The updater-owned app-src clone contains directories and tracked files owned by root:staff. A broad sudo make install was previously needed to cross the unwritable /Applications boundary, but it also ran checkout, build, and receipt writes as root. Mission Control later launched its detached updater as the signed-in account. During git checkout --force v1.3.0, Git therefore could not unlink a tracked file below src/server/setup and exited 1.

The displayed rollback error was a second instance of the same missing privilege boundary: the signed-in account cannot create the rollback sibling in /Applications. The old helper also discarded cp stderr, hiding that detail. It did not remove the working app: /Applications/Mission Control.app remains version 1.2.0, and failed-update/previous-app.bundle is also version 1.2.0.

The implemented repair

  • install-app.mjs now checks directory rewrite access before fetching or checking out the disposable clone.
  • If the clone is not writable, it creates a complete fresh clone first, atomically renames the old clone aside, and installs from the fresh canonical path. An old privileged directory that cannot be removed is preserved for one-time administrator cleanup without aborting the update.
  • app-bundle-swap.mjs keeps checkout, build, and state writes unprivileged. When /Applications is unwritable, it asks macOS for administrator authorization once for a fixed-path atomic product-bundle transaction. Arbitrary destinations are rejected.
  • Once the new app is live, deleting or filing the displaced bundle is best-effort in both the direct and administrator-authorized paths. A retention failure leaves the displaced app at its per-transaction fallback sibling and cannot turn a successful install or rollback into a reported failure.
  • apply-update.mjs uses the same narrow transaction for rollback, carries the decisive tail of install output into the failure result, and retains rollback stderr.
  • The existing remote identity check still runs before replacement. A non-canonical clone is rejected rather than silently trusted or deleted.

Operational boundary

This investigation did not mutate the live state directory or reinstall the application in /Applications. The currently installed 1.2.0 helper predates this repair. To acquire it, run an installer containing this change as the signed-in account, without sudo. macOS will request administrator authorization only for the final application swap. Later automatic updates use that same narrow prompt and can repair the clone ownership shape themselves.

Supporting operator guidance was added to desktop and packaging and the release verification runbook.
