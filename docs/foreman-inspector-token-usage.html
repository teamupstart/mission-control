The short answer

Neither loop is expensive at rest. Both become expensive in proportion to how much the fleet is doing, and the dominant cost is not the loop rate, it is the size of a single prompt.

The governing fact

Loop rate is almost irrelevant to cost. Foreman wakes up ~900 times an hour and makes a model call on a small fraction of those passes. What actually sets the bill is that one Foreman review carries ~61 KB of context and one Inspector review carries ~88 KB, every call is a cold process with no context reuse, and 28% of the Inspector's prompt on this repository is a duplicated file.

Does the polling itself cost anything?

No. Not one token. A poll that finds nothing new spends localhost HTTP calls, one gh subprocess per PR, and a SQL query. A model is spawned only when something genuinely changed:

  • Inspector: the PR head sha moved (a new PR, or a new commit pushed to one), or somebody replied in one of our threads.
  • Foreman: a session produced a new episode, meaning a distinct handledMarker. That is a new dialog on the pane, a new structured request from a driver, or a newly parked no-mistakes gate. An idle session that keeps being idle mints no new marker and costs nothing.
  • Foreman queue: a work item finished and the session settled idle, so there is a real diff to verify.

Selection is deliberately separate from spending, and this is the part worth understanding. tickTargets over-selects on purpose: promptedWantsATick keeps every idle instrumented session on the list forever, because the card summary cannot see whether it already wrapped up. Those sessions get looked at every pass and the machine answers skip in pure code. Being selected is free; only a state change opens the wallet.

Four honest exceptions

1. Retries pay twice for one answer. runStructured re-sends the entire prompt plus a 74-byte scolding when the model's reply will not parse. One logical review can cost two full spawns, and the failure caps allow up to six across ticks.

2. A failing PR burns tokens producing nothing. This is why the backoff ladder exists. Before it, a permanently broken PR was retried every 90s forever, at up to two claude -p runs a tick. It is now capped, but the first few failures are real spend for zero output.

3. A flapping marker is not real work. EVAL_DEBOUNCE_MS = 60_000 exists specifically because a marker keyed on a moving lastActivity can change without anything meaningful happening. The debounce bounds that to one call per session per minute rather than eliminating it.

4. Two settings would break the rule, and you have both set the cheap way. Foreman's triage: "shadow" (the shipped default) runs the cheap and the expensive tier concurrently on every evaluation. The Inspector's mode: "dry-run" still pays the full review call and simply does not post the result, and switching dry-run to live re-reviews the same unchanged head a second time (reviewNeedsLiveRerun). You are on triage: "off" and mode: "live", so neither applies to you today.

Two consequences of "runner: codex"

1. The Inspector gets no tools. codexRunner.sandbox is null, so inspectorRunOptions omits the tool grant entirely (inspector/worker.ts:157). The review is one shot over the supplied diff, with no Read/Grep/Glob round-trips. On the Claude runner the same review was measured at 13 turns on Opus, 23 on Sonnet, each turn re-sending accumulated context. So your prompt size is roughly your cost; on Claude it would be closer to an order of magnitude more.

2. Neither subsystem's spend reaches Mission Control's own cost ledger. The only writer of usage_ledger is applyOtelMetrics (registry.ts:3608), fed by the OTLP route from Claude Code sessions. Headless runs spawn as codex exec --ephemeral --ignore-user-config, which exports nothing. The fleet cost figure on the dashboard excludes both loops entirely.

Cadence: how often each one loops

They are not the same kind of loop

The Inspector is a poller: tick() runs, then arms setTimeout(tick, POLL_MS) at the end (inspector/worker.ts:1081). Period is 90s plus however long the sweep took.

The Foreman is a busy loop: main() is for(;;), and the 4s sleep is conditional on if (!advanced) (foreman/worker.ts:364). A pass that did something comes straight back around. Between two sessions inside one pass it waits only BETWEEN_MS = 400.

Triage is off, so the expensive tier runs unconditionally

The cheap tier exists precisely to keep Tier-2 from firing. With triage: "off" every needs-you episode that clears the debounce goes straight to gpt-5.6-terra at ~16.6k tokens. Setting it to "on" puts a ~7.1k-token gpt-5.6-luna router in front and escalates only on route-up. Note that "shadow", the shipped default, is the worst setting for cost: it runs both, concurrently, on every evaluation.

The gate that does the real work

if (s.headSha === pr.headSha && !reviewNeedsLiveRerun(...)) return (worker.ts:595). One review per push, not per tick. A PR that sits untouched for a day costs 40 gh calls an hour and zero tokens. This is why the Inspector is cheap despite carrying the largest prompts in the system.

Measured from your live database

PR #323 was adopted at 1785456624059 and last reviewed at 1785457338438, at round: 3. That is 3 review rounds in 11.9 minutes, about 238s per round, consistent with a 90s poll plus review duration. Extrapolated: ~15 rounds/hour on one actively-iterating PR, or roughly 355k tokens/hour from a single PR while an agent is pushing to it.

Backoff, so a broken PR is nearly free

backoffMs(n) = min(90s × 2n-1, 6h), giving 90s, 180s, 360s, 720s and so on to BACKOFF_CEILING_MS = 21_600_000. A diff too large to buffer goes straight to the six-hour ceiling as push-fixable, and only a new push can clear it. A push otherwise cuts the wait short at most PUSH_UNPARK_MAX_FAILURES = 3 times.

The one uncapped fan-out

waiting.length in processPr is unbounded. Every thread of ours where somebody else spoke last gets its own reply call, run serially at up to 300s each, before the review even starts. createLimiter(1) bounds PRs against each other, not calls within a PR. The only brake is MAX_REPLIES_PER_THREAD = 6 per thread.

No caching, by design

Every call is a cold subprocess. claude -p passes no --resume, --continue or --session-id; codex exec passes --ephemeral. Both set runInThread: null. This is a stated correctness property, not an oversight: Foreman reviews many sessions, and a shared context would let session A's transcript influence the verdict on session B, while growing monotonically forever. Server-side prompt caching still applies and is the only reuse available.

Waste and defects found while measuring

1. 24 KB duplicated in every review and every verify

CLAUDE.md in this repository is a symlink to AGENTS.md. Both names are in ROOT_NAMES, and readStandards deduplicates on the requested absolute path (seen.add(abs), standards.ts:126) while readRepoDoc resolves the symlink only for the read. The bundle therefore ships the same 24,576 bytes twice. Verified directly: docs[0].text === docs[1].text returns true.

Cost: ~6.6k tokens per Inspector review and per Foreman verify, about 28% of the Inspector's small-PR prompt. At the measured 15 rounds/hour that is roughly 100k wasted tokens per hour from one PR alone. The fix is one line, resolving the real path before the seen check.

2. MAX_DIFF_BYTES is a character slice, not a byte cap

full.slice(0, maxBytes) (github.ts:704) operates on a JS string. Measured: a 400,000-character slice produced 400,556 bytes on a real diff, and up to 1,200,000 bytes on synthetic 3-byte-per-character content. The name and the INSPECTOR_MAX_DIFF_BYTES environment variable both promise bytes.

3. Four uncapped inputs in the Inspector review prompt

prTitle, prBody, changedPaths and open have no cap in buildReviewPrompt. At the ledger's own maxFindingFingerprints = 2000, the open-findings section alone would add 348,230 bytes. The worst-case prompt is 944 KB, about 255k tokens.

4. Two smaller inconsistencies in Foreman

ACTIVITY_CAP = 2000 is applied in buildReviewPrompt but not in buildTriagePrompt, so the router renders the one field a child writes unbounded via report_status un-clipped. Separately, the full reviewer's transcript window is 60 turns, not the 48 that every comment in the worker claims: client.transcript(id) sends turns=48, which the route reads as the tail and adds a fixed head of 12 (routes.ts:1388). The comment at triage.ts:593 also says instructions are "capped at 16KB"; the real cap is 64,000 characters.

5. This spend is invisible to the cost dashboard

usage_ledger has exactly one writer, applyOtelMetrics, fed by the OTLP route that Claude Code sessions push to. Foreman and Inspector runs on the codex runner spawn with --ignore-user-config and export nothing. Even on the Claude runner they would land under a fresh session.id per run, orphaned from any card, and foremanStatus scopes its counts to live sessions. The fleet cost number you are looking at excludes both loops.

6. The diff was fetched twice per active tick (fixed)

A tick that both replied and reviewed used to call fetchDiff once in the reply branch and again at the top of reviewRound, two gh subprocesses each buffering up to 16 MiB, with no sharing. Not a token cost, but it was latency and memory on the expensive path. Fixed: processPr now creates a lazy per-tick memo (diffOncePerTick, worker.ts) shared by both call sites, so an active tick fetches the diff exactly once and the steady-state tick still fetches zero. The memo shares the raw result, failures included, so each consumer keeps its own failure semantics: the reply degrades to an empty diff while the review books tooLarge as push-fixable. Covered by test/inspector-diff-once-per-tick.test.ts.

What not to change

The loop rates are fine. Foreman's 4s floor and the Inspector's 90s poll cost essentially nothing, because both are gated on state change rather than on the clock. Cutting either would trade responsiveness for a saving that does not exist. Likewise the cold-process design: the absence of context reuse is what keeps one session's transcript out of another session's verdict, and it is worth its price.
