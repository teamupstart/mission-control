Approved engineering plan · 20 August 2026

Count human review interactions toward Retro

Make dashboard-mediated human decisions count as the same retro-worthiness evidence as a human text turn, live and after restart, while preserving the existing authorship and Inspector gates.

Decision recorded: proceed directly to phased implementation planning. No product choices remain open.

Problem

Mission Control shows Run retro only when a session is worth cataloguing and GitHub Inspector has finished cleanly. The corrections reason currently comes only from parsed transcript text.

SDKAskUserQuestionA human answer becomes a pure tool_result, which the transcript parser deliberately drops.
MCPrequest_inputTerminal answers and plan decisions also return as tool results, not ordinary text turns.
DURABLEreviews tableThe same decisions are already persisted with resolved_by = 'human' and replayed in the conversation.

The finished Add keybinding for To review button session exposed the gap. The human answered two design questions, PR #689 passed a clean Inspector review, and the session still returned retro: null.

Goal

Offer Retro after meaningful human steering through any supported conversation channel:

  • ordinary human transcript text;
  • a human-resolved SDK question recorded as a review; or
  • a human-resolved MCP review such as request_input or request_plan_decisions.

The result must be immediate while the daemon is running and reconstructible after a daemon restart.

Requirements

  1. Count a review only when isHumanResolvedReview(review) is true.
  2. Count human answered, approved, rejected, and dismissed reviews.
  3. Exclude pending, Foreman-resolved, orphaned, refused, and half-written reviews.
  4. Update the owning live session through the Registry's existing one-way signal.
  5. Restore the same signal from durable human reviews when a terminal or SDK session is reconstructed.
  6. Bound restoration to sessions introduced into the live Registry, not all historical ids.
  7. Keep transcript scanning as the typed-text owner and preserve automated-delivery attribution.
  8. Preserve the corrections wire value and current Session.retro shape.
  9. Leave Inspector timing unchanged.
  10. Describe the reason as human steering so the copy covers questions as well as corrections.

Proposed design

One eligibility signal, two evidence sources

Keep one Registry-owned, one-way session flag. Feed it from the transcript poller for ordinary human text and from ReviewManager after a review is durably settled, published, and proven human.

Do not parse raw tool results as conversation. The review already owns the question, selections, actor, and settlement status.

Restart restoration

Add a focused database existence predicate for one session id. Consult it only when the Registry first introduces that terminal or SDK session row, then seed the same in-memory flag before deriving Session.retro.

Bounded by live sessions: do not load every historical review session id into the Registry constructor.

Live settlement ordering

  1. Deliver the answer where delivery is required.
  2. Commit the settled review row.
  3. Publish the review update.
  4. Mark the live session retro-worthy when the settled review is human-authored.

Failed delivery, failed persistence, or a dangling review with no session row must not retain a new signal.

Data flow

Before this change, the durable review does not feed the Registry interaction signal.

Compatibility and ownership

  • ReviewManager remains the review lifecycle owner and knows a settle committed.
  • isHumanResolvedReview remains the authorship predicate.
  • Registry remains the session projection owner.
  • SQLite remains daemon-only; this adds a read helper, not a migration.
  • retroOffer stays the one browser predicate.
  • RetroReason stays append-compatible by retaining corrections.

Tests and evidence

  • Human ordinary and SDK review answers update Session.retro live.
  • Foreman, pending, orphaned, refused, failed, and half-written paths do not.
  • A fresh Registry restores worthiness from a durable human review.
  • Session eviction removes the in-memory signal.
  • Playwright shows Run retro after an SDK question answer and clean fake Inspector review, with no composer correction.
  • The existing typed-text path and clean-review timing gate remain intact.

The browser proof belongs in e2e/specs/retro-offer.spec.ts and uses the existing fake Claude question path, so it spends no model tokens and reaches no external GitHub service.

Documentation

Update docs/repository-memory.md and the retro evidence note in e2e/README.md so human steering may arrive as transcript text or a human-resolved review. Update tooltip assertions when “corrected” becomes “steered.”

Non-goals

  • Automatically running a retro or making every clean session eligible.
  • Counting permission prompts or Foreman decisions.
  • Parsing raw tool results as conversation text.
  • Adding a persisted retro table or column.
  • Changing post-merge routing, skill gates, or Inspector semantics.

Risks and mitigations

Foreman is mistaken for the humanReuse isHumanResolvedReview; never infer from status alone.

Two UI eligibility rules emergeBoth evidence paths feed one Registry signal; the browser reads only Session.retro.

Completion criteria

A session like Add keybinding for To review button gains retro.reasons = ["corrections"] after the human answers its dashboard question, keeps that reason across restart, and shows Run retro when Inspector is clean, while non-human and unsuccessful paths remain ineligible.
