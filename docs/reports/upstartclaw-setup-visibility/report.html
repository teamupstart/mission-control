UpstartClaw Setup: why it was absent and what now ships

Question: Why is the UpstartClaw integration not showing under Setup, what is the Claude Code extensions item, and is there an UpstartClaw setup guide?

Finding and delivered result: The pre-change implementation hid UpstartClaw after successful setup because it projected only warnings into Setup. The delivered implementation now keeps a detected UpstartClaw core setup row visible: completed reads Ready, while missing, unfinished, malformed, or unreadable setup reads Needs setup beside the interactive remedy. The separate Claude Code plugins row remains a generic count of all Claude plugins, not an UpstartClaw status. The guide at docs/upstart.md now contains the complete first-run sequence and is linked from the UpstartClaw row and Setup documentation.

Pre-change result The daemon returned Claude Code plugins and Mission Control skills in the Agent extensions family, but no UpstartClaw core setup row. That exactly matched the filtering rules at the investigated baseline.

Why the row disappeared before the change

At the investigated baseline, Setup had two different sources of rows. The dependency catalog produced permanent rows such as Claude Code, GitHub CLI, Claude Code plugins, and Node.js. UpstartClaw was absent from that catalog. Instead, it was one of the environment checks that produced a row only when it had a warning.

At the baseline, the key line was the early return in src/server/setup/index.ts:332-340: a check with warning === null became no row at all. The delivered projection now distinguishes positive readiness from absence: a detected completed plugin produces a satisfied row, an unfinished plugin produces a Needs setup row, and an uninstalled plugin remains silent. The behavior stays registry-driven through the UpstartClaw metadata in src/shared/setup-catalog.ts and the shared environment-row projection in src/server/setup/index.ts.

What “Claude Code plugins” means

It is not another name for UpstartClaw. It is a vendor-neutral health check for Claude Code's whole plugin registry. The probe reads installed_plugins.json, reports Missing when it has no usable entries, Unknown when the record cannot be parsed, and Ready with the total installed count when at least one plugin exists.

What it proves: Claude Code has a readable plugin record with six entries.

What it does not prove: that UpstartClaw is installed, that its OAuth and VPN setup is complete, or that any individual MCP server can authenticate.

The row is defined as Claude Code plugins in src/shared/setup-catalog.ts:333-343. Its probe counts every parsed plugin in src/server/setup/index.ts:180-190. The related Mission Control skills row is different again: it checks the app-owned workflow skills that Mission Control links into agent skill directories. UpstartClaw's domain skills are deliberately not copied into that catalog.

What the UpstartClaw integration actually is

Mission Control does not call an UpstartClaw service. Dispatched Claude sessions inherit the operator's Claude configuration, so installed UpstartClaw plugins, skills, MCP servers, and guard hooks load in those sessions. Mission Control adds three narrow integration points around that composition:

  1. A non-blocking environment warning before dispatch and in Setup when the core plugin is installed but not reliably configured.
  2. An explicit UpstartClaw Claude skill query mode for read-only Upstart Jira task sources, gated on the installed plugin and completed setup.
  3. Optional Persona import from the installed agent-team plugin, with UpstartClaw provenance.

Evidence: docs/upstart.md:3-29, src/server/environment/upstartclaw.ts:11-25, docs/upstart.md:97-130, and src/server/task-sources/jira.ts.

The guide now exists as a complete, discoverable setup path

Guide complete docs/upstart.md is titled Running Mission Control at Upstart. It explains the composition model, the interactive setup requirement, the NODE_EXTRA_CA_CERTS daemon concern, the dispatch warning, overlapping-feature boundaries, Persona import, and the complete first-run sequence.

Discoverable The delivered UpstartClaw row links directly to the guide in both Ready and Needs setup states. docs/setup.md and the root README.md also point operators to it. The generic Claude Code plugins row remains deliberately generic.

The guide now includes the authoritative marketplace, plugin installation, setup, and restart sequence:

/plugin marketplace add teamupstart/claude-code-extensions
/plugin install upstartclaw-core@upstartclaw
/upstartclaw-core:setup
# Restart Claude Code after setup completes

The sequence was verified against the UpstartClaw source checkout at README.md:19-28 and plugins/core/README.md:20-31, then added to Mission Control's docs/upstart.md.

Delivered follow-up

The investigation was initially produced as an answer-only Scout. The same task then delivered the product and documentation correction while keeping UpstartClaw optional for machines that do not install it:

  1. The generic Claude Code plugins row stayed generic. Its count remains separate from individual UpstartClaw readiness.
  2. Detected UpstartClaw gained a persistent status row. The row reads Ready for completed and Needs setup for unfinished states. A machine with no UpstartClaw remains silent.
  3. The row links to the setup guide. The guide remains visible beside the interactive skill command when setup needs attention and beside completion evidence when it is ready.
  4. The guide now carries the complete first-run path. It includes the marketplace command, plugin install command, setup command, restart instruction, and verification in Settings > Setup > Agent extensions. docs/setup.md and the root README link to it.

What this investigation did not establish

  • It did not run Glean, Slack, Jira, Guru, or Atlassian authentication probes. A completed state is the plugin's readiness signal, not proof that every credential is currently valid.
  • The initial Scout observation described the pre-change product. This revised report also records the UI and documentation delivered afterward.
  • It did not test a relocated CLAUDE_CONFIG_DIR. The current machine uses the default Claude directory. Source inspection shows the generic plugin reader honors that variable while the UpstartClaw environment check uses ~/.claude directly, so relocated configurations deserve a focused follow-up test before any implementation.
  • The live daemon response establishes the current local state only. Other operators can legitimately see a different row set.
