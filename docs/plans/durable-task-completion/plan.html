Durable, PR-driven task completion

Decouple a task's completion from the state of the session that ran it. Decisions resolved - this is the approved plan.

A task whose work shipped - a pull request we opened for it got merged - must reach done and stop blocking the backlog, whether its session is still idle, was killed, rolled onto new work, or landed in some invalid state. Whether to also close the agent stays a separate preference and must never gate completion.

The problem

Today a task's terminal state is derived from live session state plus the current work episode. When the session attributed to a task moves on, dies, or goes weird, the task can sit in running (or get marked failed) even though its work is done. A task that is not done has two downstream costs:

  • It blocks its dependents. blockersIn (@shared/backlog.ts) clears a task dependency only when the depended-on task is done; a running, failed, or cancelled dependency stays a blocker, so anything waiting on it never gets scheduled.
  • It occupies its agent. agentIsFree (src/server/foreman/backlog-machine.ts) refuses a session that still has a running/dispatching task bound to it, so the backlog autopilot will not reuse that agent.

Observed instance: the session that shipped PR #220 stayed running with its task never settling, because it kept working long after the PR was created - so its current work episode is no longer the one that merged.

Why it happens

The merge is recorded against one specific work episode, and every completion path reads only the current episode:

  • mergedPrFor(taskId) reads only the current task↔episode binding and returns a merged PR only if that binding has mergedAt. Retained historical bindings are ignored.
  • Merge attribution (reconcileWorkEpisodeMerge) fires task_pr_merged only when the current binding matches the merged episode.
  • settleIfEpisodeFinished and closeMergedSession both gate on episodeId === current.

So a merge on a rolled-past episode is invisible to completion. When the session later goes away, agentWentAway calls mergedPrFor (the current, unmerged binding), finds nothing, and marks the task failed - stranding every dependent behind a stopped blocker for work that shipped.

The machinery to fix this already exists but is only half-wired: work-episode↔task bindings are retained as historical, and the dependency merge path already reads current and historical bindings. Standalone task completion simply does not.

Requirement. If a task's work was satisfied by a merged PR, the task is done and does not block backlog scheduling - regardless of whether its session is idle, was cancelled/killed, or is invalid. Session disposition is a separate preference and must not gate task completion.

Adopted decisions

Resolved via the Mission Control dashboard review (2026-07-24).
  1. The durable PR↔task link is the work-episode bindings (current + historical). No new Task.prs field or table. The bindings are already retained and already carry prUrl/mergedAt; completion learns to read the whole record instead of only its head. A first-class field can still be layered on later without migration pain.
  2. A merged PR always upgrades the task to done - even one the operator explicitly cancelled. The work shipped; a row that says otherwise blocks scheduling for work that landed. Only a merged PR upgrades - a closed-unmerged PR changes nothing, and a cancelled task with no merged PR stays cancelled. The upgrade records the merged PR as the outcome so the row says why it moved.
  3. Formalize multiple tasks per session in this change. Task.sessionId becomes a mutable "currently executing on" pointer; the durable task↔episode bindings are the provenance record linking each task to the work (and PRs) it produced. A session runs tasks serially - at most one running/dispatching task at a time, unchanged - but completed tasks no longer pin the session, and the session's task history remains queryable through the bindings rather than a single live pointer.

Design: completion follows the durable PR, not the session

Pull apart two things that are currently entangled:

  • Task completion - a durable fact: this task's work was satisfied by a merged PR we opened for it. Independent of session liveness and episode currency.
  • Session disposition - should the agent be closed - stays gated on session state (idle and not moved on) and never blocks completion.

Completion stops depending on which episode is current or whether the session is alive; closing the agent becomes an optional, separately-gated side effect.

Concrete changes:

  • Durable merge lookup. mergedPrFor(taskId) consults the task's current and historical bindings. (Reads a record already retained.)
  • Durable merge recording. Record an observed merge on the task's binding even after the session rolled to a new episode - the way the dependency path already does.
  • A completion reconciler that ignores session state. One predicate - does any binding for this task show a merged PR? - run on a merge observation, a session going idle, a session removed, the first discovery sweep, startup, and a periodic backstop. Never reads the current episode or requires the session to be alive.
  • Terminal-state upgrade. The reconciler applies to running/dispatching tasks AND to failed/cancelled ones: any task whose binding shows a merged PR is upgraded to done with the PR recorded as the outcome (adopted decision 2). done rows are never touched.
  • Completion keeps resources. complete marks the task done, records the merged PR, and keeps the worktree/home for the operator's Clean up. git worktree remove --force stays a human click.
  • Session-kill unchanged in spirit. Close-after-merge still only fires for an idle session that has not moved on; a session that rolled to new work is never killed. Completion no longer waits on it.

Multiple tasks per session (adopted decision 3)

  • Task.sessionId is "currently executing on" - mutable and nullable. Nothing may read it as "the session that produced this work"; provenance questions go to the bindings.
  • Serial execution is the invariant: at most one running/dispatching task per session at any moment (agentIsFree already refuses otherwise). No concurrent tasks in one pane.
  • A completed task frees its agent immediately. Once the reconciler moves a task to done, the backlog autopilot may hand the session its next task - the N-tasks-over-a-session's-life flow this formalizes.
  • PRs associate with tasks through bindings, never retracted. The live card's prUrl may come and go with episode currency (a decoration); the binding record is what completion, dependencies, and history read.
  • Audit every reader of Task.sessionId and Session.task for the 1:1-for-life assumption - the card's task chip, reconcileTasksBoundTo, agentWentAway, reopenIfWorkResumed, the Foreman backlog machine, and the reset path - and repoint any that wanted "running now" vs "ever ran".

Invariants honored

  • PR provenance. Only PRs Mission Control opened are ever considered.
  • Reclaim is a human click. complete never tears down a worktree - and the cancelled→done upgrade changes the row, never the resources.
  • Dependency resolution unchanged. It already reads historical bindings; this brings standalone completion to parity.
  • Serial execution. One running task per session at a time, before and after.

Tests

  • A task whose merged PR is on a historical episode completes to done.
  • A running task whose session was killed, with a merged PR, completes (not failed).
  • A completed-by-merge task stops blocking a dependent and frees its agent - and the freed agent can be handed a second task, whose completion reads its own bindings.
  • A failed-for-no-outcome task is upgraded to done when its PR is later seen merged.
  • An operator-cancelled task whose PR later merges is upgraded to done with the PR as the outcome; one with a closed-unmerged PR stays cancelled.
  • Session-kill still refuses a session that moved on to new work.
  • Completion keeps worktree/home; existing task-merge-settles / task-session-orphan stay green.
