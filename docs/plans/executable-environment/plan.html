Mission Control architecture plan

Executable environment and locator

One daemon-owned environment snapshot will decide which executable Mission Control detects and launches. Every successful answer is an absolute path with provenance and the exact child environment that produced it.

Approved by task brief   2026-09-04

Outcome and boundary

Tools are discoverable through explicit overrides, operator directories, inherited PATH, a bounded login shell, supported version-manager directories, or OS defaults. No recursive scan is permitted. Pi completion events, the work-queue bridge, and broader Pi RPC parity remain separate work.

Resolution precedence

  1. Tool-specific prefixed override, then retained raw legacy names.
  2. Declared absolute candidates, including terminal app bundles.
  3. Operator search directories.
  4. Inherited PATH.
  5. Login-shell PATH.
  6. Supported version-manager directories.
  7. Supported OS defaults.

Implementation

1. Foundation

Introduce the registry, versioned snapshot, provenance records, bounded shell probe, shared positive and negative caches, and focused unit coverage.

2. Detection and launch identity

Route harnesses, model discovery, terminals, Setup, pipelines, task sources, open targets, workers, updater, and general command execution through one contract.

3. Process boundaries

Initialize in daemon, Electron, and standalone Foreman entry points. Preserve the snapshot through child-specific security overlays.

4. Diagnostics and enforcement

Show path provenance in Setup, make Re-check force a refresh, and reject new undeclared literal subprocess commands in tests.

5. Verification

Run focused unit, integration, Playwright, Electron, typecheck, lint, build, smoke, and full-suite checks. Register final command and rendered UI evidence for the next Persona.
