Sizing and phase count

Estimated non-test implementation lines: Phase 1 ~200-250, Phase 2 ~120-160, Phase 3 ~130-170; total ~450-580. Three phases because each boundary isolates a distinct risk class in the repository's most safety-critical worker: Phase 1 changes what the verifier sees and claims (judgment and prompt-injection surface), Phase 2 changes when text is typed into live sessions (delivery safety), Phase 3 changes persisted-state keying (compatibility). Each leaves the repository operable and independently testable.

Cross-phase contracts

  • C1 (Phase 1): VerifyInput.registeredEvidence and the registered-evidence statement; daemon-generated metadata above the untrusted fence, child-authored display names, locators, and captions inside it. Zero items is stated as "clause not satisfied"; a nonempty list is a count only - coverage judgment stays with the verifier.
  • C2 (Phase 1): the additive gap kind unverified - "the change looks done; only proof of verification is missing".
  • C3 (Phase 2 entry point, Phase 3 keying): one daemon-owned recovery ledger; an attempt counts once per delivery from either route.
  • C4 (all): consume-before-type ordering, post-model-call candidate refresh, injection fencing, and the worker-never-touches-SQLite boundary.

Verification strategy

Each phase runs its focused suites plus npm run typecheck, npm run lint, and the full npm test before its pull request. No phase changes a UI surface, so no new e2e/ spec is required. The end state is validated by the worker-level tests named in the source plan's success criteria, spread across the phases that introduce them.

Investigated findings and the cross-phase audit record are in phased-plan.md, the authoritative Markdown source of this page. The phase files are the only place implementation detail lives; each stands alone for an agent arriving with nothing but its path.
