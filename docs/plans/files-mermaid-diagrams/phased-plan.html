Why this is one phase

The work crosses the Vite build, an isolated renderer, shared Markdown, Files Preview, styles, tests, and packaging. Those are one vertical behavior rather than independent layers. Splitting the renderer from its only consumer would land an unreachable foundation, obscure the end-to-end security proof, and force two reviews through the same contracts.

Repository findings that shape the route

  • The Files API already supplies Markdown text. No daemon or persistence work is required.
  • Markdown.tsx has ten callers, so diagrams must be an explicit, memo-safe capability that only FileWorkspace.tsx enables.
  • The existing HTML preview sandbox is a security precedent, not a renderer to weaken or overload.
  • Vite needs a second stable HTML entry. The daemon already serves built static files and Electron already packages all of dist.
  • The implementation must prove an opaque-origin script shape early. A classic renderer bundle is the fallback if module loading fails.
  • The Files preview's 5 MiB source allowance requires smaller browser limits: 50,000 characters per diagram and 32 diagrams per document.

Contracts the implementation must preserve

  • Shared Markdown remains code-only unless its caller explicitly enables fenced diagrams.
  • Only exact registered tags dispatch. Unknown, inline, excessive, and unsupported blocks remain readable source.
  • Generated SVG stays in sandbox="allow-scripts" without allow-same-origin, network access, active links, or parent-DOM injection.
  • Failures, timeouts, and stale results remain local to one diagram and cannot blank surrounding Markdown.
  • Editor is the exact-source editing and recovery path. Existing HTML preview, packaging policy, and generated-output rules do not change.

Verification bar

The phase owns unit coverage for dispatch, limits, sandbox messages, memoization, and stale state; a built-dashboard Playwright spec for valid, invalid, edited, and hostile diagrams; repository typecheck, lint, unit, build, smoke, and E2E gates; and packaged-Electron resource verification.

The phase task depends on this planning session. It remains backlogged until the planning pull request merges and these paths resolve on the default branch.

Audit result

The approved Mermaid-only requirements are owned exactly once by Phase 1. There is no deferred cleanup, consumer phase, database compatibility step, or multi-repository merge. Future engines must be proposed and reviewed separately.
