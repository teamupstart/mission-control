Findings that shaped the phases

Each of these contradicts or materially extends the source plan. They are the reason the phase boundaries are where they are, and they were verified against this checkout rather than assumed.

The corrections

1. The plan's cleanup design does not match anything in this repository. It says both tables are "cleared on session_remove and on no other signal." No table works that way. Every durable subscriber orphans or settles by UPDATE - orphanReviewsFor, reconcileTasksBoundTo, orphanBinding. Deletion is a separate throttled sweep against the live key set, gated on sweptSessions because absence is not evidence before the first completed sweep. And every subscriber has a second arm on onSessionsObserved for the daemon-was-down case. Session-scoped cleanup is three mechanisms, not one.

4. previewable does not mean "can take a comment" - it includes image. It also cannot be redefined: test/console-arrow-scroll.test.ts:41-42 asserts a literal source regex over that expression. Comment eligibility needs its own predicate.

5. A bare key cannot open a composer from inside the editor. The Files keydown handler bails on isTypingTarget, which returns true for anything contentEditable - which is CodeMirror's .cm-content. In-editor creation must be a CodeMirror keymap binding; the window chord only toggles the mode.

The rest

  • 2. A new table needs no migrate() entry. The schema is one db.exec() literal that runs on every open, before migrate(). The corollary is the trap: once shipped, a later column needs addColumn as well, so phase 1 declares the full shape up front.
  • 3. The table count lives in four places and only two are enforced. test/db-shell.test.ts:58 (75 → 77) and the per-family count are tested; the lede prose and the metric tile drift silently.
  • 6. The natural c chord is the global Complete-task action. Shadowing a global in-surface is established precedent - p and e already are - but Complete is heavier to shadow. Phase 2 owns the choice; m is the alternative.
  • 7. The MCP tool name must be a bare string literal inside registerTool(. The drift test scrapes /registerTool\(\s*"([a-z_]+)"/g, so a named constant breaks it.
  • 8. A tool that is not rebuilt never reaches an agent. Sessions run the gitignored dist/mcp/server.mjs. npm run smoke is what catches it.
  • 9. LINE_INPUT_EVENTS is a hand-maintained Set literal the compiler cannot check. The change contracts require an explicit decision plus a stated, pinned bound on any new collection.
  • 10. The Files tab exists only in the Console layout. Every spec must flip the layout and reload first. There is no shared dispatch() fixture; about 40 specs carry their own.
  • 11. A new buildApp dependency is appended last and its routes answer 503 when absent, because ~50 focused tests construct it positionally.
  • 12. Markdown has a memo comparator. A new prop absent from markdownPropsEqual is silently ignored.
  • 13. The HTML preview hash test hard-codes the script count and extracts with /<script>([^<]+)<\/script>/g, so a third bridge must update the count and contain no literal <.

Sizing

Estimated 3,000 to 3,900 gross non-test implementation lines, counting shared contracts, persistence, server, MCP, and browser code together. Assumptions: the anchor module is pure and compact; the three renderer integrations share no code beyond the anchor type; styles.css additions are counted; documentation and tests are excluded from the number but not from the work.

Why five phases and not fewer

The total is an order of magnitude past the 200-line one-phase threshold, so the only question is where to cut. Each boundary is justified by a merge boundary that materially reduces risk, not by layer:

BoundaryWhy not combined
1 → 2Phase 1 is durable state whose shape is expensive to change after it ships. Landing it against a route suite, before three renderers depend on its anchor type, is what keeps that type cheap to correct.
2 → 3Phase 2 ends with comments that persist and render but never send. That is the last point at which the feature touches no live agent.
3 → 4Phase 3 is a server state machine; phase 4 is an agent-facing tool with a build obligation whose failure mode is silent. They fail differently and are verified differently.
3 → 5Phase 5 is the only work touching the shared HTML preview sandbox, a controlled security module also used by Scouts. Worth reviewing alone, and it blocks nothing. It could stand on phase 2 alone; it waits on phase 3 for the anchor-survival measurement rather than for code.

Phase 1 is the largest at roughly 1,100-1,400 lines and is deliberately not split further: cutting it at the store/route seam would produce two pull requests that are each unreviewable without the other.

Dependency graph and concurrency

Cross-phase contracts

  • src/shared/file-comment-anchor.ts (Phase 1): the only definition of an anchor and the only re-anchor implementation. Browser-safe, no node: imports. Phases 2, 3 and 5 consume it; none reimplements it.
  • Both tables' full column shape (Phase 1), declared up front including columns phases 3 and 4 are first to write, so no later phase needs an addColumn.
  • status and outdated are two dimensions (Phase 1): outdated is a column, not a status value, because a thread whose quote stopped resolving keeps its place in the queue and the flag clears if the text comes back. orphaned is a status, and terminal. No later phase adds a status meaning outdated or a flag meaning orphaned.
  • appendFileCommentMessage (Phase 1): the only writer of a file_comment_messages row, for either author. Phase 2's reply box passes human; phase 4's MCP tool passes agent.
  • Session-scoped lifetime is three mechanisms (Phase 1): orphan on session_remove, a reconcile arm on onSessionsObserved, and a throttled prune of terminal rows. No later phase adds a fourth teardown path.
  • Two ServerEvent variants (Phase 1) are the only wire frames for this feature. Phases 3 and 4 emit them; neither adds a third.
  • Comment eligibility is its own predicate (Phase 2), never previewable.
  • One turn outstanding (Phase 3), on top of Phase 1's partial unique index over every outstanding status - sending and awaiting both, since a comment is outstanding until it is answered. Phase 4 changes what advances the queue, never how many are in flight.
  • respond_to_file_comments (Phase 4): the only agent-facing write, its name a string literal at the registerTool call site.

Final verification strategy

After phase 5, on a single branch: npm run typecheck, npm run lint, npm test, npm run build, npm run smoke, and npm run test:e2e. The smoke run is not optional here - it is the only check that proves the built MCP bundle actually publishes the new tool.

Then one manual pass a test cannot make: open a real spec in the Files tab, write six comments across three surfaces, run the walkthrough against a live session, and record how many of the six reached the head still anchored. That number is the measurement the two 60% assumptions in the source plan need, and phase 3 is where it is taken - before phase 5 is scheduled.
