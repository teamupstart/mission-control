Workflow pipeline UI

Migrate the Workflows builder and runs monitor to the stage-based pipeline design (review mockups B and C, 2026-07-25). Authoring becomes "stages of reviewers"; a run is watched on the pipeline its author drew. Graph storage, publish, engine, bindings and deliveries keep their shape; the one semantic change lifts the one-submitted-route restriction so a first stage can hold parallel reviewers.

Implements the recommendations of the 2026-07-25 workflow feature review (fan-out refusal reproduced live; UUID vocabulary; 8 hand-drawn edges for a 2-reviewer workflow; unthemed canvas chrome; jargon empty states).

Why

  • The validator (src/shared/workflow-graph.ts:170) requires exactly one submitted edge, so the all-pass Join's headline case - N reviewers in parallel on the submission - cannot be authored at all. The engine already fans out (one durable receipt per outgoing edge); the cap is validator-only.
  • Every legal workflow today is "Session, then waves of reviewers, then End, with every fail returning to Session". The canvas makes operators hand-draw that grammar and then polices misses with codes. A stage editor makes the grammar unrepresentable instead of policed.
  • The runs monitor is a wall of stacked sections naming nodes by UUID. Operators think in the pipeline they authored; the run should be displayed on it.

Goals

  1. Parallel first-wave review: N reviewers in stage 1.
  2. Authoring is stages; joins, fail routes, return edges and reachability are generated.
  3. The runs monitor replays a run on the pipeline: live status, verdict cards, round scrubber, timeline - all current data, none of the UUIDs.
  4. Human vocabulary everywhere; machine codes demoted to detail affordances.
  5. No storage migration; published versions stay immutable; existing drafts keep working.

Non-goals

  • Mockup A's full canvas restyle (the Graph view stays a co-equal fallback editor but only inherits shared vocabulary work).
  • Engine, delivery, binding, Inspector-gate or persona-editor changes beyond the validator rule.
  • New run capabilities; the monitor re-presents existing detail data.

Design

Stages are a projection, not a second model

The persisted model stays WorkflowDraftGraph / published graphs. A new browser-safe module src/shared/workflow-stages.ts owns:

  • projectStages(graph) - the stage pipeline a graph expresses, or null when the graph is not stage-expressible.
  • compileStages(pipeline, previousGraph) - emits a graph, reusing node and edge ids wherever the same stage member survives so autosave diffs, undo history and version comparisons stay stable. Positions are generated deterministically.
  • stageExpressible(graph) and nodeLabel(node, personas) - the shared vocabulary helper adopted by every surface.

Stage-expressible: one Session; a linear chain of stages; a stage is one Persona (pass onward, fail to Session) or N Personas plus one all_pass Join (every member's pass and fail into the Join, Join pass onward, Join fail to Session); one End; nothing else. Round-trip invariants are pinned by tests.

The editor never mutates edges directly - every pipeline edit compiles and hands the graph to the existing useWorkflowDraft.update, so CAS autosave, conflicts, undo/redo, publish and versions behave exactly as today.

The validator change

session_submitted_route relaxes from exactly-one to at-least-one (zero still errors). The engine gains a test proving N submitted edges activate N personas in parallel; the fan-out sentence in docs/plans/workflow-builder/phase-2-builder-publishing.md and test/workflow-graph.test.ts are updated in the same change. Compatibility: published versions are immutable and older engines execute fan-out correctly; only re-publishing a fan-out graph on an older build would refuse.

Pipeline editor (mockup B)

  • PipelineEditor.tsx rendered by WorkflowLibrary when the draft is stage-expressible; a Pipeline | Graph toggle switches surfaces, defaulting to Pipeline when expressible and Graph otherwise with a banner naming exactly why.
  • Session and End as fixed termini; stages between; seams carry the "all pass" gate mark and an insert-stage affordance. Stages list reviewers with an inline Add reviewer picker, per-reviewer remove, and drag or keyboard reordering.
  • Destructive removals confirm through an overlay-hosted modal, not window.confirm.
  • Right rail: workflow settings (stale "(Phase 4/5)" labels removed), sentence-first validation, version history, and a working "Bind to a session..." call to action.
  • Accessibility parity: roving focus, announcements in persona names, new keys registered in ACTIONS and the README keyboard table.

Runs monitor (mockup C)

  • Rail with tone chips and filter chips (All, Running, Needs you, Done) over the existing status filter; session branch and relative time per run.
  • Header keeps every contextual action: Export, Cancel, Resubmit, Retry provider call, Prepare PR, Recheck Inspector, Restart all Personas.
  • Round scrubber over detail.submissions; scopes strip, verdicts and timeline.
  • Pipeline strip: projectStages(version.graph) plus the existing workflowNodeStatuses(detail) drive per-reviewer status chips. Non-stage-expressible versions fall back to today's read-only canvas with statuses.
  • Verdict, Inspector-gate, completion-claim and delivery sections restyled into the fleet card grammar, keeping all recovery machinery (uncertain deliveries, retry, resolve).
  • Empty state gains the "Bind to a session..." button, replacing the jargon sentence.

Phases

1

Model groundwork

Validator relaxation + engine fan-out test + workflow-stages.ts (projection, compiler, expressibility, nodeLabel) with round-trip, id-stability and taxonomy tests. No UI change; ships green on its own.

2

Pipeline editor

PipelineEditor.tsx, the Pipeline | Graph toggle, overlay confirm modal, right-rail updates, vocabulary adoption in the Graph view's panels, keyboard registry + README.

3

Runs monitor

The WorkflowRuns rebuild: rail, header actions, round scrubber, pipeline strip with statuses, verdict/gate/delivery cards, timeline, bind CTA, canvas fallback.

4

Cleanup and settings placement

Remove obsoleted strings and affordances; move the Workflow settings drawer into a Settings page category registered in SETTINGS_CATEGORIES, with the Workflows page linking to it.

Each phase updates the README in the same change and lands its tests. Suites expected to change: workflow-graph.test.ts, workflow-builder-*; new: workflow-stages.test.ts, workflow-runs-render.test.ts.

Risks

  • Projection round-trip subtleties. Id stability across edits is the hard invariant; getting it wrong breaks undo or manufactures CAS churn. Property-style tests land before any UI.
  • Almost-expressible graphs open in Graph view; the banner must say precisely what blocks projection or it reads as a bug.
  • Runs parity. Inventory the current reader's recovery affordances first so none are dropped silently.
  • Cross-build re-publish of fan-out graphs fails validation on older builds; acceptable for a single-operator tool, noted in the README.

Adopted decisions (submitted 2026-07-25)

1 · Session fan-out rule

Relax to at-least-one. The engine is ready and stage 1 parallelism depends on it.

2 · Graph view's role

Co-equal fallback editor. Pipeline is the default for stage-expressible graphs; the canvas still edits anything, so no migration pressure.

3 · Stage naming

Derived names only. No model change.

4 · Workflow settings placement

Migrate into a Settings page category in phase 4. Restores the registry convention and settings-search coverage.

5 · Follow-up

Create the phased implementation plan. Phase documents beside this plan plus dependency-linked Mission Control tasks.
