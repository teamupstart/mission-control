Mission Control · issue #1116 · mockups

A persistent “working” indicator near the bottom of the chat

Today the only live signal that a session is moving is InProgressRow, drawn at the tail of the transcript (TranscriptPanel.tsx:1479). It says the right thing and it scrolls away: read three turns back and the one element that answers “is this still going?” is off screen. Five ways to fix that - four single moves and the combination that was chosen, Option E - all reading the same signals, all costing nothing while the session is idle.

Every frame below is the real conversation geometry: the log, the 184px secondary rail (244px in the app), and the composer row whose Send sits on the edge the rail shares with it. Colour, type and radii are the shipped tokens.

What any answer has to respect

  • Zero cost when idle. ConsoleDetail.tsx:800 records a rejected activity band above the conversation: it “cost the conversation its height whether or not anything was running, and described the present at the top of a pane whose present is at the bottom.” None of these draw anything on an idle session.
  • One signal, not a second cache. The gate is liveActivity(session) (src/shared/session.ts), already shared by the board tile and the in-progress row: it answers only while the session is instrumented and actually driving work, so a settled session's stale activity label is never animated.
  • Working vs stalled is the actual ask. session.lastActivity is the epoch ms of the last hook, report or driver event. Past a threshold the indicator should stop claiming progress and say the signal has gone quiet, in --attention, rather than spinning forever.
  • Two renderings. The chat frame and the terminal frame (.transcript[data-view="terminal"]) both need it. The frames below show chat; each option notes its terminal treatment.
  • Copy discipline. The Observed-activity rail's rule is that a row means a record was observed, never that a tool is running. The indicator is a different claim - a live report from the session - so it says what the agent reports it is doing, and the elapsed number is time since the turn began, not a duration for a tool.

Today

baseline

The in-progress row exists, and it is the last thing in the log. Scroll back to re-read what you asked for and it is gone; the composer below tells you nothing. Both frames are the same working session, one second apart, differing only in scroll position.

The defect, precisely: the only live element in the pane is bound to a scroll position. The Observed-activity rail is not a substitute - by its own contract a row there means a record was seen, not that anything is running now.

Option E · The pinned status row, plus a loading bar on the reply box

chosen

The combination: D's row - the one the log already draws - pinned to the bottom edge of the transcript so it survives any scroll position, carrying the current status, a spinner and an elapsed clock; and C's 2px indeterminate bar along the top edge of the reply box. Two marks, one claim, and they answer at different distances: the row says what is happening, the bar says something is happening and is visible in peripheral vision from across the room.

Nothing new is invented above the composer and nothing is duplicated. At the bottom of the log the row is simply the last line, exactly as today.

As built

  • The clock is the base experience. Every working row carries how long the current turn has run, counted from the prompt that started it, with nothing to switch on.
  • The two marks are opt-in Display items, under Settings → Display → Session display → Working indicator, with a live preview beside them: Pin the working row and Reply box progress bar. Both ship unchecked, so with neither checked the conversation is what it was, plus the clock.
  • Queue ordering needed no change. A row pinned by its own overflow has every queued turn after it below the fold too, so the pin never covers the queue.
  • The quiet-signal amber below was not built. A long tool call sends no hooks while it runs, so "quiet for 3m" would flag a healthy npm test. The clock says how long the turn has run and leaves the judgement to the reader.

The two marks are one state, and they are driven by one predicate. Both mount on liveActivity(session) and both take the amber treatment past the quiet-signal threshold, so there is no arrangement where the bar sweeps while the row says the session has gone quiet.

Idle cost

Nothing, and no reflow either: the row only exists while a turn runs, and the bar is a class on the reply box that is already there.

Terminal frame

The row already takes .pty-entry. The reply box has no border there, so the bar rides the top of the prompt line instead.

To settle in implementation

Queued turns render after the in-progress row on purpose; the sticky row has to sit below them, or fold the count in (“Editing styles.css · 2 queued”). And the elapsed clock needs a turn-start timestamp - lastActivity is the last event, which is what the stale rule reads.

loudest

One full-width row between the log and the reply box, mounted exactly while liveActivity() answers. It carries the live report, an elapsed clock, and a Stop affordance - the thing you most often want the instant you notice a session is still going. Idle, the row does not exist and the log reclaims its height.

Side by side

OptionGlanceableReflowCan carry Stop / elapsedSpec + CSS surface
A · strip Highest - a full-width band in the fixed footer region ~28px in and out per turn Yes, both New component, new block, one e2e spec
B · pill High - centred and floating, but narrow None Elapsed yes; Stop crowds it New component, overlay geometry, scroll-position state
C · composer Lowest - a 2px sweep and a dim line None Elapsed yes; Stop no Classes on existing chrome; smallest visual footprint
E · D + bar ● High - a log-type line that never leaves, plus a bar readable from across the room None Elapsed yes; Stop no One CSS block plus classes on the composer; queue ordering to settle
D · pinned row Medium - log type, inside the scrollport None Elapsed yes; Stop no One CSS block; queue ordering to settle

Chosen: E - the current status in D's pinned row, with a spinner and an elapsed clock, and C's loading bar on the top edge of the reply box. It reaches glanceability the way A does without A's reflow, because neither mark takes layout height: the row already exists in the log and only changes how it behaves when you scroll away from it, and the bar is a class on chrome that is there whether or not a turn is running. The cost it does carry is A's Stop button, which stays where it already is.

Open question for whichever wins. The elapsed clock needs a turn-start timestamp. session.lastActivity is the last event, which is what the stale rule reads; turn start has to come from the transcript's last user turn or from workCycle. Worth settling before implementation rather than during it.
