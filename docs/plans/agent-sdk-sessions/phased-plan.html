Repository findings that shaped the phases

  • The seam exists: ControlSpec's unimplemented stream-json variant, controlFor(session), two tested refusal sites (actions.ts:909, :970).
  • Sessions are discovered, never registered: applyDiscovery is the registry's only entry; SDK subprocesses have no tty, so phase 1 adds a registration path and scopes eviction.
  • Restart ordering point: supervisor restore must complete before startPoller(registry) (src/server/index.ts:140).
  • canWriteTo operates on PaneHandles (Session AND DiscoveredSession); canMessage takes PaneHandles & { runtime }, so only Session-shaped call sites move.
  • Settings surface is settings-registry.ts + SettingsPage.tsx + HarnessesPanel.tsx (AGENTS.md's SettingsModal reference is stale); the toggle lands in the existing Harnesses cards over the existing HarnessesConfig blob.
  • No harness/claude/launch.ts exists; the SDK branch composes from the same inline dispatcher inputs the terminal path uses.
  • PaneDialog already ships to the browser; optional extensions are wire-compatible.
  • Foreman is HTTP-only; everything it needs arrives via existing routes or the Session payload.
  • PR provenance requires authorship evidence; the driver's pr_created event feeds the same rule.
  • Binary resolution and packaging: adapters pin subprocesses to resolveAgentBin; phase 2 owns the SDK dependency surviving the esbuild bundle and electron-builder allowlist.

Cross-phase contracts

C1 (P1) - the runtime axis: SessionRuntime, Session.runtime (comparator byValue), sdk:<uuid> ids, NameSource "sdk". Branch on runtime, never on an id prefix.
C2 (P1) - canMessage vs canWriteTo; the phase 1 call-site table is exhaustive; no surface re-derives either.
C3 (P1 shape, P2 answering) - PaneDialog optional source/requestId/kind/questions; {number, label} answers verified by optionRowMiss on both runtimes; forms answered with the full answers map.
C4 (P1) - SdkSpec family, Harness.sdk, pure runtimes capability, agreement pinned by test; adapters built over an injectable transport seam.
C5 (P1) - registerSdkSession / applyDriverEvent; eviction scoped to terminal sessions; restore before first sweep; bound fills identity and sets instrumented/stateConfirmed/hooksSeen, keeping the file-based read path and instrumentation gates working.
C6 (P2) - sessionRuntime config (default terminal, unknown values fall back and report) + resolveDispatchRuntime gated on the declared driver; panel-only control.
C7 (P2) - one dispatch branch after identical worktree provisioning; no home, no hook wait; supervisor answers task liveness true/false.
C8 (P2) - handoff: graceful stop + terminal home on the harness's resume argv; decorations follow noteKeyFor.
C9 (P3) - promptHarness.runtime, answer.form, queue over acked send with no pane-uncertainty arms, runtime-aware foremanAutomationAuthorized (phase 6 relies on it).
C10 (P4) - one app-server subprocess per session; committed generated bindings pinned to the binary; protocol spoken only in the adapter.
C11 (P6) - pi RPC JSONL (LF-only framing), extension_ui_request → C3, new_session as clearContext, work-queue revisit on C9's arm.

Merge order and final verification

Merge 1 → 2 → (3 ∥ 4) → (5 ∥ 6). After phase 5: dispatching Claude and Codex with the toggle on runs end to end (dispatch → structured asks answered from the card and by Foreman → queue → wrap-up → PR adopted) with zero keystroke writes; with the toggle off the terminal path is byte-identical to today. After phase 6 the same holds for pi. Defaults remain "terminal" everywhere - flipping them is an operator act in settings. Every phase leaves CI green (npm run typecheck, npm test, npm run build, bundle smoke) on Node 24 and 26.
