Ensemble UX: the operator journey, its gaps, and three directions

Status: direction approved 2026-07-26 - phased composition (Section 8) · Source of truth: docs/plans/ensemble-ux-gaps/plan.md
Basis: full read of src/web/ensembles/*, the Workflows-page ensemble surfaces, src/server/ensembles/*, docs/ensembles.md, and the 31 test/ensemble-*.test.ts files.

1. The journey today, start to finish

1.1 Launching a run

The entry point is the Dispatch modal. A Single | Ensemble switch (new dispatches only - an existing backlog Task cannot be converted) swaps the form for the ensemble dispatch: strategy segments (Best of N, Consensus, Panel vote), a roster of 2-5 candidate lanes (agent, model, effort, approach nudge), an optional evaluator Persona, judges for panel vote, an optional Workflow for the winner. A "Launch plan" strip previews the shape. Launch is two-step and idempotent: Review launch posts a side-effect-free preview whose fingerprint any edit invalidates; Launch N agents creates the run and navigates to the run detail. solid

1.2 Tracking progress

Two loosely stitched places. The run detail (Workflows page → Ensembles tab → run) shows a status pill, a facts list (Members N / M max, Active stage as the raw activeStageId string, base sha, elapsed, concurrency, review cost, candidate cost), member cards grouped by wave with attempt/artifact histories and a "Reported by member" vs "Observed" split, and a timeline of stage attempts, evaluations, decisions and raw events. The fleet shows each member as an ordinary session with a small ensemble mark ("⧉ Best of N · working" chip, E 2 · working tile flag, a bare E in the rail). Nothing groups siblings; the run list row is just strategy · status word · time. thin

1.3 When a member needs the operator

A member's blocking question travels the ordinary session channels (request_input → ReviewModal; TUI/SDK dialog → pane prompt on the card). The session tone flips to attention. Nothing on the ensemble side changes: no member status for it, the run summary's attention ignores it, the run detail keeps saying "Active", the chip keeps saying "working". The two views disagree about the same agent. broken

1.4 The decision

At ≥ 2 ready snapshots the anonymous comparison runs and the run parks at awaiting_decision with one toast. The strategy result renderers are genuinely strong: ranked scorecards with score, confidence, strengths, risks and rationale (Best of N); aggregate ranking, Contested marks, a disagreement figure and full per-judge ballots (Panel vote); agreements and divergence questions (Consensus); each with a guarded decision form. What is missing is the material to check the judges against in one place: diffs are one-at-a-time in Artifacts, claims are in Members, scores are in Result - three sections correlated by hand. good bones, scattered

1.5 After

Finalization verifies the winner ref, restores or materializes the winner, reaps loser worktrees (never refs), runs the handoff, completes. Artifacts stay inspectable (Show diff) and restorable (Reset checkout). A decision is one-shot by design; Delete is typed-id-confirmed and irreversible. solid

2. Gap catalog

Group 1 - "Where is my ensemble?" (fleet visibility and orientation)

G1Member sessions are never grouped. Five siblings scatter through the grid, rail and Board tone columns like unrelated work; the only tie is a small chip, and on the Board they can land in three different columns. There is no way to see "the ensemble" as a unit in the fleet. GridView / BoardView / ConsoleView have no ensemble input; groupByTone knows nothing of runs.
G2The live summary is broadcast but unused. EnsembleSummary carries readyArtifacts, launchedMembers, memberCount, outcomeKind on every upsert and no web surface renders any of them. "3/5 submitted" exists on the wire and nowhere on screen (except one tooltip). useEventStream.ts, EnsembleRuns.tsx list rows.
G3The marks are state-poor. Rail: a bare E. Tile: E 2 · working. Chip: "⧉ Best of N · working" - even while that member's card is red with a waiting question. No run status, no progress, no blocked signal. session-bits.tsx:238-380, ensembleMemberStateLabel.
G4No persistent "a run needs you" indicator. awaiting_decision fires one toast; the Ensembles tab has no badge; the topbar has no ensemble chip. Miss the toast and the decision sits silently. A failed run is info-severity (deliberate) which compounds into "failed overnight, discovered by accident". useNotifier.ts, shared/alerts.ts:428-495, WorkflowPage tab.
G5The feature's home is another feature's page. Ensembles are a tab on the Workflows page; launch is discoverable only via the Dispatch mode switch (the list's empty-state sentence is the sole cross-reference). "Workflows → Ensembles" invites conflating two engines the architecture keeps deliberately separate. WorkflowPage.tsx, useWorkflowRoute.ts.

Group 2 - "What is it doing right now?" (progress comprehension)

G6Stage progress is spelled in internals. The header prints stage-2-review in a <code>; the timeline names driverKeys (comparative_review@1) and commandKeys. No humanized pipeline, though the compiled plan's driverKind sequence expresses launch → work → review → decide → promote strategy-agnostically. EnsembleDetail.tsx facts, EnsembleTimeline.tsx.
G7waiting is never explained. Barriers (members_settled{minEligible:2}, stages_succeeded, human_decision) are not translated into "waiting for 2 more submissions" or "waiting on you". engine.ts barrier evaluation; nothing projects it.
G8Member cards are records, not live views. No current-activity line, no goal line, no per-member elapsed, no live cost. Seeing what a member is doing means Open session and losing the run context. EnsembleMembers.tsx; report_status reaches only the session card.
G9A stalled-but-live member is invisible. deadlineMs is null in every shipped strategy; there is no member-level idle/stall signal. A wedged agent shows "Active" forever; the levers are withdraw or wait. engine.ts enforceDeadline is the sole timer.
G10Observed model never lands. observedModel() returns null unconditionally ("a later phase"), so member cards show only the configured model. member-launch.ts:75.

Group 3 - "Someone needs me" (blocking questions)

G11A blocked member does not exist in the ensemble vocabulary. No member status, no summary field, no run attention, no event. ensembleNeedsAttention reads only {status, unreadable}. A member's pending review does not revise the run row, so the detail does not even refetch - an operator watching the run will never learn a question exists. shared/ensemble.ts:1260; member statuses tuple.
G12Answering requires leaving. The question is answerable only on the member's session surface, found via the needs-you column or the topbar reviews chip. The run detail offers no path to it and no inline answer surface. ReviewModal.tsx, PaneDialogPrompt; zero ensemble references in either.
G13The answer surface hides the ensemble context. The reviews chip and modal never say "this session is candidate 3 of 5 in run X". The operator cannot tell they are steering one competitor of a comparison - relevant for fairness and for deciding whether to answer or withdraw. App.tsx topbar chip, ReviewModal.tsx.

Group 4 - "Which one is better, and why?" (comparison and judge reasoning)

G14No side-by-side anything. Diffs are one-at-a-time expandable rows stacked vertically; no two-pane diff, no file-touch matrix, no diff-of-diffs. EnsembleArtifacts.tsx.
G15Evidence is anchored to whole artifacts. A scorecard's Evidence button scrolls to the artifact row; "B missed the migration" cannot be checked against the file it names without hand-searching the patch. BestOfN.tsx / PanelVote.tsx Evidence → openArtifactId.
G16The comparative material is scattered across three sections. Claims + observed stats (Members), scores + rationale (Result), diffs (Artifacts) - nothing composes one row per candidate: summary, diffstat, checks, cost, score, rank, confidence. EnsembleDetail.tsx section stack.
G17The decision is one-shot and the record is passive. Scorecards and ballots persist, but there is no post-hoc comparison workspace, and the fact that loser refs survive (restorable work) is discoverable only by knowing what Reset checkout does. decide() expectedStatus; EnsembleOutcome.
G18Judge disagreement is listed, not shown. Panel vote has the pieces (disagreement figure, Contested tags, rank strips, full ballots) but no at-a-glance judges × candidates matrix and no surfaced dissent. Understanding why the panel split means opening every ballot. PanelVote.tsx ballots section.

Group 5 - lifecycle edges that surface as UX confusion

G19No path from an existing Task to an ensemble. The mode switch renders only for new dispatches; a backlog task must be retyped to fan out. DispatchModal.tsx (!editing guard).
G20manual is the only source kind. No agent-initiated or scheduled ensembles; bounds the stories the UI can serve. ENSEMBLE_SOURCE_KINDS.

3. One prerequisite shared by every direction

Whichever direction is chosen, the blocked-member signal must reach the wire. The fix is a derivation, not a new persisted status (the member status tuple stays append-only): where session state and the task link meet - the EnsembleManager, which holds both the store and the registry (verification showed the store is DB-only and the registry deliberately store-independent, so neither can host the join; see phase-1-blocked-member-wire.md) - fold "this member's session needs input" into the published projections:

  • EnsembleSummary gains membersNeedingInput: number (and attention ORs it in),
  • TaskEnsembleLink gains needsInput: boolean so every chip/flag/mark can say it,
  • the detail already refetches on summary revisions, so publishing on the review/dialog edge updates it for free.

One derived field in two shared shapes plus a publish edge. No new event type, table, or Session field; the extension contract (no strategy branch, no new route family) is untouched.

4. Solution A - "Fleet Lens"

Thesis: the operator already lives in the fleet. Make the ensemble legible where they already look, and keep the run detail as the deep-dive it is.

  1. Ensemble clusters: member cards render as a visible group with a slim header (title, strategy, humanized stage word, progress dots, cost, attention rollup) that deep-links to the run. (Superseded detail - phase-3-fleet-lens.md is authoritative: grid arrow-nav is geometric, so the grid gets adjacency sorting only and no frame; Board clusters never cross tone boundaries - a blocked member sits in the attention column with the header repeated.) The console rail gets a section header per run.
  2. State-rich marks: the chip becomes stage- and state-aware ("⧉ Best of N · reviewing · 3/5 in", or an attention-toned "⧉ needs an answer"); the rail's bare E gains tone; tiles carry E 3/5.
  3. Progress where the summary already is: an attention badge on the Ensembles tab, progress dots + counts on run list rows, a topbar ensembles chip when any run needs attention.
  4. Humanized stage vocabulary: one shared function maps driverKind to operator words (launching, working, reviewing, waiting on you, promoting, done), used by clusters, chips, rows, and the detail header.

5. Solution B - "Run Console"

Thesis: the run detail becomes a command center the operator can stay in: humanized pipeline, live member lanes, questions answered inline, and a real comparison workspace. The fleet changes minimally.

  1. Stage pipeline header derived from the compiled plan, each step with state and counts; waiting names its barrier.
  2. Live member lanes: session tone, the report_status activity line, goal, elapsed, live cost - and a blocked member's question rendered inline in its lane (reusing ReviewCard / DecisionForm / PaneDialogPrompt and the existing resolve routes), labelled "candidate 3 asks:".
  3. Compare workspace: pick 2-3 ready artifacts → side-by-side columns over a shared file-touch matrix, synchronized per-file diff panes, and a claims strip per column (summary, checks, cost, then score/rank/confidence once the review lands). Rationale text that names a path links into the matrix row.
  4. Judge reasoning panel: a judges × candidates rank matrix with contested cells and surfaced dissent above the full ballots.

6. Solution C - "Attention Inbox + Decision Dossier"

Thesis: the operator's obligations are exactly two - answer a member's question, and make the final call. Build the best surface for each; keep ambient monitoring light.

  1. Attention inbox: the topbar reviews chip generalizes into one queue - member questions labelled with run context, decision requests, parked finalizations, gate decisions - answerable inline or by deep link. Nothing depends on catching a toast.
  2. Decision dossier: at awaiting_decision the run leads with an "At stake" header (intent, base, elapsed, spend), one column per candidate (summary, diffstat, checks, cost, score, rank, strengths/risks, expandable diff), a judge-reasoning band (rank matrix, consensus statement, dissent quotes), and the decision form last. After the decision it persists read-only as the "why we picked B" record, with Restore beside each losing column.
  3. Run strip on member cards: one line under the title - "⧉ Best of N · candidate 3/5 · run: reviewing · 1 sibling blocked" - orientation without touching Board layout.

8. Adopted decisions (2026-07-26)

Where this section and a phase file disagree, the phase file wins. The phase documents beside this plan (phase-1-*.md ... phase-6-*.md, indexed by phased-plan.md) were written after repository verification and record explicit reconciliations against this design record: the blocked-member join lives in EnsembleManager (not the registry or store), the grid gets adjacency sorting (never a frame), Board clusters never cross tone boundaries, and Phase 3 builds no topbar chip (the topbar surface belongs to Phase 4's inbox). Each reconciliation is logged in the owning phase's cross-phase audit record.
  1. Direction: phased composition. Build in this order, each phase shippable on its own:
    • Phase 0 - wire prerequisite (Section 3): derive membersNeedingInput into EnsembleSummary and needsInput into TaskEnsembleLink at the registry join; run attention ORs it in.
    • Phase 1 - Fleet Lens (Section 4): ensemble clusters, state-rich marks, tab badge + topbar chip, shared humanized stage vocabulary.
    • Phase 2 - Attention Inbox + Decision Dossier (Section 6): the unified attention queue and the decision-time dossier with rank matrix and surfaced dissent.
    • Phase 3 - Run Console (Section 5): live member lanes with inline question answering, the stage pipeline header with barrier explanations, and the compare workspace.
  2. The wire prerequisite ships first, regardless - it is Phase 0, so chips and list rows can use it immediately.
  3. Compare surface v1 is the full build: file-touch matrix plus synchronized side-by-side diff panes, requiring a per-file cut (?path=) of the byte-bounded patch route.
  4. Follow-up: a phased implementation plan with merge-aware phase docs and dependency-linked tasks.
