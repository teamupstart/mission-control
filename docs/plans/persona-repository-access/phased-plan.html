Execution model

Each enabled Persona runs once in an isolated workload. Claude or Codex repeatedly calls a local stdio repository MCP server, then returns one structured verdict. The MCP reads a portable immutable snapshot. Repository bodies stay inside the workload; Mission Control receives ordered lifecycle events, safe audit metadata, and the verdict.

The earlier daemon-side broker plan is obsolete. Its three implementation tasks were cancelled before code landed.

Gross implementation estimate

4,800-6,200 LOC

Production code added or materially changed. Tests and documentation prose are excluded.

Critical feasibility gate

Phase 1 must prove that both installed provider paths can make multiple calls to one workload-scoped MCP server, preserve images, disable direct tools, and return a structured verdict. If either provider fails, implementation stops for operator review.

Repository findings that shape the graph

  • Built-in Personas are generated application data, not database rows, so local access needs a narrow sidecar override.
  • Publication currently reuses a version by draft revision before resolving Persona snapshots, so access-only edits need a canonical graph fingerprint.
  • Stable Workflow capture is the only safe checkout boundary; a clean detached check lease cannot represent staged, unstaged, and untracked state.
  • Workflow capture now resolves a checkout per repository run and validates external artifact expectations before raw-context persistence. Artifact candidates bind to that checkout and are promoted only after the existing capture guards pass.
  • Reserved image/text evidence and evidence-readiness policy remain independent. A repository artifact enables queries and cannot satisfy criterion-mapped evidence.
  • The general headless LlmRunner has no MCP descriptor and must remain tool-less. Full session adapters provide the provider-specific launch patterns.
  • Mission MCP includes task tools and credentials, so repository MCP is a separate bundle with no daemon credential.
  • A normal Git bundle would include sensitive reachable blobs. The portable artifact must be a sparse object set that preserves commit/tree identities but omits denied blob bodies.
  • History pagination cannot define artifact retention. RepositoryHistoryPolicyV1 retains one deterministic all-parent prefix capped before 2,048 commits or 512 MiB of additional allowed historical blobs.
  • Workflow events and LLM calls are already paged. Query audits need an independent bounded page and compact summary.
  • Evidence has eight stable quote/path/line-shaped kinds. Repository handles append one protocol-gated discriminated-union branch without changing any existing identifier or wire shape, and their daemon-owned metadata preserves exact line, byte, or diff ranges.
  • Imported and plugin-managed Personas carry provenance. New imports default access to none, while reimport and synchronization preserve operator-owned access.

Why exactly three phases

  • Phase 1 proves the load-bearing provider mechanism before durable state lands.
  • Phase 2 isolates Git fidelity, sensitive omission, and crash-safe deletion.
  • Phase 3 is one vertical behavior slice, preventing a visible setting that does nothing.
  • No test-only, docs-only, cleanup-only, or UI-only phase is added.

Artifact security resolution

  1. Preserve original commit/tree ids and exact layer ids.
  2. Include only allowed blob bodies.
  3. Record denied paths and object ids in the manifest without content.
  4. Pre-authorize literal paths before every content-producing Git invocation.
  5. Disable external diff, text conversion, filters, hooks, fetching, and network.
  6. Own shared bytes by digest and delete them only after atomically releasing and rechecking the last submission claim.
  7. Digest the ordered retained revisions and frontier metadata; deny outside revisions as revision_out_of_range. For retained revisions, patch a true root against the empty tree, patch a non-root only against a retained recorded first parent, and otherwise return history_boundary with no patch. Mark frontier log/blame truncation.

Final compatibility audit

  • All twelve required design areas have one explicit owner and all consumers follow direct or transitive prerequisites.
  • Access-off behavior retains the historical prompt, provider options, fingerprints, and verdict path.
  • Read-enabled attempts never reconstruct from the live checkout or degrade to prompt-only review.
  • Shared artifact bytes survive release of any submission claim until the final active claim is atomically released and cleanup rechecks zero references.
  • History selection is deterministic at both ceilings; in-range queries work after source removal, and boundary or out-of-range behavior is provider-neutral and auditable.
  • Repository bodies stay inside the workload; SQLite, logs, exports, SSE, and browser receive safe metadata only.
  • Repository evidence references contain only operationId and opaque evidenceHandleId; daemon-owned metadata proves the exact returned path and discriminated line, byte, or diff range without storing quotes or excerpts.
  • Materialization is bound to the active submission, workload, and Workflow attempt before artifact paths are opened.
  • A crash before candidate promote/discard cannot leak unbounded snapshots: startup removes only contained pending entries with a valid atomic daemon marker, and quarantines malformed or unowned paths.
  • Mixed-version read-enabled dispatch fails before provider launch or durable verdict write; rollback after repository citations restores the verified pre-migration database recovery point.
  • Built-in overrides affect future operator-published versions, never shipped built-in versions.
  • The local executor is a conformance implementation for a future remote adapter, not a hidden selection of remote infrastructure.
