Agent SDK sessions

Migrate dispatched Claude and Codex sessions from keystroke-driven terminal panes to their vendors' programmatic interfaces - the Claude Agent SDK and Codex's app-server protocol - behind a shared per-session runtime abstraction, selected by a settings toggle, with no new agent ids and no change to sessions an operator starts themselves.

The plan answers three questions: what would we lose (Tradeoffs), what is the abstraction (Architecture), and how do we cut over and deprecate (Phases). All five open choices were decided from the Mission Control dashboard on 2026-07-24 - see Resolved decisions. The README owns the current runtime-specific dispatch contract.

Terminal-path baseline for this plan

Four choke points carry every write to a session, and one parser carries every structured read:

  • injectPrompt / sendText (src/server/actions.ts) - paste, settle 400ms, Enter, verify against a paste placeholder the harness may not render (submitVerified: false for Codex and pi).
  • selectPaneOption / submitPaneForm - answer a menu by walking the cursor row by row, re-reading the pane after every keystroke; multi-select forms tick checkboxes and walk to a Submit tab, refusing on an "unanswered" banner.
  • parsePaneDialog (src/server/discovery/pane-dialog.ts) - the harness-neutral screen grammar with per-harness tokens in DialogSpec.
  • The 1.5s discovery sweep - sessions exist because ps found a process on a tty; identity is proc:<tty>:<pid>:<startMs>.

The seam for this migration already exists and is deliberate: ControlSpec (src/server/harness/types.ts:434-476) declares { kind: "stream-json" } with zero implementations, controlFor(session) takes a Session rather than an AgentType precisely so "the delivery path asks the SESSION how to talk to it", and exactly two call sites refuse the unimplemented variant by name (actions.ts:909, :970). The pluggable-integrations plan calls this "the seam that makes headless dispatch possible later". This plan is that later.

Research findings

Claude: the Agent SDK (@anthropic-ai/claude-agent-sdk)

The TypeScript SDK spawns the claude CLI as a subprocess and drives it over the stream-json control protocol. Everything the pane path scrapes arrives structured:

  • Sessions: streaming input holds one process across many turns; interrupt(), resume, forkSession. Session files land in ~/.claude/projects/ - the same storage the interactive CLI uses, so an SDK session can later be resumed in a terminal (claude --resume <id>) and vice versa.
  • Permissions: canUseTool(toolName, input, {suggestions}) is called for anything the mode does not settle; the caller answers allow / deny / allow-with-updated-permissions. setPermissionMode and setModel work live.
  • AskUserQuestion (the multi-select case): arrives as a canUseTool call carrying questions: [{question, header, options, multiSelect}]; the answer is an answers map, with free text supported. No tabs, no checkboxes, no Submit walk, no "unanswered" banner - the entire DialogFormSpec machinery has no SDK equivalent because the problem it solves does not exist there.
  • Hooks as in-process callbacks for the full event set; machine-installed ~/.claude/settings.json hooks also still fire in the subprocess.
  • Everything else: MCP via options.mcpServers; skills and CLAUDE.md via settingSources; /clear and /compact as user messages; images as base64 blocks; per-turn usage and total_cost_usd on result messages.

Codex: the SDK cannot answer approvals; app-server can

This is the decisive Codex finding. @openai/codex-sdk is a thin wrapper over codex exec --experimental-json: approval policy is pre-set and there is no callback - a headless run either auto-decides or fails. Human-input tools are stripped from the toolset in exec mode. The SDK's only interrupt is killing the subprocess.

codex app-server - the JSON-RPC-over-stdio interface the IDE extension, the Desktop app, and the official Python SDK use - surfaces everything we need:

  • Approvals as answerable requests: item/commandExecution/requestApproval and item/fileChange/requestApproval, answered accept / decline / cancel.
  • Threads and turns: thread/start / resume / fork, turn/start with per-turn model / effort / sandbox overrides, turn/interrupt, and turn/steer - input appended to an in-flight turn, which no other Codex interface has.
  • Programmatic equivalents of TUI-only commands: thread/compact, review/start, account/rateLimits/read.
  • Typed bindings generated from the pinned binary (codex app-server generate-ts).
  • Shared rollouts in ~/.codex/sessions/; the interactive TUI resumes them (codex resume --include-non-interactive).

Caveat: the protocol is documented as experimental. Mitigation is the generated bindings against the binary we launch, plus adapter isolation - the protocol is spoken in exactly one module.

pi: has a first-class RPC mode

In scope as this plan's final phase (a resolved decision): pi --mode rpc is JSONL over stdio with prompt / steer / abort / switch_session / fork / set_model / compact, full streaming events, and interactive dialogs surfaced as extension_ui_request (select / confirm / input) answered over stdin. That last part matters doubly for pi: it has no hooks and no readable TUI grammar today, so the RPC driver is the first time a pi session gets structured needs-you evidence at all. One caveat: pi enforces no tool approvals itself (permission gating is an extension concern), so the driver surfaces whatever dialogs pi's configured extensions raise rather than a built-in approval stream.

Gained

  • Delivery stops being probabilistic. send() acks; no settle window, no paste placeholder, no submitVerified: false, no Enter swallowed by a mention popup, no pane lock, no copy-mode probe, no capture-miss counter.
  • Menus stop being screens. A permission prompt is a callback with the tool name and input as data; a multi-select is a typed form with free text; a Codex approval is an RPC carrying the exact command and diff. The failure class where a dialog swallows typed characters and Enter confirms the default row is structurally gone.
  • The folder-trust dialog disappears for SDK sessions - the dialog that motivated the --permission-mode launch-flag work (#223).
  • True interrupt, live mode/model changes instead of TUI walks that read footers which dialogs hide.
  • Exact usage per turn on the event stream.
  • Dispatch verification collapses: the 20s hook wait and prompt acceptance polling become "the SDK reported init".

Unchanged by design

  • The read path stays file-based. Both SDKs write the same session files the CLIs write, so transcript.locate / passiveRead / messages, goal reading, queue verification windows, Codex usage ledger, and the transcript SSE stream keep working with zero changes. The driver replaces the write path and the state path, never the read path.
  • Worktree provisioning, pinned bases, the pool - identical.
  • Task lifecycle contracts - session_remove remains the durable signal.
  • The MCP ask-channel descriptor is rendered into SDK options instead of argv; same single declaration.

Architecture

The axis is a per-session runtime, not a new harness

An SDK-backed Claude session is still Claude on every axis the registries measure - same transcript format, same skills directory, same models, same identity, same accent. A claude-sdk agent id would give one product two settings cards, two model catalogs, two entries in every agentList() sentence, would fragment the hook-overlay namespace (overlayFor matches on agent), and would silently become the ensemble default if it ever landed at AGENT_TYPES[0]. The fact being encoded is how this particular session is driven, which is exactly what controlFor(session) was shaped to answer.

// @shared/types.ts
export type SessionRuntime = "terminal" | "sdk";

export interface Session {
  // ...
  runtime: SessionRuntime;  // fixed for the life of an entry
}

SESSION_FIELD_COMPARATORS gains runtime: byValue. NameSource gains "sdk". SDK session ids are sdk:<uuid>, disjoint from proc:<tty>:<pid>:<startMs> by construction.

The harness slot: SdkSpec

One new nullable capability on the server-side Harness:

export interface Harness extends HarnessCapabilities {
  // ...
  /** How to run this harness embedded, or null when no driver exists (yet). */
  sdk: SdkSpec | null;
}

export interface SdkSpec {
  launch(opts: SdkLaunchOptions): Promise<SdkSessionHandle>;
}

export interface SdkSessionHandle {
  events: AsyncIterable<SdkEvent>;
  send(turn: { text: string; images?: SdkImage[] }): Promise<void>;  // acked
  interrupt(): Promise<void>;
  answer(requestId: string, answer: SessionRequestAnswer): Promise<void>;
  setPermissionMode: ((mode: PermissionMode) => Promise<void>) | null;
  setModel: ((model: string) => Promise<void>) | null;
  clearContext: (() => Promise<void>) | null;
  stop(): Promise<void>;
}

export type SdkEvent =
  | { kind: "bound"; agentSessionId: string; transcriptPath: string | null }
  | { kind: "state"; state: "working" | "idle"; activity: string | null }
  | { kind: "request"; request: SessionRequest }
  | { kind: "request_resolved"; requestId: string }
  | { kind: "turn_done"; usage: SdkUsage | null }
  | { kind: "pr_created"; url: string | null }
  | { kind: "exited"; reason: string; resumable: boolean };

The purity split holds: the browser needs to know whether a harness offers the SDK runtime (to draw the toggle), so HarnessCapabilities gains runtimes: readonly SessionRuntime[]. A contract test pins runtimes.includes("sdk") === (HARNESSES[a].sdk !== null) - the one-fact-two-files treatment GOAL_UNSUPPORTED already gets.

Declarations as the phases land: claude ["terminal", "sdk"] (phase 2), codex ["terminal", "sdk"] (phase 4), pi ["terminal"] with sdk: null until its driver phase (phase 6) - a real absence taking the tested degradation in the interim: no toggle, terminal dispatch, a sentence composed from the capability.

The supervisor

src/server/sdk/supervisor.ts, in the daemon - the Inspector precedent, for the Inspector's reasons: a packaged Electron build must have it, and its state must survive restarts. The Foreman stays a separate HTTP-only process.

  • Owns the handle map; serializes send() per session (the pane lock's job, without the pane).
  • Registers sessions with the registry - the counterpart of applyDiscovery for sessions no ps sweep will see (SDK subprocesses have no tty). It mints sdk:<uuid> ids, feeds bound events into the same identity slots hooks fill today (agentSessionId, transcriptPath - which is what keeps the file-based read path working), and applies state / request events through a new registry.applyDriverEvent. No attribution guard is needed: the supervisor owns the binding it reports.
  • Persists to a new sdk_sessions table (new table, so migrate() needs nothing; no REFERENCES; explicit NOT NULL primary key).
  • Resumes on startup, and the restore completes before the discovery poller starts, so registry.onSessionsObserved (the restart twin that settles orphaned tasks) sees SDK sessions on the first completed sweep. A failed resume is registered, marked exited, and evicted normally so TaskManager.reconcileTasksBoundTo settles its task visibly.
  • Evicts: applyDiscovery's unseen-means-exited rule is scoped to proc: sessions; SDK sessions exit when their handle says so, through the same exited then session_remove sequence both existing subscribers already handle.

One request shape for menus, permissions, questions, approvals

The multi-select special case, resolved by making the pane dialog one producer of a shared shape rather than the shape itself. PaneDialog is already the wire shape the dashboard renders and Foreman answers; it generalizes with optional fields (absent on pane dialogs, so the wire is compatible):

export interface PaneDialog {
  // existing: options, highlighted, multiSelect?, prompt?
  source?: "pane" | "driver";
  requestId?: string;   // driver correlation; answers echo it
  kind?: "permission" | "question" | "plan" | "approval" | "trust";
  questions?: SessionRequestQuestion[];  // multi-question forms (AskUserQuestion)
}

Answering routes by runtime, not by caller: select-option keeps its {number, label} body (pane: cursor walk; SDK: verify the label with the same optionRowMiss rule, resolve the callback); submit-options resolves multi-select with the full answers map - no Submit tab, no unanswered banner, and free text becomes possible instead of refused. promptHarness gains runtime so the reviewer prompt states the true grammar; multi-question forms become answerable (answer.form) instead of menuMismatch's blanket multi-select refusal. reportBucket's activePaneDialog check needs no change: a pending driver request lives in the same field, so an SDK session with an open ask reads needs-you everywhere it does today.

One simplification falls out: dispatched Claude sessions today launch with --disallowed-tools AskUserQuestion plus a redirect prompt steering asks into the MCP ask-channel. SDK sessions re-enable the native tool - the card renders the question directly, which is what the redirect was approximating.

The delivery predicate

canWriteTo answers "is there a composer to type into", and ~20 call sites use it to mean "can Mission Control deliver a turn". Those become different questions: a new canMessage(s) (pane-writable OR sdk runtime) is adopted by every delivery-intent call site (send boxes, queue gate, assign preflight, pickers, Foreman's canSend); canWriteTo keeps its literal meaning for pane mechanics (focus, rename, locks, capture tolerance). The sweep is enumerated per call site in the phase work and pinned by tests.

Dispatch, the toggle, and the settings panel

HarnessesConfig (src/server/harnesses.ts) is the documented home for dispatch-time defaults, read at dispatch time so a toggle mid-batch affects the next launch:

  • Schema: sessionRuntime: Record<AgentType, SessionRuntime> defaulting every agent to "terminal", with hand-written per-agent patch blocks. A persisted value this build cannot read falls back to "terminal" and reports the drop (the ResolvedLlmRunner.unknown precedent).
  • resolveDispatchRuntime(agent): config value, gated on HARNESSES[agent].sdk !== null.
  • Panel: the Harnesses card per agent gains a runtime control, rendered only for agents whose capabilities declare "sdk"; the absence sentence is composed from the capability.
  • Dispatcher.dispatch: after worktree provisioning (identical), branch once - terminal: today's path; sdk: supervisor.start(...). No home, no 20s hook wait (init IS ready), no paste (the prompt is turn one). Task.homeName stays null; the homeAlive three-valued contract gets an sdk arm where the supervisor always answers true/false, never null.

Automation parity

  • Foreman (HTTP-only, unchanged process shape): classifyPending already keys on the shared request field and driver state. The pane capture returns null for SDK sessions; the review prompt substitutes the structured request and transcript window - strictly more faithful than a 60-line viewport.
  • Work queue: pickup/completion arrive as driver events (SDK sessions are instrumented by construction); delivery goes through send() with a real ack - mayHaveLanded, paneBlocked, and the pane-recreated guard have no SDK arm because their failure modes cannot occur; verification (transcript.since) is unchanged.
  • Reset: resetSession routes through handle.clearContext(); work-episode rebind keys on the rotated agentSessionId exactly as the hook path does.
  • Inspector / PR provenance: the driver watches gh pr create on its tool stream (pr_created event) and feeds the same adoptPr path - authorship evidence, preserving the two-signal provenance rule.
  • Cost: unchanged pipelines (Claude OTEL from the subprocess, Codex rollup from rollouts SDK sessions still write); driver usage is display enrichment, not a second ledger writer.

Terminal takeover

Because both vendors share session storage between their programmatic and interactive surfaces, "let me drive" is an explicit handoff rather than a lost capability: POST /sessions/:id/handoff stops the driver gracefully, marks the SDK session exited, and launches a terminal home in the same cwd running claude --resume <agentSessionId> / codex resume <threadId>. Discovery adopts the new process; session decorations keyed by noteKeyFor follow the agent session id through the same rebind machinery a /clear exercises today. The card gains a "Continue in terminal" action where "Focus" renders for pane sessions.

Phases

  1. The seam (no behavior change): Session.runtime + comparator, canMessage / canWriteTo split with the enumerated call-site sweep, PaneDialog extensions, registerSdkSession / applyDriverEvent / eviction scoping, supervisor skeleton + sdk_sessions table, SdkSpec slot (all three harnesses null), runtimes capability + contract test.
  2. Claude driver, behind the toggle (default stays terminal): the Agent SDK adapter, request projections, dispatch branch, sessionRuntime config + Harnesses panel control, resume-on-restart, all four session-drawing components rendering runtime truthfully - and the "Continue in terminal" handoff, so the first SDK session an operator ever dispatches is never a trap.
  3. Automation parity on Claude: Foreman structured answers + prompt runtime projection, work queue over send(), reset, wrap-up invocation, cost double-count verification, PR provenance events.
  4. Codex driver: app-server adapter with generated bindings pinned to the launched binary, approval projections, per-turn permission/effort overrides, thread resume, parity re-run of phase 3's checklist.
  5. Deprecation of the dispatched-session keystroke surfaces: defaults stay "terminal" - cut-over is the operator flipping each harness's toggle, never a default change (resolved decision). This phase retires the machinery only SDK-runtime dispatch makes unreachable and documents the enduring terminal surface: operator-started sessions, and Foreman's pane-menu answering for sessions we do not own.
  6. pi RPC driver: a pi adapter over --mode rpc behind the same SdkSpec - extension_ui_request dialogs projected into the shared request shape, pi's runtimes gaining "sdk" and the Harnesses toggle appearing for it. Also where pi first gains structured needs-you evidence and a deliverable work queue signal, so its workQueue: null / hooks: null declarations are revisited for SDK-runtime pi sessions.

Resolved decisions

Submitted from the Mission Control dashboard on 2026-07-24:

  1. Codex transport: codex app-server. The only interface with answerable approvals; the official @openai/codex-sdk was rejected because it reduces approvals to pre-set policy. Drift risk is absorbed by generated typed bindings pinned to the launched binary, spoken in exactly one adapter module.
  2. Toggle scope: Harnesses settings panel only. One per-agent default read at dispatch time; no per-dispatch override.
  3. Terminal handoff: built with the Claude driver (phase 2). The first SDK sessions ship with the escape hatch.
  4. No default flip. The stored default stays "terminal" for every harness; cut-over is the operator flipping each toggle in settings.
  5. pi RPC driver: in scope, as the final phase (6).
