Review answers can outlive their MCP result channel

No Mission Control review timer is set to 30 minutes. The daemon waits in 30-second HTTP long-poll slices. The likely 30-minute boundary is the MCP host's maximum per-tool wait. After that channel is canceled, the dashboard can still persist an answer, but nothing durable carries it back to the session.

Finding

The current heartbeat reduces idle timeouts, but cannot guarantee an unlimited wait. The MCP specification allows a client to reset its timer on progress and recommends a maximum timeout regardless of progress. Mission Control currently documents the reset as mandatory and indefinite, which is not the protocol contract.

Failure flow

Solution options

  1. Durable continuation fallback, recommended. When the MCP host cancels a blocking review call, persist that the result channel detached. When the review is later resolved, atomically enqueue the answer through the existing pending-turn outbox. This is client-independent and survives daemon restarts.
  2. Raise host timeouts. Add an explicit long tool_timeout_sec for Codex launches and equivalent supported settings elsewhere. This is small, but only moves the loss boundary and cannot promise delivery.
  3. Replay on identical retry. Reuse a recently answered identical review when the model retries. This is useful defense in depth, but it depends on a retry and risks confusing a legitimate repeated question without a stable idempotency key.

Limits

The repository establishes the 30-second daemon slice and the missing fallback. It does not establish which specific host produced the operator's observed 30-minute boundary. No operator database or live session state was opened. Official OpenAI documentation confirms a configurable Codex per-tool timeout but does not document a 30-minute default.
