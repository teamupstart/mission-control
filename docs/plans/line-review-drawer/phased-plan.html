What the repository confirmed

Read against the working tree before the phases were drawn.

  • The two complaints are one bug. All 31 blocked runs in the live database carry phase = "session_disappeared". ReviewDrawer.tsx:154 resolves a name only from live sessions, so a run whose session was removed falls through to the noteKey GUID.
  • The durable title already exists. workflow_bindings.session_name is captured at bind time and survives the session. WORKFLOW_RUN_SUMMARY_SELECT already JOINs workflow_bindings - adding b.session_name is a projection change with no new join and no new statement.
  • The reason already ships. WorkflowRunSummary.phase is on the SSE payload for every run. phase is a free string, not a union, so any map over it needs the replaceAll("_", " ") fallback alerts.ts:369 already uses.
  • All four remedy routes are argument-free, taking { requestId } plus optional fields that default.
  • Two tests encode the rule this work revises. test/line-drawer.test.ts's "the Review drawer offers escalation and never a mutation", and test/workflow-external-source.test.ts:774 which pins the summary's exact key set. Both are rewritten deliberately in Phase 1.
  • README carries the same rule in prose and is Phase 1 work, not a follow-up.
  • A blocked run cannot be seeded by writing SQLite. Run summaries come from an in-memory map on the Registry, so the e2e spec drives the daemon and waits out the hardcoded 8s EXIT_LINGER_MS.

Discrepancies recorded against the source plan

Three, all found by reading the code rather than trusting the plan:

  1. src/web/App.tsx is probably not where the remedy handlers go. The right seam is the one WorkflowLadderPanel already uses on a secondary surface: local confirm/localError state, run-action-store.ts for pending and requestId retention, workflowRequest, and the shared WorkflowConfirmModal.
  2. src/web/lib/api.ts has no wrapper for any of the four routes. Workflow mutations go through workflowRequest in src/web/workflows/workflowApi.ts.
  3. Two remedies' run-page guards are not summary-only. restart-full guards on detail.inspectorGate and retry reads detail.attempts for an optional nodeAttemptId. Both remain reachable with coarser summary-only guards.

Cross-phase contracts

Phase 1 establishes these; Phase 2 consumes them and must not change their shape.

ContractShapeNotes
WorkflowRunSummary.sessionName sessionName?: string on src/shared/workflow.ts Optional and append-only. Emitted only when non-empty, using the ...(x ? { x } : {}) spread externalSource already uses, so a run with no captured name costs no bytes on a payload that ships for every run on every change.
blockedPhaseClause(phase: string): string exported from src/web/workflows/run-model.ts Short lower-case clause for the state column ("session gone"). Falls back to phase.replaceAll("_", " ") for any unmapped phase.
runRemedy(run): RunRemedy | null exported from src/web/workflows/run-model.ts The single argument-free action for the run's phase, decided from the summary alone. RunRemedy's kind doubles as the RunActionId, so it must be one id per intent.
The revised drawer rule doc comment on ReviewDrawer.tsx + README "No fetch and no run detail. Actions only where the summary alone proves the run is stopped and the route needs no argument beyond the run id."
Row name resolution live session name → run.sessionName → run.noteKey The GUID is the third fallback and renders as a dim mono identifier, never as a bold title.

Final verification

Each phase runs its own verification. Across both, the definition of done is the repository's:

npm run typecheck
npm run lint
npm test
npm run build && npm run smoke
npm run test:e2e

npm run test:e2e needs npm run build first and npx playwright install chromium once per machine. README and this plan directory must match the implementation when Phase 2 merges.

Cross-phase audit record

  • After Phase 1 was written. Confirmed Phase 1 leaves the repository valid on its own: rows are named and explain themselves, and every remedy is wired, with no reference to grouping. Confirmed the two deliberately-broken tests and the README rule are inside Phase 1, not deferred.
  • After Phase 2 was written. Confirmed Phase 2 adds no field to WorkflowRunSummary and no server change beyond foldReview. Confirmed the group threshold (3) lives in Phase 2 alone, and that the strip/drawer count split changes presentation only - workflowRunWaitsOnOperator is untouched, so the command palette's "waiting on you" list keeps its meaning. Phase 2 raised the bucket-overlap trap (a run can be both blocked and operator-action-waiting) and owns the test that pins it.
  • Phase 1 revised after reading the client action plumbing. The source plan's App.tsx seam was replaced by the WorkflowLadderPanel / WorkflowConfirmModal / run-action-store shape the repository already has, and a guard table was added.
  • Final pass over both. Every source-plan requirement and every submitted selection is owned by exactly one phase. The dependency direction is single and forward. No phase depends on a later phase to repair an intermediate state.
