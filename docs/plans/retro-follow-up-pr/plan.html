Post-merge retro follow-up pull requests

A retro follows the review boundary. It rides an open work pull request, but becomes a separately tracked task and pull request after the original review has merged.

Open work PRUse the existing session, branch, task lifecycle, and pull request.
Merged work PRCreate or reuse a linked retro task, then start a fresh branch and review.
No approved changeCreate no empty commit or PR. Complete only the retro task with a verified no-change outcome.

The post-merge follow-up is unique per source task work episode. Repeated clicks return the same task. Mission Control tries immediate dispatch and leaves that same task visible in the backlog if launch cannot proceed.

Problem

The live-session path currently injects the retro into the session that did the work. That is correct while its pull request is open. After merge, the branch cannot add commits to that review. Continuing in the old task can also reopen work whose merge already proved completion, while an old merged binding can be mistaken for evidence that the retro shipped.

The dead-session fallback creates a backlog task, but does not distinguish this post-merge boundary, does not try to start immediately, and cannot explicitly complete a successful retro that produces no memory change.

Goals and boundaries

Goals

  1. Preserve same-session behavior while the source pull request is open.
  2. Keep a merged feature task complete and make later retro work separately reviewable.
  3. Create the follow-up idempotently against the exact source work episode.
  4. Dispatch immediately when possible, with an honest, retryable backlog fallback.
  5. Open a new pull request automatically for approved memory commits.
  6. Complete a no-change retro without a fake commit or pull request.
  7. Report delivered, started, and queued outcomes consistently in every dashboard entry point.

Non-goals

  • No source-task reopening or new Mission Control goal.
  • No separate pull request for every retro.
  • No daemon-authored git changes and no automatic merge.
  • No replacement of the existing dead-session fallback without durable merged-episode proof.

Changed request and completion flow

Lifecycle design

Resolve durable posture

Identify the source task and current episode, then use a retro-specific durable query. The current episode's open pull request wins. Only when no current review is open may the newest merged binding from current or historical episodes establish the post-merge boundary. This is deliberately different from merged-first task completion; a session pull request field remains too weak because it is only a projection.

Keep open reviews together

An open source pull request keeps the existing action delivery, skill approval, branches, and review. No second pull request is opened.

Create or reuse post-merge work

A merged source episode maps atomically to one normalized retro-follow-up relation and one named ship task. The task copies the source repository set, but never its leases, branches, worktrees, or pull-request bindings. Ordinary task dispatch is attempted after durable creation.

Ship approved changes

The fresh retro session invokes the retro approval procedure and ordinary pull-request shipping. Each changed repository gets one new review. The retro task completes only from pull requests belonging to its own episode.

Settle no-change explicitly

A narrow MCP operation derives the calling session's task, verifies its durable retro-follow-up relation, and completes only that task. It cannot name or complete arbitrary tasks and does not manufacture merge evidence.

Explain the outcome

Add started and queued response arms while preserving delivered and dispatched. One shared formatter supplies the Action Bar, Complete dialog, and Workflow Ladder copy.

Data and compatibility contracts

  • Idempotency is keyed by source task and work episode, with a unique retro-task relation.
  • Retro routing uses a current-open-first posture query and does not change the merged-first task completion rule.
  • Fresh and upgraded databases create the relation in migration-safe order.
  • Existing response arm spellings are frozen; new arms are additive.
  • Task and session changes flow through TaskManager and Registry so SSE, leasing, dependencies, and merge reconciliation remain consistent.
  • An old source merge can never settle the retro task.
  • Multi-repository follow-ups preserve the source repo set and one-review-per-changed-repo rule.

Verification

  • Database upgrade and idempotent source-episode linkage tests.
  • Retro route tests for open, merged, duplicate, dispatch, fallback, dead-session, and multi-repo cases.
  • Task lifecycle tests proving the source stays done and only retro-owned evidence settles the follow-up.
  • MCP schema, vocabulary, authorization, and bundled-server smoke tests.
  • Shared response formatter and component rendering tests for every arm.
  • A fake-agent Playwright regression for the merged click, separate task, duplicate suppression, and source-task status.
  • Typecheck, lint, full unit tests, build, smoke, and full end-to-end tests.
