Pi's models are compiled into Mission Control, not sourced from Pi

Verified root cause: the four rows in the screenshot come from a hand-maintained array in src/shared/model.ts. The installed Pi 0.84.2 has a structured, account-aware model-list command that Mission Control does not call. On this machine Pi reports 38 available models; Mission Control offers four, only three overlap, and it misses 35 current entries.

Recommendation: use Pi's RPC get_available_models response as the live source for Pi, through a harness-owned server capability. Keep the shipped catalog and the currently stored value as fallbacks. This fixes the drift without making settings depend on Pi always succeeding.

How the list is sourced today

src/shared/model.ts:94-150 declares one MODEL_CATALOG for Claude, Codex, and Pi. The Pi branch contains exactly the four screenshot rows. The source comment says the list is hand-maintained because no CLI exposes a machine-readable account list. That premise is no longer true for Pi 0.84.2.

The same helper, modelChoicesFor, supplies multiple surfaces:

  • src/web/components/HarnessesPanel.tsx:179-200 renders the Settings model select shown in the screenshot.
  • src/web/components/DispatchModal.tsx:283-332, 2489 uses it for dispatch choices and default labels.
  • src/web/components/schedules/ScheduleEditor.tsx:436 uses it for scheduled tasks.
  • src/web/ensembles/dispatch/EnsembleDispatch.tsx:769, 1131 uses it for ensemble members and summary labels.

The selected ID is not restricted to the array. src/shared/protocol.ts:605-613 accepts safe provider-qualified IDs, and modelChoicesFor preserves an already stored off-catalog value. This is a useful fallback, but the UI has no free-text path to discover or choose a new value in the first place.

Root cause

Verified, 99% confidence: catalog drift is caused by the static array and the obsolete discovery premise in its comment. The evidence is direct: the screenshot labels match the four literals exactly; every picker reads that array; Pi 0.84.2 exposes both a table command and a structured RPC command; Mission Control calls neither.

This is not a browser cache issue and not an operator configuration issue. Restarting or rebuilding Mission Control can only render the same four compiled values until source changes.

Solution options

Recommended architecture

  1. Add a required server-side models capability to Harness. Claude and Codex return their shipped catalogs; Pi supplies a discoverer plus fallback. This follows the registry pattern already documented in src/server/harness/types.ts:1035-1076.
  2. Implement Pi discovery as a short-lived RPC subprocess using the same resolveAgentBin("pi") path as dispatch. Send one correlated get_available_models request, accept only its matching success response, allowlist fields, validate every derived provider/id, bound time, bytes, and row count, then terminate.
  3. Expose the resolved catalog from a generic harness-model route. Return source, refresh time, and a non-secret diagnostic state so the browser can distinguish live data from fallback.
  4. Give all picker consumers one browser model-catalog store. Merge the currently saved value exactly as modelChoicesFor does today, so a transient probe failure or older build never erases a valid selection.
  5. Keep the shipped list as a failure fallback, not the primary source. Older Pi versions, a missing binary, no configured provider, malformed output, timeout, and subprocess failure must leave the picker usable and visibly stale.
  6. Cover the new UI behavior with Playwright and the subprocess/parser with focused tests. The fake Pi binary must answer the RPC probe so end-to-end tests never reach a real provider.

Decision resolved

The operator approved mirroring every model Pi reports available, grouped by provider. The live catalog is therefore complete rather than curated. The compact shipped list remains only as a failure fallback, and a saved off-catalog value remains selectable.

Limits and what was not established

  • The live probe covered this machine's Pi 0.84.2 installation and one configured OpenAI provider. No custom provider or multi-provider account was available to exercise grouping.
  • The probe used --offline. It establishes that Pi can expose its locally known, account-filtered catalog without a model call; it does not establish the desired policy for refreshing remote dynamic catalogs.
  • Older Pi versions were not installed and tested. The solution therefore must feature-detect or fail back instead of declaring a minimum version from this sample.
  • No request was sent to any model. "Available" here means Pi includes the entry after its auth/filter pass, not that all 38 APIs were individually invoked successfully.
  • No production code was changed and no repository test suite was run. Only read-only repository inspection and no-session Pi catalog probes were performed.
