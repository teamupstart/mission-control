Foreman completion judgment and recovery fixes

Source finding: docs/reports/foreman-completion-detection-stall/report.html. The completion signal works; the judgment and recovery layers around it fail in three compounding ways. This plan turns the report's recommendations into an implementable, three-phase design.

Problem

A dispatched ship task finishes, reports completion, and registers verification evidence. Foreman detects it within seconds and runs its verifier - which holds, because:

  1. It cannot see command output. The transcript renderer emits tool inputs only (src/server/foreman/prompt.ts:604-628; ToolCall in src/shared/types.ts:3126 has no output field). It sees npm test start and can never see it pass.
  2. It cannot see registered evidence. VerifyInput (src/server/foreman/queue-prompt.ts:26-65) has no evidence field; the workflow_evidence_staging rows carrying exactly the missing proof are invisible.
  3. The contract makes it judge what it cannot observe. The ship contract (src/shared/task-completion.ts:64-90) requires verification-run and evidence-registration facts it structurally cannot check.

A held verdict is silent (prompted-wrapup.ts:309-359); recovery is the 20-minute ship shepherd (ship-shepherd.ts:124); each nudge mints a new generation, resetting the verifier's gap memory (round: 0, priorGaps: [], worker.ts:1991-2022) and the shepherd's 3-attempt escalation budget (ship-shepherd.ts:71-87). Observed: 4 completions, 4 holds, 3 nudges ~23 min apart, 0 workflow runs; fleet-wide, 15 of 31 decided sessions currently sit on held. The repository standing instruction ("do not rerun the full test suite before re-submitting") directly contradicts what the verifier keeps demanding.

Goal

  • A completion whose registered evidence covers required verification is claimed into its bound workflow on the first verify.
  • A genuinely incomplete managed ship completion gets gap feedback within one worker pass (seconds), not after a 20-minute backstop.
  • A session held across repeated cycles of one intent episode reaches a human after a bounded number of attempts.
  • Human-driven (non-task) sessions keep today's behavior exactly: the prompted trigger stays a silent bystander on hold.

Non-goals

  • No change to workflow internals, drain/queue-item semantics, or dispatch.
  • No new UI surface - recorded episodes reuse existing situations so the Foreman drawer renders them unchanged.
  • No relaxation of injection safety: child-authored text stays inside the untrusted fence; consume-before-type ordering is preserved.

Design

Phase 1 - Evidence-grounded verification

Structural pre-check. Before the LLM call on the prompted verify path for a task-bound session, the worker fetches registered evidence via a new client.workflowEvidence(sessionId) against the existing daemon route GET /api/sessions/:id/workflow-evidence (src/server/routes.ts:1973). What is registered becomes a stated fact, never a model inference about database contents: zero rows render as "the clause is not satisfied"; a nonempty list renders as a count, with coverage judgment left to the verifier - it is never declared to satisfy the clause outright, because a task that requested several artifacts is not satisfied by one.

Evidence in the prompt. VerifyInput gains a registeredEvidence list. Only daemon-generated metadata - counts, evidence kinds, generations, timestamps, byte sizes - renders above the evidence fence as trusted context. Child-authored fields - display names, source locators/commands, captions - are the session's own text, chosen at registration, and render inside the untrusted fence, capped, exactly as the transcript does.

Policy alignment. The verify POLICY is extended: when registered command evidence covers the required verification, absence of test output in the transcript is not a gap; prior-generation evidence remains valid for a re-submission - which resolves the standing-instruction contradiction without touching the instruction.

Auto-submit fallback for verification-evidence-only holds (adopted decision, 2026-08-24). The gap vocabulary gains an explicit evidence-class marker (an additive kind value in GapSchema). When a foreman_complete binding exists and a verdict is otherwise complete but every blocking gap carries that marker, the worker claims the workflow instead of holding - the bound workflow runs the real suite, so submitting is strictly safer than stalling. With no binding, the hold stands. The claim summary records that the fallback fired.

Touches queue-prompt.ts, queue-verify.ts, worker.ts, client.ts. Tests in test/. No UI change.

Phase 2 - Immediate gap delivery for managed ship tasks

When planPromptedWrapup returns hold and the session is a managed ship task the shepherd would eventually nudge anyway (same gates as decideShipShepherd: Foreman invited, live and allowlisted, hooked, pane available, no human owner, no queue items or pending turns, no active workflow, no task-owned open PR), the worker delivers the held-gaps payload immediately in the same pass - reusing the shepherd's structuralPayload wording and its recovery/episode accounting so the attempt counts once wherever it is delivered from. The 20-minute shepherd remains as the backstop. Authority (adopted decision, 2026-08-24): the existing keepShipTasksMoving flag governs both - no new knob.

Touches worker.ts, prompted-wrapup.ts, ship-shepherd.ts. Cuts cycle latency from ~23 min to one pass.

Phase 3 - Convergence and escalation across generations

Gap strikes survive the generation bump. The previous held decision's gaps (already persisted in prompted_decision) feed the next verify for the same intent episode as priorGaps with persisted strike counts, so the verifier's REUSE-GAP-IDS machinery works across cycles.

Attempt budget keyed on the episode, not the generation. Ship-recovery attempt counting moves to (task, intent episodeKey, reason): a nudge-response's new generation continues the same budget, and attempt 4 escalates through the existing path. A new accepted human prompt advances the episode and correctly resets the budget. Old persisted JSON keeps parsing (compatibility pinned in tests); append-only identifier contracts untouched.

Touches ship-shepherd.ts, worker.ts, src/shared/types.ts.

Adopted decisions (2026-08-24 plan review):

  • Auto-submit on verification-evidence-only holds: included in Phase 1. The reviewer chose the belt-and-suspenders reading of report recommendation 3 - the No-Mistakes workflow runs the real suite, so holding finished work out of the stage that runs the tests is the worse failure.
  • Phase 2 authority: reuse keepShipTasksMoving. No new config knob.
  • Follow-up: phased implementation - merge-aware phases and dependency-linked Mission Control tasks.

Flow change

Phasing and dependencies

Phases land in order - all three touch src/server/foreman/worker.ts, and Phase 2's attempt accounting is what Phase 3 re-keys.

  1. Evidence-grounded verification (highest leverage; removes the false-hold class).
  2. Immediate gap delivery (cuts cycle latency from ~23 min to one pass).
  3. Cross-generation convergence and escalation (bounds the loop).

Success criteria

  • Worker test: completion with registered evidence covering required verification is claimed on first verify; without evidence rows it still verifies on intent alone and can hold.
  • Worker test: a verdict whose blocking gaps are all evidence-class claims the bound workflow (fallback recorded in the claim summary); any other blocking gap holds; with no binding, the evidence-class hold stands.
  • Worker test: a held managed ship completion receives gap text in the same pass; a held human-driven session receives nothing.
  • Policy test: three held cycles across three generations of one intent episode escalate; a new human prompt resets the budget.
  • npm run typecheck, npm run lint, and the affected test/ files pass; no UI change, so no new e2e/ spec is required.
