Plan: Backlog autopilot - Foreman schedules the backlog

Foreman reads the enabled backlog, works out what depends on what, and hands one item at a time to an idle agent or to a fresh worktree - up to a ceiling you set.

Implemented · live-only · max agents default 3

Why

The backlog is a list of things you want done, and the board shows it right next to your idle agents. Nothing closes that gap but your hand. Foreman already drains a session's work queue; this drains the fleet's backlog.

The two halves already exist. A task can reach an agent two ways - POST /api/tasks/:id/dispatch cuts a worktree and launches one, POST /api/tasks/:id/assign hands it to one that is already running. Both are a click on the board today. All that is missing is something deciding which, and when, and whether there is room.

What the human sets

KnobDefaultWhat it does
Auto-schedule the backlog autoBacklogoffarms the autopilot
Max agents running at once maxSessions3the ceiling it will not launch past
Open PRs keep an idle agent off the backlog backlogRespectOpenPrsonan agent whose branch still has an open PR is not handed the next task; a merged PR never blocks

Max agents counts every live agent on the machine, not just the ones Mission launched - it is a claim about the machine's load, and a count that ignored six hand-started sessions would not be one. It bounds autopilot only: it never refuses a dispatch you clicked, because blocking a button you pressed to protect a background scheduler's budget is the worse surprise.

The gate

Launching an agent starts unattended work; handing a task to a running agent types a whole prompt into a pane a human may be sitting in front of. Both are more consequential than answering a prompt, so autopilot clears the same bar an automated wrap-up does:

  • Foreman enabled, and autoBacklog on.
  • Mode is live. In dry-run and semi-auto it still plans - the board shows the ordering and the dependency read - but it never launches or types. Dry-run means dry-run.
  • The task's repoRoot is on the repo allowlist, judged with the shared foremanAllowlisted so the board explains the decision with the same predicate the server gates on.

Architecture

The precedence

  1. autopilot off → none.
  2. backlog empty → none.
  3. the stored plan does not cover every enabled planning item → plan, and nothing is scheduled this tick. Acting on a plan that has never seen the newest item is how two conflicting tasks get started together.
  4. walk ready items in plan order; the first with a genuinely free agent in its repo → assign.
  5. otherwise the first ready item, if the fleet is under maxSessions → dispatch.
  6. otherwise none, saying which of those it was.

Assignment is checked before capacity on purpose. It consumes no new session, so it is correct at the ceiling and cheaper below it. Putting the ceiling first would silently disable the one path that costs nothing.

Capacity is sessions plus tasks mid-provision

A task that has been dispatched but whose agent has not been discovered yet is an agent - the worktree is being cut, the process is coming up. Counting only the session list leaves several seconds in which every tick sees spare capacity and launches into it. Not theoretical: discovery polls, and provisioning a worktree takes longer than one Foreman pass.

What "free agent" means

Stricter than the board's Idle column, because the board's version is a human saying "yes, that one" and this is a background loop typing into a pane nobody asked:

  • reportBucket === "idle" - the shared bucketing, which already excludes a review waiting, a menu on screen, a parked gate.
  • settledIdle - a pause between turns is not being finished.
  • hooksSeen - reportBucket files an uninstrumented session under idle by default. Right for a readout, wrong for an autopilot, which would have no way to tell it was mid-thought.
  • a pane, an empty work queue, no open PR on its branch (backlogRespectOpenPrs, on by default; a merged PR does not block), no non-terminal task of ours bound to it, the same repoRoot, the same harness the task was filed for (a Codex task is never typed into a Claude pane unasked, though a human's drag still may), and allowlisted.

TaskManager.assign re-checks what it can, because an agent can go busy between the decision and the POST - and it now resets the agent's checkout before typing, refusing when the reset would destroy work.

The dependency read, and why it is not trusted as written

This visual predates operator-declared prerequisites. The authoritative dependency rules, plan sanitization, staleness contract, and read budget live in plan.md.

When planning breaks

Three consecutive failures and the machine stops asking and drops to serial mode: one task in flight at a time, oldest first, covering assigns as well as launches - typing a task into an idle agent starts it just as thoroughly as cutting a worktree does. Serial execution satisfies every possible dependency order by construction, so a broken planner degrades to slow rather than to wrong. A plan that arrives later is used again immediately - exhaustion never sticks to the data - and after FOREMAN_BACKLOG_RETRY_MS (10 min) one fresh read is let through, so a transient outage heals without a restart and a hung planner cannot re-stall the shared loop three times per cooldown. A daemon that refuses to store a plan keeps its own count and backoff, and at the same cap degrades the same way rather than halting the autopilot outright.

"In flight" is judged against the session list, not the task row alone. A task with no session yet still counts - that discovery window is exactly what the cap is protecting - but one bound to a session that is gone does not.

A running task is only ever reconciled when the daemon restarts, so an agent whose terminal was closed leaves a row that reads running for as long as the daemon lives. Counting it turned the fallback into a dead end rather than a degradation: one dead row held the in-flight count above zero forever, and the mode that exists so a broken planner "degrades to slow rather than to wrong" instead scheduled nothing at all. Observed exactly that way, with two dozen ready items parked behind a single row whose process had exited hours earlier.

One read is one model call, over the first 400 enabled backlog items; disabled items are omitted before the limit is applied. Reading a longer backlog in batches was built and then taken back out: the calls run on the Foreman worker's single loop, which also drives queue drain and needs-you triage, so every extra batch is another span in which nothing else in the fleet is attended to - the same failure the planner's one-probe-per-cooldown rule exists to bound, arriving by another door. The limit sits below the route schema's 500-entry cap, since a plan the route refuses is a write that fails every time.

Above the limit the enabled tail is unplanned, and the readers already answer for it: unnamed items are unblocked and go last, oldest first. The cost is accepted rather than hidden - staleness is coverage, so while the enabled backlog is that long each dispatch promotes an unplanned item into the head and the next tick spends one dependency read. One call, only above 400, against a bounded worst case on the shared loop.

What the board shows

  • an on/off switch that holds an item out of autopilot without blocking manual dispatch;
  • a blocked chip naming what an item waits on - in the attention tone when the dependency was cancelled or failed, since that one will never clear on its own;
  • a distinct disabled blocker state when the unmet prerequisite is parked;
  • a next up mark on the item autopilot would take next;
  • launch controls distinguish overridable inferred blockers from authoritative declared prerequisites; see the authoritative plan.

The Foreman popover carries the live readout - 2/3 agents · 4 ready · 1 blocked · 1 disabled - so "why is nothing launching?" is answerable without reading a log. All of it is drawn from the shared predicates in @shared/backlog.ts, which the scheduler decides with, so the column cannot mark a card ready that the machine will not touch.

Testing

  • backlog-machine.test.ts - the precedence table: off, empty, stale plan, assign preferred over dispatch, assignment at the ceiling, capacity including mid-provision, blocked-only, un-allowlisted, dry-run, serial fallback.
  • backlog-plan.test.ts - sanitizePlan on a cycle (two- and three-task), a self-dep, an unknown id, a forgotten entry; blockersFor across every dependency status; ordering and staleness.
  • backlog-plan-http.test.ts - the plan round-trips through buildApp, cannot be back-dated, replaces rather than merges, and a malformed body is refused.

Out of scope

  • Autopilot completing a task. A finished agent still hands its work to the existing wrap-up triggers.
  • A hard fleet cap on manual dispatch.
  • Cross-repo scheduling logic. Items in different repos are independent to the scheduler; a dependency the planner states across them is still honoured.
