Showing a bound workflow run on the session detail pane: the stage ladder

Source design: mockups.html, Option D - stage ladder, selected by the operator. Options A, B and C are not in scope; the collapsed grid card keeps today's chip, which is what Option D's own parity row says shipping D alone means.

Phased into three implementation units in phased-plan.md (rendered as phased-plan.html beside it).

The problem

A no-mistakes run gets a whole embedded strip on the card: a named stage, a segmented rail, a ticking clock, findings, and the buttons to answer a gate. A bound workflow run gets one pill that says Preview · R2, and everything else - which stage is executing, who objected, what they said, whether a check actually ran - lives two clicks away on the Runs page.

The asymmetry is not cosmetic. Three of the run states an operator most needs to act on are invisible from the session surface: a reviewer's actual objection, a run parked at the Inspector gate, and a repair delivery whose write may or may not have landed.

What ships

A vertical stage ladder in the Console and Board detail pane: a spine with one rung per stage, reviewers nested under their stage, and the failing stage's verdict opened inline where the operator is already looking.

StateRung behaviour
ReviewingPassed stages collapsed to a line; the running stage lists its members with live status
Changes requestedThe failed stage expands the objection in the reviewer's own words
Inspector gateThe gate is its own rung carrying PR number, target head and posture
Delivery uncertainIts own rung with the shipped sentence and the two resolution actions

Height is the axis a detail pane has, which is the whole argument for a ladder rather than a rail. It is explicitly not put on the collapsed 330px grid card or the board tile.

Where the data comes from

Investigated findings

Verified against main at 985aaa23.

The derivation already exists and must not be duplicated

RunPipeline already draws a run over its published graph, and every piece of derivation it uses is reusable as-is: projectStages, stageName/stageSummary/nodeLabel, and run-model.ts's reviewerStatus, checkStatus, stageStatus, endStatus, latestAttemptsFor, verdictOf, verdictMeta, gateWaitSentence, deliveryStateView, checkStatusView. Stages are a pure projection of the graph and are persisted nowhere.

The ladder is therefore a new leaf rendering over an existing derivation, not a new derivation. This materially lowers the cost the mockups estimated ("the most expensive client one"). A second copy of any of the above is the specific failure this plan exists to prevent.

The data is detail-only, and that is deliberate

WorkflowRunSummary is what SSE carries, and it holds no stage or member structure at all. Graphs, attempts, verdicts and events never travel over SSE by design. Everything the ladder draws lives on WorkflowRunDetail. So Option D's stated cost is confirmed exactly: no SSE widening, one HTTP fetch on open. One consequence the mockups did not note: WorkflowRunDetail.inspectorGate is filled only in WorkflowManager.decorateRun; the store sets it null.

Three corrections to the mockups

  1. maxRepairRounds defaults to 5, not 6. The mockups' "round 2 / 6" is illustrative. The ladder reads the run's own value and hardcodes no bound.
  2. The uncertain-delivery actions are not plain buttons. "Discard and send new round" requires the typed phrase DISCARD AND SEND A NEW REPAIR ROUND and is disabled when no session is bound. A card-side button that fired it directly would be a destructive action behind one click that the Runs page deliberately gates.
  3. The shipped sentences already exist and must be reused, not retyped. deliveryStateView and checkStatusView are the verbatim sources.

The degraded-check rule already has a mechanism

The mockups' "do not tint a degraded stage green" is enforceable today rather than newly invented. An unconfigured slot is recorded "skipped" with a note, and RunPipeline threads this through checkOutcomeFor, whose doc comment states the exact trap: "a skipped or unavailable check still finishes as a passing attempt, so without this the chip would report 'Passed' for a command that was never spawned." The ladder must pass checkOutcomeFor for the same reason.

The built-in moved to version 4 while this plan was being written

BUILTIN_WORKFLOWS holds no-mistakes-review at version 4. Its stages match the mockups exactly, but completionPolicy moved from one fact about the workflow to one fact per version: v4 reuses v3's pipeline and sets onFindings: "inspector_only" where v3 set "restart_workflow" (#305), so Inspector findings now open an inspector-only submission rather than restarting the whole review. missingPrAction: "offer_prepare_pr" is unchanged across all four.

The consequence the ladder must respect: a round can legitimately contain no persona review at all. runRounds already flags such a round inspectorOnly. A ladder that drew three pending reviewers for one would be wrong in what is now the normal path after findings.

A case the mockups never drew

projectStages returns null for a graph that is not stage-expressible, and the Runs page falls back to a read-only canvas. Hand-built graphs predate stages and a run of one must stay watchable. A ladder has no canvas, hence decision 3 below.

Adopted decisions

Submitted by the operator on 2026-07-27. Requirements, not open questions.

  1. The Runs page keeps RunPipeline. The ladder is detail-pane only. Both surfaces draw from the same derivation, so they cannot disagree about a run's status even though they differ in shape. This preserves what RunPipeline's own doc comment calls "the point of the whole migration": the runs monitor shares its leaves with the Pipeline editor, so an operator watches the shape they authored. Two drawings, one derivation - and what is forbidden is duplicating the derivation, never the leaves.
  2. The seam is an inline strip in the conversation tab, beside ForemanStrip and NomistakesStrip, which is how the mockups draw it. This keeps Option D's pitch intact: the objection is where the operator is already looking. Height is controlled by collapsing passed stages to a single line.
  3. A freehand-graph run shows today's chip plus an "Open run" link. No ladder is claimed for a graph that has no stages.
  4. Option C's repeat-offender derivation is taken, on the run detail only. "The same member has failed N rounds running" is derived server-side and exposed on WorkflowRunDetail. SSE and the chip are untouched, so Option D keeps its cleanest property: it widens the SSE summary not at all.

Non-goals

  • No change to WorkflowRunSummary or the SSE event pair.
  • No ladder on the collapsed grid card, the board tile, or the console rail. Those keep their chip, tile flag and rail mark unchanged.
  • No new workflow execution behaviour. This is a reading surface; every action it offers routes to an existing endpoint with its existing confirmation.
  • No second copy of any stage projection or status derivation.
