Mission Control scout · incident diagnosis

Why every Claude turn printed MODULE_NOT_FOUND

The question, as asked: “I just attempted to start an iTerm2 session and got this error after the prompt was typed into the iTerm session”, followed by a UserPromptSubmit hook error and a Stop hook error, both reporting Cannot find module '/Users/jordanmance/workspace/ai-harness/hooks/harness-hook.mjs'.

The finding

Nothing was wrong with iTerm2, with the session, or with Node’s module resolution. The operator’s ~/.claude/settings.json told Claude Code to run a hook script at an absolute path inside a checkout that had been renamed: ~/workspace/ai-harness is now ~/workspace/mission-control. The path was baked in by a Mission Control installer months earlier and does not follow a checkout that moves.

Claude Code was therefore launching a script that did not exist, on all nine of its hook events, in every Claude session on the machine. Each launch died before running a line of the script. The two errors in the report are simply the two events that fire around a typed prompt.

The failure was invisible in a second way that mattered more than the first: the stack names Node’s loader and nothing else. It does not name Mission Control, does not name settings.json, and does not say which tool wrote the path, so the only signal the operator ever got pointed nowhere near the cause. Meanwhile the bridge that reports session state to Mission Control was the thing failing, so every terminal session on the machine also showed no status at all.

1. The root cause, established

Mission Control installs a hook bridge into Claude Code’s user settings so the dashboard can see what a session is doing. Both installers write an absolute path: hooks/install.mjs writes this repository’s hooks/harness-hook.mjs, and the packaged app’s src/main/integrations.ts writes dist/satellites/hook.mjs from inside its bundle. Nothing rewrites either path afterwards, and nothing checks it.

At the time the incident was reported, the operator’s file held nine entries, one per event, all naming the renamed checkout. Read back from ~/.claude/settings.json:

"SessionStart"     "/opt/homebrew/bin/node" "/Users/jordanmance/workspace/ai-harness/hooks/harness-hook.mjs" SessionStart
"UserPromptSubmit" "/opt/homebrew/bin/node" "/Users/jordanmance/workspace/ai-harness/hooks/harness-hook.mjs" UserPromptSubmit
"PreToolUse"       "/opt/homebrew/bin/node" "/Users/jordanmance/workspace/ai-harness/hooks/harness-hook.mjs" PreToolUse
   ... six more, one per event ...

And the directory it names is gone. ~/workspace holds ai-harness-old, claimyourcourt, configs-and-scripts and mission-control; there is no ai-harness:

That is the whole cause. The file named on the command line is not on disk.

2. How a typed prompt reaches a missing file

iTerm2 is incidental to this failure and does not appear in it. The question assumed the terminal both triggered the hook and supplied the module path; neither is true, and both matter for anyone diagnosing the next one.

Mission Control asks a terminal backend to open a window and start the claude binary in a checkout. From that point the terminal is a pipe. Claude Code reads ~/.claude/settings.json once, at session start, and thereafter runs the command string it found there for each lifecycle event, passing the event name as the last argument and the event payload on stdin. The path in the error was already in the file; nothing at launch time computed or passed it.

Two consequences follow from “read once, at session start”, and both were visible in the incident:

  • Every turn repeats it. UserPromptSubmit fires when the prompt is submitted and Stop when the turn ends, so a single exchange produces the two errors that were reported. PreToolUse and PostToolUse fire per tool call, so a working turn produces many more.
  • A repair does not reach a running session. Sessions already open keep the configuration they read at start, which is why the standing advice after installing hooks is to start a new session.

The event vocabulary is declared once, in src/server/harness/claude/hooks.ts, and read by both installers. The nine events are SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Notification, Stop, SubagentStop, PreCompact and SessionEnd.

3. Module resolution: what was ruled out, and how

The error is a resolution error, so the resolution algorithm is the obvious suspect. It is not the cause, and it can be excluded rather than merely doubted, because the specifier is absolute. Node’s NODE_PATH, the node_modules walk, the nearest package.json and the process working directory are all inputs to resolving a bare or relative specifier. For an absolute path Node performs a file lookup and nothing else, which is why the reported requireStack is empty: there was no requiring parent and no search.

Driven rather than asserted. The same command was run under four conditions that would each change the answer if any search were happening:

Condition variedCommandResult
cwd = /node <old path> StopMODULE_NOT_FOUND loader:1573
cwd = /tmpnode <old path> StopMODULE_NOT_FOUND loader:1573
cwd = $HOMEnode <old path> StopMODULE_NOT_FOUND loader:1573

Five conditions, one identical failure; change the path alone and it succeeds. The resolution algorithm is behaving correctly and the input is wrong. The same reasoning disposes of the neighbouring suspects: the node binary resolves (/opt/homebrew/bin/node is present, and a missing interpreter produces a shell command not found rather than a Node stack), the file is a module entry point rather than an import inside one (the failing frame is executeUserEntryPoint, so nothing inside the script ran), and the .mjs extension is irrelevant because the failure precedes any decision about module format.

The generalisation worth keeping. An absolute path in a configuration file is a promise about the filesystem that no resolution mechanism can rescue. Every install-time convenience that bakes one, and there are several in this product, is a latent version of this incident waiting for someone to rename a directory.

4. A second defect found while confirming the first

Both installers have to find their own entries again, to replace them on a re-run and remove them on uninstall. Each carried its own marker, and the packaged app’s did not match its own script: src/main/integrations.ts searched commands for the string harness-hook, while the script it installs is dist/satellites/hook.mjs, which contains no such substring.

So the desktop app’s Install Claude integrations stripped nothing before appending. Every press added another group to every event, each event fired once per press, and Remove integrations removed none of them. This is the same family of fault as the reported one, in the same file, and it degrades the same way: silently, with the damage accumulating in a file nobody reads.

5. State of this machine now

The machine has since been repaired, by an operator action taken while this investigation was running rather than by anything in the diagnosis. ~/.claude/settings.json was rewritten at 16:24 today and now names the packaged app’s satellite, which is present and executable:

$ ls -l "/Applications/Mission Control.app/Contents/Resources/app/dist/satellites/hook.mjs"
-rwxr-xr-x  1 jordanmance  admin  5091  8 Sep 15:45  ...  /dist/satellites/hook.mjs

$ echo '{}' | node "/Applications/.../dist/satellites/hook.mjs" Stop ; echo $?
0

Nine entries, one per event, all resolving. The symptom is gone. Note that this repair was manual and undetectable: nothing told the operator the machine had been broken, and nothing would have told them if the press had missed.

6. What shipped

The diagnosis was turned into a detection, because the expensive part of this incident was not the broken path but the weeks it survived unattributed.

  • A new environment check, src/server/environment/claude-hooks.ts, reads ~/.claude/settings.json per request and probes the script paths that belong to Mission Control. It reports and never repairs: the daemon reading it may itself be running from a pooled worktree that will be reclaimed, so an auto-repair would be free to cause the outage it just reported.
  • Two existing surfaces carry it. A note in the Dispatch dialog naming the dead path, the number of events affected and both repairs; and a required Claude Code hooks row in Settings → Setup, which raises the setup banner. Both re-read the disk, so both clear when the machine is fixed.
  • Silence by default. No settings file, paths that resolve, a file that cannot be parsed, or another tool’s broken hook all produce nothing. A warning nobody can act on is how a reader learns to stop reading warnings.
  • One shared marker in src/server/harness/claude/hooks.ts, fixing section 4: each installer now recognises the other’s work and replaces it rather than stacking on it.

Covered by 11 new unit tests, 2 new installer tests and 3 new browser tests, and documented in docs/troubleshooting.md under the symptom an operator would actually search for.

7. What this did not establish

  • When the checkout was renamed, and how long the machine was broken. Nothing timestamps the rename, and settings.json has since been rewritten, so its own mtime no longer carries the answer. “Months” is inferred from the old directory name and the surviving ai-harness-old sibling, not measured.
  • Whether any real work was lost. The failing hook is a reporting bridge, so the expected damage is missing session status rather than damaged sessions, but no attempt was made to audit past sessions for consequences of the missing PreToolUse events.
  • The duplication defect in section 4 was not reproduced against a released build. It is established by reading the installer and pinned by a new unit test over the same code path; nobody pressed the button on a shipped app repeatedly and counted the entries.
  • Other baked absolute paths were not audited. The status-line wrapper, the MCP server registration and the OpenTelemetry endpoint are all written into operator configuration by the same installers and are all capable of the same failure. Only the hook path is checked.
  • Nothing was verified on Linux or on a packaged Windows build. Every command above was run on this macOS machine, Node.js v26.7.0.

Diagnosis reproduced on macOS 25.6.0, Node.js v26.7.0, against ~/.claude/settings.json and the checkout at commit aa2412c7. Every command quoted here was run; no output is paraphrased.
