1. What the diagram already answers

Keeping the diagram is not a constraint on the redesign, it is a simplification of it. Drawing it out made that concrete: the stage strip already answers "which stage failed" completely and better than prose could. Session, Stage 1, the Intent Conformance gate, Stage 3, each with a status chip and each member's own chip inside it. Nothing below it needs to restate that.

Which leaves the area below a much narrower job than the four original mockups assumed:

QuestionAnswered byWhat is left for the area below
Which stage failed?The diagramNothing. Do not repeat it.
Which reviewer failed?The diagramNothing. The member chip inside the stage card says so.
Why did it fail?Nothing todayThe verdict summary, and the pattern across rounds.
What is being asked?Nothing todayRequested changes, concise, with the file.
What can I do about it?Partly the headerThe full option set, including the moves that are unavailable and why.
Am I making progress?Nothing todayRound-over-round movement. This is what F is for.

One thing the diagram exposes that the original four missed. Drawing Stage 1 truthfully for this run puts test in the strip as a member of a stage whose status chip reads pass, when the command was never run - it is disabled for this run and auto-passed. In the diagram that is a single amber member chip inside an otherwise green stage, which is very easy to miss at a glance. Whatever goes below has to carry that as a named warning, because the strip alone will not.

10. Recommendation

Keeping the diagram changed my answer from the first revision. Previously I recommended A as the shell with C inside it. Having drawn the strip, E is now the strongest single direction, because it is the only one that treats the diagram as the thing you already like rather than as a header to scroll past.

  • Build E. It makes the page shorter, not longer, which none of the others do. It has no new derivation to invent - the stage-to-attempt mapping already exists to render the strip. And it puts "disable this reviewer" next to the verdict that motivates it, which is the single most useful adjacency on this run.
  • Put A's option list inside E's stage footer, and A's stalemate alarm above it. E as drawn is scoped to one stage, so the run-level facts - budget spent, two reviewers never passed, one gate disabled - need somewhere to live that is not inside a stage. A short run-level strip between the diagram and the stage panel is the right home.
  • Add F second, gated on round 3. It is the highest-value addition on exactly the runs that hurt, and it is invisible on the runs that do not. Its "no net progress for 3 rounds" line is the one sentence on any of these six screens that would have saved the most time on this particular run.
  • Take D's copy-as-checklist regardless. Today's Copy feedback copies the raw delivery payload, which on this run is 4,000 characters with 9 nested repair preambles.
  • Hold B and C. C's matrix is superb but overlaps F once F exists, and F is cheaper. B is the best worklist but the most expensive, and this run has three changes.

Three fixes are worth doing whichever direction wins, because they are defects rather than layout preferences:

  1. Render repeatOffenders on this page. It is already in the payload and already computed, and only WorkflowLadder shows it. "Code Risk Reviewer has failed 10 rounds running" is the most decision-relevant fact on this run and it is not on screen.
  2. Lead the intent section with refined, not rawPrompt. A 155-character sentence is demoted beneath 4,005 characters that are 9 copies of a repair preamble.
  3. Say a disabled gate is disabled, at run level. In the strip it is one amber member chip inside a stage whose own chip reads pass. That is the one thing on the page that can mislead rather than merely bore.

The round scrubber also wraps to two rows at 10 rounds, which mockup A draws honestly. Worth its own fix.

11. What I did not establish

  • These are mockups, not implementations. No component was changed and no test was written. Every screen is static HTML built to the app's own tokens from src/web/styles.css, not a render of WorkflowRuns.tsx.
  • The diagram is redrawn, not reused. I rebuilt the strip from your screenshot plus RunPipeline.tsx and pipeline-bits.tsx, so spacing, the exact menu affordance and the seam treatment are approximations. Stage grouping, the "N reviewers · all must pass" subtitle, the gate labels and the footer sentence are taken from the real component.
