Mission Control · research note · 2026-10-26

Anthropic's single-agent-loop guidance, read against Mission Control

Question as asked: "Read Anthropic's latest Claude prompting guide and tell me how it relates to Mission Control." Source: Building agents: When to fold subagents into your main agent loop, Diane Sarkis, claude.com, published 2026-10-22, read 2026-10-26. It sits in the "Best practices" category and is about agent architecture, not prompt wording, so I treat it as an architecture guide rather than a prompting guide.

Short answer. The article argues for one model, one context window, and progressively disclosed skills and tools, and keeps subagents for three jobs: verification, parallel work, and permission boundaries. Mission Control does not run the agent loop itself. Each dispatched session is already a single loop in Claude Code, Codex or Pi, and Mission Control does not split it into specialists. What Mission Control adds sits around those loops: Foreman, the GitHub Inspector, workflow Personas and ensemble judges.

Against the article, those split into two groups. Personas, the Inspector and ensembles are the patterns it endorses (generator-verifier and parallel candidates split by context). Foreman is the closest match to the failure it describes: a second, cold agent rebuilding from a 60-turn transcript window the context the blocked session already holds. Three other things are worth acting on. The verifiers pay a real handoff cost, which Mission Control covers with evidence registration. The standing instructions Mission Control adds to dispatch prompts are the "Frankenprompt" risk the article names. And a keyword search of docs/, src/ and scripts/ found no end-to-end eval set for Mission Control's own model-driven parts. The article treats that as the first step before changing any of them.

1. What the article says

  • Default to one loop. One model and one context window run an open-ended tool loop with turn, cost and write budgets set in the harness. The model writes its own plan on turn one and revises it. The same model plans and executes.
  • Progressive disclosure. The agent sees short descriptions of skills and tools and loads full detail on demand. The article says Anthropic cut Claude Code's system prompt by over 80% for advanced models, and that starting with Opus 4.5, models can hold much more in one loop.
  • Subagents remain for verification, parallel work and modular permissioning. If you use them, start with generator-verifier or orchestrator-subagent, and divide by context, not by problem type. Each subagent should need little from the rest of the system and return a compact result. Splitting by problem type causes a "telephone game".
  • Named failure modes: subagent sprawl, a conflicting "Frankenprompt", unvetted local evals, lossy summaries at every handoff, and nested model loops that add latency. One customer saw about 2x slower runtime on a multi-agent harness.
  • Tools: group them by user intent. Tool choice degrades beyond 30 to 50 definitions, so use tool search with deferred loading. Move hard preconditions into tools that return actionable refusals, and enforce permissions inside tools.
  • Skills hold how a team does its work. Each team has a DRI, and every skill ships with evals.
  • Evals first: start with one shared end-to-end set (10 golden examples is enough), grade with a rubric, timestamp key events for replay, run each task more than once, and fold in one subagent at a time. Keep it as a subagent only if the folded version scores worse.

4. What Mission Control already does that the article recommends

Verifiers split by context, not by problem type

Personas, the Inspector and the ensemble judge each get a bounded, immutable artifact and return a verdict. That matches the article's rule that a subagent should need little from the rest of the system and return a compact result. The ensemble judge is blind to agent names, models and ordinals (docs/ensembles.md), so its answer cannot drift with the identity of the work's author.

Preconditions live in tools

The MCP tools refuse with a next step instead of trusting the model to sequence correctly. Evidence registration returns a retryable handoff_awaiting_discovery until the successor session is verified. submit_ensemble_result works out who the member is from the calling session and never lets the member name itself. Both match "if Y needs X's output, Y's tool checks for it and returns an actionable instruction".

Shadow measurement before trusting a cheaper path

Foreman's cheap tier has an explicit shadow posture. It runs the cheap tier beside the full review, acts only on the full review, and records every divergence, with cheap-over-eager called out in red (docs/foreman.md, "Cheap tier"). The article's migration loop works the same way: keep the old path, measure the new one, and switch only when the numbers hold.

A smaller root prompt

Commit b6ea3e7 (2026-07-30, "docs(agents): streamline project guidance") cut AGENTS.md from 80,918 bytes to 6,076, which is 92% smaller (figures from docs/agent-guides/inspector-prompt-bytes.md). That file is loaded into every Inspector review and every Foreman verify, so the cut is the same trim the article describes for Claude Code's system prompt.

5. Where it pulls against the article

Foreman rebuilds context instead of verifying an artifact

Foreman answers a question the blocked session asked, using a 60-turn window of that session's transcript plus its pane. The article's concerns all apply: the window is a lossy summary, each call is a nested cold loop (about 61 KB per review in the August token report), and its prompt has its own owner (Library, Personas, Foreman). The difference is that Foreman stands in for the operator, not for a domain specialist. So part of what it does, deciding what to escalate to a human, has no single-loop equivalent. That part is a permission boundary, which the article keeps as a reason for a subagent.

The part it does not obviously cover is Foreman's routine work: implementation trade-offs it "auto-answers ... defaulting to the most correct, secure, non-duplicative option" (docs/foreman.md). A current model holding the full context could often make that call itself if a standing instruction told it not to ask. That is an inference I have not tested.

Verifier handoffs are expensive, and the contract shows it

Because Personas have no repository tools, anything they need has to be packed into evidence by the session. This task's own prompt asks the session to register "complete relevant sections from unchanged authoritative documents", search results, git history patches and a removed-detail-to-owner mapping, because "the reviewers cannot search the checkout themselves". That is the lossy-handoff cost, paid on purpose for an isolated, reproducible verdict. The article supports the trade for verification. It does mean evidence-packing instructions are now one of the biggest standing sections in a dispatch prompt.

Standing instructions come from several owners

This session's one-line request arrived with six appended sections (execution authorization, plan discovery, document task, completion handoff, documentation review evidence, workflow evidence readiness), built in four source files. One of them framed a research question as "write or maintain the requested repository documentation". That mismatch is a small, concrete example of the article's Frankenprompt: instructions written separately, each reasonable on its own, conflicting at the point where they are combined.

No end-to-end eval set found for the model-driven parts

The article makes an eval set the first step before folding anything in. I searched docs/, src/ and scripts/ for "golden", "eval set", "evals/" and "benchmark". Every hit was a code fixture or a telemetry benchmark (test/helpers/workflow-telemetry.ts, scripts/observability/benchmark.ts), not a graded set of Foreman decisions or Persona verdicts. Shadow mode measures one divergence. Within that search I found nothing that scores Foreman, the Inspector or the Personas against known-good answers. A harness under other names or outside those paths would not have shown up (see limits).

6. Experiments the article would suggest

These are the article's method applied here. They are proposals, not findings.

  1. Build a small eval set first. Take about 10 resolved Foreman decisions from its decisions ledger and about 10 completed workflow runs with known-good outcomes. The daemon already timestamps these, which the article names as the raw material for replay evals.
  2. Try folding Foreman's routine tier into the session. Add a standing instruction telling the session to resolve routine trade-offs itself. Run it beside Foreman in a shadow-style comparison, more than once per case, and check which tasks changed, not only the total.
  3. Audit the dispatch standing instructions as one prompt rather than four. The article's /claude-api prompt-audit is built to flag instructions written for older models.
  4. Leave Personas, the Inspector and ensembles as subagents. They are the verification and parallel cases the article keeps. The lever there is how much evidence they need, not whether they exist.

7. What I did not establish

  • I read the article through WebFetch, which returns a model summary rather than raw text. Figures such as "2x slower", "over 80%" and "30 to 50 tools" are as that summary reported them. I did not check them against the page source, and I did not open the migration kit repository it links.
  • I did not measure Mission Control's own latency or cost for any of these paths. The Foreman and Inspector byte figures come from docs/foreman-inspector-token-usage.html, dated 2026-08-07, which predates later changes. For example, that report calls cheap-tier shadow the shipped default, but the current docs/foreman.md says on is the default.
  • The eval-set gap rests on a keyword search. A differently named harness could exist outside the paths I searched.
  • The claim that current models could absorb Foreman's routine answers is an inference from the article, not something I ran.
  • The retrieved article contained no instructions directed at the reader agent. I treated it only as data.
