Sizing and phase count

Estimated non-test production effort is 55 to 110 lines: one database existence helper, one bounded Registry hydration seam, review publication calls through the existing signal, and small copy and documentation changes.

The work is sensitive to ordering and attribution, but it is one compact vertical slice. The estimate is below 200 production lines, so this plan has exactly one implementation phase and one one-shot Mission Control task.

Splitting live settlement from restart restoration would create a merged state that fails the same product promise after a daemon restart.

Delivery flow

There are no parallel groups. The implementation task depends directly on this planning session and remains backlogged until the plan is merged to the default branch.

Compatibility contracts

  • isHumanResolvedReview remains the review authorship authority.
  • The durable settle completes before the Registry is marked.
  • Restoration is per introduced live session and cleanup remains tied to session_remove.
  • The transcript scanner continues to own attributed text turns and feeds the same Registry signal.
  • Session.retro, the corrections reason, and the browser retroOffer predicate remain wire-compatible.
  • Inspector cleanliness remains an independent timing gate.

Verification strategy

  1. Focused Node tests cover live settlement, SDK recording, actor and status negatives, failed delivery or persistence, restart hydration, and eviction.
  2. Existing transcript and offer-predicate tests keep the original evidence source and gate intact.
  3. Playwright answers the fake SDK agent's question through the dashboard, observes the existing retro reason, supplies a clean fake Inspector result, and asserts Run retro appears without a composer correction.
  4. Typecheck, lint, build, smoke, the targeted browser spec, CI, and review gates all pass before merge.
