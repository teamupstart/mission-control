Library · detail screens

Actions

Actions inherit every fault Personas have - no exit, two lists for one choice, chrome above the payload - and add one of their own. An Action is the only Library asset carrying a machine-checked contract: it needs a skill to be present on the session, and something observable has to happen (session_turn, pull_request, repo_commit) before the stage is allowed to call it done. Today that contract is two unlabelled selects sitting in a row of four fields, so the screen never says what it will actually check. Each approach below gives the contract a different shape.

evolve the workbench · smallest diff

Same rail grammar as Personas A - a permanent ← Library row carrying esc, Built-in and Yours groups, one promoted verb and an overflow menu. What is specific to Actions is the contract line under the property chips: the same two values the selects hold, written once as the sentence they form. The rail sub-labels change too, from a description that repeats the title to skill · completion, which is the one thing that distinguishes two Actions from each other at a glance.

smallest change to ship contract is stated, not inferred exit always visible contract still lives in chips you must open to change

pull-request.md MARKDOWN
# Pull Request Prepare the reviewed work as a reviewer-ready pull request. ## What to do Use the invoked pull-request skill to turn the work this workflow just reviewed into one open pull request. Commit everything that was reviewed, push the branch, and open the pull request. This is about one repository and one branch: the repository named in the packet above, or the one you are standing in when it names none. If an open pull request already exists for that branch and its head matches the work you just pushed, update that pull request rather than opening a second one for it.

What changed against today: "Required skill" and "Completes when" stop being two selects in a four-across field row and become chips with a sentence beneath them. The rail sub-label switches from the description - which just repeats the title - to the contract, so Pull Request and Retro are told apart by the thing that differs.

B

Focus

the contract is a sentence you fill in

Same document shape as Personas B - centred column, breadcrumb and a labelled Close, properties collapsed behind a bar that summarises itself. The Actions variant puts the contract above the instruction as a sentence with the controls set into it: "Run this on the bound session, which must have the pull-request skill. Consider it done when a pull request is opened and verified." Both selects are still selects; they are just read in the order that explains them. A completion kind this build cannot prove renders as a dashed, unset slot inside the same sentence, so an unsatisfiable contract is visible as a hole in a sentence rather than a disabled option inside a closed dropdown.

the contract cannot be misread unavailable completion kinds are visible while closed largest writing surface a sentence is harder to scan than a table when you have many no side-by-side comparison

1 of 2 · built-in used by ⌁ No-Mistakes Review

Why the sentence and not a form: the two values are not independent settings, they are one rule with a subject and a predicate. Written as a sentence, "requires retro, completes on repo_commit" is obviously coherent and "requires pull-request, completes on session_turn" is obviously suspicious. Written as two selects two columns apart, neither reads as anything.

C

Sheet

the contract, drawn

Same sheet mechanics as Personas C - the card wall stays behind the app's own rgba(4,6,9,.72) backdrop, Escape and Close both dismiss, you never lose your place. The Actions variant spends its Contract tab on a picture: where this instruction enters the run, which session receives it, what skill has to be present, and what Mission Control watches for before the stages below are allowed to read the evidence. That chain exists today only as prose in a paragraph most people scroll past, and it is the single hardest thing to hold in your head when you are writing a new Action.

the run-time chain is shown, not described Escape is self-evident you never lose your place in the Library smallest writing surface a diagram is one more thing to keep true as the model changes
