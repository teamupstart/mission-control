The review worklist, as a browser drew it

Visual record of the Workflow runs reader pane after the Blocker Worklist replaced the Reviewer verdicts wall. Every image below is a browser capture of a real Workflow run, not a mock-up.

Produced by e2e/specs/workflow-run-blocker-worklist.spec.ts: a real dispatch, a real published workflow, two real review rounds, driven through the dashboard by Playwright. The reviewers are scripted by e2e/fixtures/fake-claude.mjs, so no model tokens are spent. Assembled by scripts/workflow-worklist-evidence.mjs.

MC_E2E_EVIDENCE=1 npm run test:e2e -- workflow-run-blocker-worklist
node scripts/workflow-worklist-evidence.mjs

1. Blocking, with the selected change in full

The agenda. Two reviewers objected in the same words about the same file, so there are two rows - the change key leads with the reviewer that raised it, and each row's actions target that reviewer. The selected one is shown whole: its summary, confidence, runner and model, the file it cites, the round it was first raised in, the rounds it has been open, its rationale and the evidence behind it.

Captured as 01-blocking-leads-with-the-change.png.

2. Passed, where an approval costs a count

The same run, one click away. This is the 1,984 characters of header, summary, approval rationale and evidence list the redesign was measured against - now one line, with the whole verdict still reachable for the reader who asks for it.

Captured as 02-passes-behind-the-count.png.

3. Archive, telling resolved from unconfirmed, beside the stalemate card

The three-elements-agreeing case the design is built around. A green Resolved row naming the round its own reviewer confirmed in; an amber Unconfirmed row claiming neither outcome, because that reviewer ran again and did not pass; and the stalemate card naming that same reviewer. Green on the second row would tell an operator a reviewer is satisfied on the same rail as a card calling it a repeat offender.

Captured as 04-archive-tells-the-two-apart.png.
