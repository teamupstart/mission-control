Implementation plan

Auto-continue interrupted SDK sessions after app restart

When Mission Control restarts, every SDK-runtime session still reattaches to the same Claude or Codex conversation, and any session that was in the middle of a turn automatically continues. Sessions that were already idle restore quietly.

Outcome

The user no longer has to restart or nudge every SDK session after the app comes back. Conversation identity, checkout state, task binding, model, effort, and permission posture remain unchanged.

What happens today

The repository already persists SDK session rows, records clean shutdown as suspended, and runs SdkSupervisor.restore() before terminal discovery. Restore relaunches each live row with its existing harness-native conversation id and registers its card before startup reconciliation.

The missing piece: resume deliberately launches with prompt: "". That avoids replaying the original task, but it restores the conversation without continuing the interrupted turn. Claude waits for a new user turn; Mission Control has no durable, harness-neutral fact saying which restored sessions need that turn.

Design

1. Persist whether a turn still needs completion

Add turn_in_progress INTEGER NOT NULL DEFAULT 0 to sdk_sessions, in both the fresh schema and an addColumn() migration. Project it as turnInProgress: boolean in the SDK store and preserve it when adopting a resumed handle.

This remains separate from lifecycle status: status says whether the driver is running, suspended, exited, or failed; the new bit says whether the conversation owes work after reattachment.

2. Maintain the flag at the supervisor boundary

  • Set it for a new launch whose first prompt is already running.
  • Set it after handle.send() acknowledges a normal or recovery turn.
  • Also set it on driver state: working as a backstop.
  • Clear completed work on structured turn_done evidence; a confirmed successful context reset intentionally clears all outstanding work for the idle replacement.
  • Do not clear it during shutdown or for a pending approval/input request.

The database and vendor process cannot share a transaction, so recovery is intentionally at-least-once across a crash in that narrow boundary. The recovery turn is worded to be idempotent.

3. Continue only interrupted sessions during restore

  1. Read live SDK rows.
  2. Relaunch with resume: row.agentSessionId and an empty launch prompt.
  3. Adopt the handle and register the card.
  4. If row.turnInProgress is true, send one recovery turn through the existing serialized supervisor path.
  5. Leave the bit set until the driver emits the final turn_done or confirms a successful context reset onto an idle replacement.
Mission Control restarted while your previous turn was still in progress. Continue that work from the current checkout and conversation. Inspect the current state before acting, do not repeat completed work, and ask again for any approval or input you still need.

For Claude this starts the continuation turn its resumed stream is waiting for. For Codex, the existing send() behavior steers a still-active resumed turn or starts a new turn if the restored thread is idle. The supervisor needs no harness-specific branch.

4. Keep failure and task semantics unchanged

  • Unresumable conversations still register and evict so session_remove settles durable bindings.
  • Idle suspended sessions relaunch without receiving unsolicited work.
  • Restore remains before startPoller(registry).
  • No web protocol or layout changes are required.

Verification

  1. Upgrade migration adds the column with default 0.
  2. First prompts and acknowledged follow-ups persist 1.
  3. turn_done persists 0.
  4. Clean shutdown preserves unfinished work while status becomes suspended.
  5. Interrupted Claude and Codex sessions receive one continuation in a daemon lifetime.
  6. Idle restored sessions receive nothing.
  7. A second restart before completion retries recovery; a restart after completion does not.
  8. Failed resume still takes the existing eviction and task-settlement path.
  9. Clearing an active Codex thread confirms an idle replacement, persists 0, and a restart sends no continuation.

Run the focused SDK/database tests, then the repository typecheck and full test suite.

Non-goals

  • Replaying the original task prompt.
  • Persisting vendor approval request payloads; the agent asks again after recovery.
  • Changing terminal-runtime sessions.
  • Adding a user setting in the first version.

Decision

Adopted: auto-continue only SDK sessions whose durable row says a turn was in progress. Restored sessions that were intentionally idle receive no unsolicited work.
