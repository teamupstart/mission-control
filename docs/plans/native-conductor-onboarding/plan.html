Native integration

Conductor should always have a front door.

Settings becomes the permanent place to install the machine-wide engine, register each repository, and grant Mission Control observation. Setup becomes visible without weakening the repository-specific gate that makes Pipeline appear in Dispatch.

Product decision

Always show Conductor in Settings, deep links, search, and the command palette.

Readiness boundary

Runs and Dispatch stay gated by active observation of the exact repository.

Decision

Make Settings → Conductor permanent. Use the page to explain and perform three separate acts: install the engine once on the machine, register a repository through Conductor's CLI, and grant Mission Control permission to observe it.

Dispatch does not become global. Pipeline appears only when the selected main repository is in activePipelineRepos(config). Always-visible Settings repairs discovery; it does not bypass consent.

The recommended repository action is Register and observe. Registration runs first. Mission Control writes its own observation consent only after the provider confirms the canonical path. If that second write fails, the row reports partial success and offers a focused recovery action.

Why this boundary

The current design hides setup behind evidence that setup already happened. A native integration needs a stable front door. It must also teach the actual scopes: installation is machine-wide; registration is per repository in Conductor's registry; observation is separate Mission Control consent.

  3. The panel offers only provider-reported or already-configured repositories. It omits unregistered workspace repositories: src/web/components/ConductorPanel.tsx:134.
  4. The shared inventory and canonicalization already exist at src/server/repos.ts:80, src/server/repos.ts:123, src/server/routes.ts:2323, and src/server/routes.ts:2328.
  5. The provider seam already owns CLI composition and forbids direct provider-file writes: src/server/pipelines/types.ts:139 and src/server/pipelines/conductor/index.ts:355.

This supports a visible terminal ceremony, not a silent HTTP mutation: bin/install:7, bin/install:591, bin/install:693, and bin/install:1331 in ai-conductor.

Intended experience

The rail row, hash route, and palette entry always exist. An amber dot can mean setup needs action; green means at least one repository is actively observed. Missing software is incomplete setup, not an error.

State 1

Engine missing

Say: Install Conductor once on this machine. Repositories are registered separately.

When a verified local ai-conductor main checkout exists, confirm it and open bin/install in a hosted interactive terminal. Otherwise provide copyable clone/install instructions and an explicit recheck.

State 2

Repo unregistered

Merge the workspace repository catalog with provider projects and configured rows. A searchable picker offers unregistered repositories.

Register and observe resolves the main root, runs the provider CLI without a shell, verifies exact output, probes again, then saves observation consent.

State 3

Registered, not observed

The row clearly separates provider registration from Mission Control permission. Enable observation recovers a partial setup without repeating the provider mutation.

State 4

Dispatch ready

Keep the current health, ingest, master switch, per-repo switch, and Foreman controls. Show registered, observed, and dispatch-ready as distinct facts.

Installer candidate rules: a real main checkout, not a linked worktree; expected installer and package markers; and a recognized upstream remote or future explicit trust grant. Detection is read-only. Only the user's click launches it.

Data and request flow

Registration belongs on the provider axis. Extend PipelineProvider with a narrow registerRepo(repoRoot) capability and a typed result. Do not compose an ai-conductor command inside routes.ts.

Installation is a different kind of action: an interactive terminal ceremony rooted in verified source. Reuse the typed terminal targets and launcher. The browser submits only a provider id, detected checkout, and terminal backend; it never sends argv or shell text.

Implementation slices

01 / Discoverability

Remove category gates

  • Make Conductor navigation and palette indexing unconditional.
  • Keep SettingsStatus.pipelines.present wire-compatible as detection if a rail dot consumes it.
  • Keep pipelines.observing unchanged as the Runs gate.
  • Remove the minute presence cadence only if it has no remaining reader.
02 / Contracts

Model setup explicitly

  • Add provider registration and typed Zod request/result schemas.
  • Resolve and canonicalize every path server-side.
  • Add read-only verified installer-candidate detection.
  • Bound process duration and captured output.
03 / Interface

Build native states

  • Merge workspace repos, provider projects, and configured rows.
  • Add the commissioning line and contextual setup card.
  • Serialize setup actions with existing optimistic config writes.
  • Never hide existing cleanup controls when detection fails.
04 / Alignment

Refresh Dispatch and docs

  • Refresh active pipeline repos after Register and observe.
  • Keep exact-repository Dispatch eligibility.
  • Rewrite docs/pipelines.md around machine, registry, and consent scopes.
  • Remove the current absent-by-default promise and stale phase notes.

Failure and safety contract

  • No direct registry writes. conduct-ts register remains the only Conductor registry writer.
  • No browser-supplied commands. Provider and server code compose all argv.
  • No silent global installation. The first release does not clone or install in the background.
  • No worktree installation. Use verified main checkouts and canonical main repository roots.
  • Validate outcomes. Require exit success, exact bounded output, and a fresh provider probe.
  • Report partial completion. Never call registration plus failed observation complete.
  • Preserve reversibility. Disabling observation does not deregister provider state.

Tests and evidence

Unit and route contracts

  • Invert settings registry, sidebar, deep-link, and palette tests: Conductor exists without engine or config.
  • Cover exact registration argv, missing binary, invalid repo, worktree resolution, bad exit, misleading zero-exit output, truncation, timeout, idempotence, and canonical confirmation.
  • Cover schema refusal, force-probe, consent success, and registered-but-not-observed partial failure.
  • Cover candidate union and keep stale configured rows visible for consent withdrawal.

Browser contract

Update e2e/specs/settings-conductor.spec.ts and its fake engine for:

  1. No-engine rail, palette, deep-link, and machine-scoped guidance.
  2. Installer checkout confirmation and a faked hosted-terminal request.
  3. Workspace repository selection and fake CLI registration.
  4. Partial failure and Enable observation recovery.
  5. Pipeline absent for other repos and present for the exact observed repo.
  6. Narrow layout, keyboard order, accessible names, and non-color status cues.

The fake intercepts registration and installation, spends no model tokens, and performs no user-level mutation. Use roles, labels, and placeholders; add no data-testid.

Validation ladder

Run focused pipeline/settings tests, then npm run typecheck, npm run lint, npm test, npm run build, npm run smoke, and npm run test:e2e. Preserve browser evidence for missing-engine, registration, ready, and partial-failure states in a gitignored location.

Non-goals

  • Bundling ai-conductor inside Mission Control or becoming its package manager.
  • Silently cloning, downloading, upgrading, uninstalling, or registering every repo.
  • Writing any provider-owned registry or pipeline state directly.
  • Showing Pipeline in Dispatch for an unobserved repository.
  • Starting a pipeline as part of registration.
  • Deregistration, upgrade management, or a multi-provider marketplace in the first release.

Confirmed product decisions

The 2026-08-17 continuation approved both recommendations and authorized implementation phasing, task scheduling, and publication of the plan artifacts.

Approved

Guided terminal install

Launch the upstream interactive installer only from a verified local main checkout. Fall back to copyable instructions when no checkout exists. A fully managed download waits until source trust, networking, versions, updates, and rollback have a policy.

Approved

Register and observe

One explicit action performs the provider registration, then Mission Control consent, with honest partial-success handling. Register-only is simpler but leaves Dispatch in the same surprising state that motivated this plan.

Follow-up approved: create merge-aware implementation phases and schedule their dependency-linked tasks after these artifacts are published.
