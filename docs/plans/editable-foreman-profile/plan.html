Mission Control plan

Editable Foreman profile

Approved on 2026-08-15

Outcome

Give Foreman a first-class, editable profile beside Personas in the Library without turning it into a workflow Persona.

The profile lets an operator read, preview, replace, clear, copy, download, and restore Foreman's standing guidance. It also makes the current provider and model-role configuration easy to find. Foreman's identity, built-in operating policy, safety boundaries, protocol grammar, and eligibility remain owned by Mission Control and cannot be changed through the profile.

The intended result is:

  • Foreman appears under a distinct System group in Library -> Personas.
  • Its fixed identity is visibly different from built-in and operator-authored workflow Personas.
  • Its standing Markdown is editable with the same quality of draft, preview, conflict, keyboard, copy, download, and reset interactions as the Persona editor.
  • Operational and authority-bearing controls retain one owner in the top-bar Foreman control, Settings -> Foreman, and Settings -> Trust.
  • Foreman never enters the Persona catalog consumed by workflow stages or ensemble evaluators.
  • A save affects the next Foreman evaluation, while an evaluation already in flight finishes with the exact guidance it captured at its start.

Approved decisions

  • Profile location: add a System guidance profile in the Persona Library. Existing Settings, top-bar, and Trust surfaces continue owning typed model, operational, and authority controls.
  • Save semantics: keep one current, exact-text document with compare-and-swap conflict protection. Do not add immutable version history or an activation step.
  • Prompt coverage: preserve the current guidance surfaces only: triage, full review, queued-work verification, and prompted completion verification. Do not add guidance to backlog dependency planning.
  • Follow-up: decompose this approved plan into merge-aware implementation phases and schedule one task per phase. Keep every task disabled so backlog automation cannot pull it, and pin each task to Codex gpt-5.6-sol with xhigh reasoning effort.

Why this is smaller than the older Persona versioning plan

docs/plans/persona-versioning-and-foreman/plan.md proposed extracting a shared Persona domain, adding immutable Persona versions, migrating every workflow draft, changing ensemble references, and representing Foreman as a non-stage-eligible database Persona. The repository has changed since that plan was written:

  • Persona authoring now has an independent home in the Library rather than under Workflows or Settings.
  • Operator Personas still use one mutable row with a compare-and-swap revision.
  • Workflow publication already snapshots exact Persona content for durable execution.
  • Foreman's standing guidance already has a dedicated storage and prompt-injection seam.
  • No current consumer needs Foreman to share the workflow Persona store.

This plan therefore does not make general Persona versioning a prerequisite for editing Foreman. It reuses the current product semantics: one current editable document protected against stale writes, with immutable workflow snapshots remaining a separate concern. The older plan remains a possible future expansion for Persona history, but its broad migration is not required here.

Editable and application-owned boundaries

The central rule is that prose may shape judgment but may not grant authority or rewrite the protocol that makes Foreman safe and compatible.

Standing guidance continues to be a one-way ratchet. It may make Foreman more careful, move an ask away from automatic approval, or raise the definition of complete. It cannot make Foreman less careful, authorize a destructive action, bypass a typed switch, dictate a literal message, or redefine the JSON it must return.

This change does not add standing guidance to the backlog dependency planner. It preserves the current prompt coverage: triage, full review, queued-work verification, and prompted completion verification.

Product experience

Library entry and routing

Add a fixed foreman asset under #/library/personas/foreman. The Persona rail becomes three groups: System, Built-in, and Yours. The System group always contains one Foreman row.

The row is sourced locally by the Persona Library and is not appended to streamed PersonaView[]. Its sub-label names its effective provider and four model roles. A System tag and tooltip state that it is unavailable to workflows and ensembles. The Library front-page Personas shelf also shows a System card without changing the count of workflow Personas.

Foreman profile editor

Use the Persona workspace's visual language without forcing Foreman through PersonaEditor's data model. A focused ForemanProfileEditor reuses the workspace header, file editor, Markdown preview, property chips, overflow menu, copy feedback, and unsaved-change navigation guard.

  • Fixed name Foreman, fixed description, and System profile identity.
  • Source chip: Built-in default, Customized, or No standing guidance.
  • Provider/model summary linked to Settings -> Foreman -> Models.
  • Authority summary linked to the top-bar Foreman control and Settings -> Trust.
  • Character usage against the existing 64,000-character ceiling, plus Edit and Preview modes.
  • Promoted Save, with Copy Markdown, Download FOREMAN.md, and Reset in the overflow menu.

There is no Rename, Duplicate, Archive, Delete, or Re-import action. Duplicate would imply that standing preferences are a complete workflow reviewer prompt when they are only an overlay on Foreman's fixed policy.

Reset requires confirmation when it discards a custom or empty saved state. Clearing and saving stores No standing guidance. Reset restores the shipped default.

Cross-links, not duplicate owners

Add a compact Standing guidance card near the stable posture in Settings -> Foreman. It reports the current source and opens the Library profile. The Library profile links back to Models, posture, and Trust.

Provider/model fields remain in Settings; authority and scheduling controls remain in their current top-bar and Settings homes. This keeps one writing surface per value.

Persistence and API contract

Keep the existing value and add compare-and-swap

Continue storing the exact custom string in app_config["foreman.instructions"] and null for the built-in default. Do not add a Persona row, a second text key, or a database migration.

Build a stable ETag from the source discriminator and exact effective bytes. Including the source prevents custom text identical to the default from being mistaken for the built-in state. The ETag supplies stale-write protection without changing the storage shape or losing downgrade readability.

interface ForemanInstructionsView {
  text: string;
  defaultText: string;
  source: "builtin" | "custom" | "none";
  etag: string;
}

type ForemanInstructionsUpdate =
  | { expectedEtag: string; text: string }
  | { expectedEtag: string; reset: true };

The schema must preserve exact text, accept empty text, distinguish Reset, require expectedEtag, return HTTP 409 with the current view on stale writes, and reject malformed, oversized, or non-loopback requests before storage changes.

Keep GET /api/foreman/instructions as the worker and editor read. Keep PUT as the one CAS-protected mutation. The worker projects only text; the browser consumes the full view.

The editor fetches the document when selected and when the browser window regains focus. A clean editor adopts a changed ETag. A dirty editor preserves every local byte and shows an explicit conflict. No 64 KB document enters the global SSE snapshot or four-second Foreman poll.

Runtime atomicity

  1. The worker requests the effective text once while gathering an evaluation's inputs.
  2. Shadow triage and full review receive the same captured string.
  3. A verification call receives the one string gathered for that verification.
  4. A save during a model call does not mutate the in-flight prompt.
  5. The next evaluation reads the newly saved state.

instructionsSection() remains the only way editable prose enters a Foreman prompt.

Data and request flow

Workflow and ensemble exclusion

Do not add a stageEligible flag merely to filter Foreman back out of a catalog it does not need to enter. Use separation as the primary invariant:

  • PersonaManager.list(), personaCatalog(), Registry snapshots, and persona_upsert never contain Foreman.
  • /api/personas and /api/personas/:id do not resolve the fixed Foreman id.
  • PersonaView and the personas SSE collection remain workflow Persona contracts.
  • The Library alone composes its local System entry with streamed workflow Personas.
  • Workflow and ensemble validation reject a forged Foreman reference as an unknown Persona.

Implementation workstreams

1. Harden the standing-guidance contract

  • Add shared view and CAS update schemas.
  • Return source-aware views and compute exact-byte ETags without changing stored compatibility.
  • Update routes, body limit, 409 response, and loopback tests.
  • Keep the worker reading only text and degrading to fixed policy alone on a read failure.

2. Add the System profile to the Library

  • Add a focused API helper and ForemanProfileEditor without widening PersonaView.
  • Compose the fixed System row into the rail and add the front-page card and canonical route.
  • Reuse the file editor, preview, header, property chips, copy feedback, confirmation, save shortcut, and navigation guard.
  • Implement clean refresh, dirty conflict, empty-save, character limit, reset, copy, and download states.

3. Connect existing configuration owners

  • Add a source summary and profile link to Foreman Settings.
  • Link profile summaries back to Models, posture, and Trust.
  • Keep typed config writes on ForemanConfigPatchSchema.

4. Lock the boundary with tests and documentation

  • Cover default, custom, empty, reset, exact text preservation, conflicts, malformed/oversized input, and missing seed behavior.
  • Cover the System rail, fixed identity, allowed actions, source states, links, and conflict copy.
  • Assert that API catalogs, SSE, workflow choices, graph validation, and ensemble choices never admit Foreman.
  • Add a Playwright profile flow with no model or agent call.
  • Update README and the Foreman, Library, workflow, and personas documentation.

Explicit non-goals

  • General immutable Persona history or activation.
  • Migration of workflow drafts or ensemble evaluator references.
  • Making Foreman a workflow node, Persona evaluator, or plugin-imported Persona.
  • Editing built-in prompts, policies, schemas, or delivery grammar.
  • Per-repository or per-session Foreman guidance.
  • Changing which model roles receive standing guidance.
  • Moving authority-bearing controls into Markdown.
  • Changing worker startup, leases, retention, caps, concurrency, or transport.
