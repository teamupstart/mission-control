Repository findings

  • src/server/retro.ts currently chooses live delivery before considering task pull-request posture.
  • primaryRepoPrForTask already supplies durable merged history across current and historical work episodes.
  • Resumed work can reverse an idle-inferred task completion, so the retro must not continue inside the completed feature task after merge.
  • Historical merge evidence can settle later work if episode identity is blurred. The retro therefore needs its own task episode and PR binding.
  • The retro skill's current “never open a second PR” rule needs an explicit open-versus-merged branch.
  • RetroResponse permits additive arms, while existing clients currently assume only delivered or dispatched.
  • No narrow agent-callable outcome exists for a correct retro that produces no commit.
  • The existing Playwright retro-offer spec already drives the real browser-to-daemon flow with fake agents and local hooks.

Why one phase

The estimated 400 to 600 non-test production lines span several layers, but they form one transactional vertical slice. Splitting would publish either tasks that cannot finish without a fake pull request, a UI that cannot explain what the route did, or an MCP completion tool no launched retro can use.

The work is larger than the 200-line one-shot threshold, but no independently operable merge boundary reduces risk. Storage, route orchestration, launch outcome, no-change settlement, wire vocabulary, and dashboard behavior must agree in the same merged commit.

Open the detailed implementation guide. It owns the durable link, task dispatch, conditional shipping procedure, no-change MCP outcome, response/UI changes, tests, and documentation.

Only one implementation task is scheduled. It depends directly on the current planning session and cannot release until this planning pull request merges.
