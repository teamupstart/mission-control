Mission Control / dispatch incident / 2026-08-15

Dispatches are waiting behind cleanup

Question: Why do newly dispatched tasks disappear and never appear to be scheduled?

Finding: dispatch acquisition is blocked behind a long Treehouse startup-cleanup queue. Restarting the daemon during that wait marks every in-progress dispatch as failed, moving it out of the active scheduling surfaces. The task records are persisted; they are not deleted.

Finding

This is a lock convoy in worktree lifecycle management, amplified by restart recovery and made confusing by the asynchronous dispatch UI.

Primary cause

On startup, TaskManager starts reconciliation for every resource-holding terminal task without awaiting or bounding the batch. Each pooled teardown queues a Treehouse return behind the same per-repository lock used by new worktree acquisition. With 47 terminal task rows still holding pooled worktrees, acquisition can sit behind many minutes of cleanup even when treehouse status already shows available slots.

Why tasks appear to disappear

The create route returns once the task row exists, while worktree provisioning continues in the background. The modal closes on that successful create response. If the daemon restarts before provisioning finishes, startup reconciliation changes the task from dispatching to failed. It then leaves the backlog and active dispatch views and appears only among recent terminal outcomes.

The live task submitted at 21:25:51 remained dispatching with no worktree, provider, session, or error through repeated reads roughly nine minutes later. During those reads, the daemon process repeatedly had a treehouse return … child. That places the wait before worktree registration and agent launch, at the exact shared-lock boundary described by the source.

Failure flow

Evidence

1. Database state

A read-only query against ~/.mission-control/harness.db found three tasks created between 21:17 and 21:23 with identical transition time and error:

status = failed
updated_local = 2026-08-15 21:24:05
error = dispatch interrupted by a restart - Focus or Cancel it
worktree_path = NULL
provider = NULL
session_id = NULL

The same database initially contained 47 terminal tasks whose provider='treehouse' and worktree_path IS NOT NULL: 36 done, 8 failed, and 3 cancelled. Forty-six of those joined to exited SDK session rows. By the final 21:35 read, the terminal worktree count had risen to 48 as another task completed.

2. Live process and pool state

The daemon listening on port 7317 was PID 48460. Repeated process snapshots showed it spawning treehouse return against different pool slots. Two examples were slot 76 alive for 21 seconds and slot 37 alive for 22 seconds. A live pool count reported 49 leased and 5 available worktrees. Despite those available entries, acquisition remained blocked because returns and gets share the in-process per-repository lock.

3. Source path

  • create A new immediate task is stored as dispatching, then Dispatcher.dispatch is fired without awaiting it: src/server/tasks.ts:1405–1425.
  • ui The dispatch modal treats successful row creation as submission success and closes while provisioning continues: src/web/components/DispatchModal.tsx:1803–1829.
  • acquire Dispatch must finish provisionAll before it records a worktree on the task: src/server/dispatcher.ts:260–280.
  • lock Both treehouse get and treehouse return are serialized by withPoolLock: src/server/pool-lease.ts:123–164 and src/server/dispatcher.ts:1448–1456.
  • recovery The constructor starts reconcileOnStartup for every dispatching or resource-holding task with void, producing an unbounded batch of cleanup work: src/server/tasks.ts:436–447.
  • restart An interrupted pre-worktree dispatch is deliberately moved to failed: src/server/tasks.ts:2927–2977.
  • visibility Terminal tasks are retained, but they are no longer backlog or active work; only the recent terminal projection reloads them for outcome surfaces: src/server/db.ts:4892–4914 and src/server/registry.ts:753–757.

What is not causing this

  • Foreman is enabled. Persisted config has enabled=true, mode=live, autoBacklog=true, a repository allowlist containing this checkout, and maxSessions=9.
  • The task rows were accepted. The API-to-database seam is working. Each affected task has a durable id, timestamps, title, status history, and restart error.
  • Agent binary or SDK launch was not reached. The affected rows never acquired a worktree, so there is no evidence of an agent binary failure, runtime refusal, prompt delivery failure, or SDK supervisor failure.
  • Pool capacity alone is not the live blocker. Five pool slots were already available during observation. The daemon still could not acquire one because its own cleanup calls occupied or queued ahead of acquisition on the same lock.

Immediate recovery

Do not restart the development stack again while cleanup is draining.

Another restart fails the current dispatch and starts startup reconciliation again for every task whose cleanup did not finish.

  1. Leave the current daemon running until its treehouse return queue stops and the current dispatching task either acquires a worktree or reports a concrete failure.
  2. Find the three failed submissions under recent outcomes. Because they have no worktree, provider, or session, the server permits a clean re-dispatch after the pool queue clears.
  3. If an operator chooses to reclaim leases manually, verify each target is idle, clean, merged, and not pinned before returning it. A forced return is destructive. This investigation did not perform any return, cleanup, cancellation, or task mutation.

Recommended product changes

  1. Give acquisition priority over background reconciliation. Startup cleanup should not place dozens of teardown operations ahead of a human dispatch on the same repository lock.
  2. Bound startup cleanup. Reconcile resource-holding tasks through a small queue instead of launching every cleanup concurrently with void. The bound should be per repository because that is the lock domain.
  3. Stop dry-pool recovery after it creates capacity. The dispatch path currently completes a full reap before retrying get. A waiting launch only needs one safe slot, not an exhaustively cleaned pool.
  4. Expose the dispatch phase. Keep the task visible as “waiting for worktree cleanup” with the count ahead of it. If row creation closes the modal before launch, the card must carry the asynchronous failure and progress prominently.
  5. Make pre-provision restart recovery retryable by default. A task with no worktree, provider, home, or session is known not to have launched. Consider restoring that narrow state to backlog instead of terminal failure, while preserving the conservative behavior once any launch resource exists.
  6. Add a regression test for the convoy. Seed many resource-holding terminal tasks, hold teardown returns, submit a new dispatch, and assert that acquisition can proceed without waiting for the entire cleanup batch. A browser spec should also assert the user-visible waiting state because the current symptom is a disappearing task.

Limits and unanswered questions

  • The shell could not connect to the loopback daemon from inside its sandbox, so live HTTP responses and the dashboard DOM were not captured. The listening process, database WAL activity, process children, and Treehouse pool were inspected directly.
  • The investigation established that make restart began at 21:24:02. It did not establish whether a person, script, or higher-level workflow invoked it.
  • The reason each individual Treehouse return took 20–30 seconds was not isolated. Large cleanup work, process termination, and Treehouse behavior are possible contributors. The dispatch blockage does not depend on which of those made the return slow.
  • No destructive validation was performed. In particular, no lease was returned, no task was cancelled or re-dispatched, and no process was stopped.
