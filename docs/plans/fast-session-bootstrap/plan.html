Paint the Board before session restore finishes

Serve the ordinary Mission Control dashboard as soon as the daemon owns its state and routes, project persisted SDK sessions as inert restoring cards, and replace each with its real card as the driver resumes.

ONE VERTICAL IMPLEMENTATION SLICE

Status and approved direction

The operator directly selected phased implementation of the restoring-card approach. The existing Starting strip supplies visual precedent, but its dispatching-task projection is not reused as session authority. There are no unresolved choices.

Problem

The Electron window points at the daemon origin, but the daemon currently restores every resumable SDK session before binding HTTP. Each persisted row may start a subprocess, initialize its protocol, resolve configuration, and resume its conversation before the next row starts.

Desired outcome

  • The installed app paints its ordinary frame and Board near the non-restore baseline.
  • Each readable persisted live SDK row appears immediately with stable identity, title, agent, and repository context.
  • Restoring cards are visibly provisional and have no selection, actions, composer, workflow controls, drag target, alert, or automation eligibility.
  • Each provisional card hands off one-for-one to the real card.
  • Terminal discovery and first-observation reconciliation remain gated until every SDK row succeeds or follows existing failure eviction.
  • Dashboards connecting at any restoration point converge without a lost SSE update.

Repository findings

HTTP is behind restore

src/server/index.ts awaits SDK restore before the poller, route construction, static middleware, and serve(). React cannot load during that await.

The real invariant

SDK sessions must register or evict before the first completed terminal observation. HTTP itself does not need to wait.

Ghost rows are tasks

StartingStrip renders dispatching tasks without a session id. Restoring SDK rows are durable sessions without a live driver, so they need a separate transient view.

SSE has a startup gap

The handler snapshots before subscribing. Background adoption makes an event in that interval observable and potentially lost.

The merged state-home lock remains before SQLite and HTTP. The current browser's hasSnapshot distinction may supply an honest fallback after React loads, but it cannot solve the packaged black interval on its own.

Approved design

1. Add a transient restoring-session projection

Add a minimal browser-safe view keyed by stable SDK session id. It carries only facts available before launch: known agent, restored name, cwd/repository, optional task identity/title, created time, and minimal restore presentation state. It is bounded by readable live sdk_sessions rows, rebuilt on every boot, never persisted, and excluded from normal session counts and automation.

2. Split preparation from driver restoration

Read and classify persisted rows once. Publish views before HTTP, then process the same prepared rows asynchronously and serially. On success, the real session_upsert wins before the provisional row retires. On failure, existing registerAndEvict() runs first. No teardown path is added.

3. Serve early and gate discovery

Build routes and bind HTTP after state ownership, database initialization, managers, and restore-view preparation. Start serial SDK restore after the listener succeeds. Start terminal discovery only when that promise settles. Keep an owned promise so shutdown launches no later row and cleans an in-flight launch through the supervisor.

4. Render an inert Board bootstrap

Use the Starting strip's provisional visual language, but render a dedicated, non-interactive component in the repository group where the real card will land. A real session with the same id suppresses the restoring card. Real Board, Line, Sitrep, search, and alert counts stay unchanged.

5. Close the SSE race

Subscribe before snapshot capture, queue while the snapshot is written, and drain in order. Keyed duplicate upserts and idempotent removes are safer than a missing transition.

Data and request flow

Failure and compatibility behavior

  • A failed port bind starts no background driver restore.
  • Unreadable future SDK statuses remain untouched and are not falsely presented.
  • Unresumable live rows still register and evict so durable subscribers settle.
  • Shutdown starts no later prepared row and leaves no disposable home, marker, credential, or child behind.
  • No schema or migration changes; projections rebuild from existing rows.
  • Vite development keeps the same API/SSE origin.

Verification strategy

Focused contracts

Test row classification, one-time serial consumption, success/failure retirement ordering, discovery gating, shutdown during delayed resume, bounded snapshots, and mutation during initial SSE delivery.

Built browser restart

Use a resume-only delay in the fake SDK agent. Dispatch and settle a session, crash and restart the built daemon, prove health and the Board answer while resume is held, inspect one inert restoring card, then prove exactly one real card replaces it. Capture both visual states.

Documentation

Update architecture startup ordering and packaged-app behavior. State that restoring cards are not live sessions and health does not mean every driver is ready.

Non-goals

  • No parallel resume, new persisted status, schema, migration, browser polling, second endpoint, or local loading app.
  • No synthetic real sessions and no restoring rows in fleet counts or automation.
  • No change to terminal discovery cadence, durable cleanup, or health meaning.
  • No absorption of the unrelated uncommitted loading-spinner worktree.

Success criteria

  • The built server serves health and the Board while a fake SDK resume remains delayed.
  • One inert restoring card appears per readable live row, followed by exactly one real card.
  • First terminal observation remains after restore settlement.
  • Failures and shutdown use existing owners without stranded state or resources.
  • SSE initial delivery cannot lose a concurrent mutation.
  • Focused tests, typecheck, lint, full unit tests, build, smoke, and Playwright pass.

Approved implementation direction: serve early, restore in the background, and keep provisional state explicitly non-authoritative.
