Mission Control scout report

The evidence preflight loop is fed by its own output

Question asked: Evidence preflight sent the "Update Retry pi models login prompt" work back for repair many times. Do we require new evidence to be collected for every submission? If sufficient evidence was provided on a prior run, reattaching it seems excessive unless recent changes could have corrupted it. How do we make evidence sufficient more reliably and cut the token spend of preflight kickbacks?

Short answer to the question as asked: yes, the system does require freshly staged evidence for every submission, and it should not. Staged evidence is consumed one way at capture (staged to reserved), so the next submission starts from an empty tray. Re-staging a byte-identical item is a silent no-op that does not attach it, and re-staging under the same id throws "already reserved", which is why the agent had to mint fresh id prefixes (repair-2-, g5-, g6-, r7-, r8-) every round. On this one task, 70 evidence registrations produced only 28 distinct artifacts, and the same screenshot was registered nine separate times.

But that is the second-order problem, not the reason this task looped. The dominant cause is a closed feedback loop. Mission Control types its own repair packet into the session; the Claude UserPromptSubmit hook captures it as a human instruction into session_goals.prompt; context compaction reads exactly that column as its raw goal and derives the acceptance criteria from it. From submission 3.1 onward the No-Mistakes Review was reviewing the change against criteria distilled from its own complaint text. Six of the eight failing verdicts on this run were artifacts of that loop, not findings about the code.

The displayed goal is not the polluted one, and that is why this is invisible. session_goals keeps four separate columns. The dashboard renders text, the durable objective, which captureAcceptedPrompt writes only on the first prompt. Across all 16 sessions on this machine, text and objective are clean in every single one. It is prompt and focus, which nothing renders under the title, that get overwritten, in 6 of those 16 sessions, and prompt is the one the workflow reads.

The causal chain

Five independent mechanisms compose into one loop. Each is small; together they made an eight-round review out of a two-finding change.

1. Delivered packets land in the Goal column the workflow reads

This session is an SDK session (sdk:1a43686b), and an SDK session has two doors into the Goal pipeline. The supervisor door is guarded: deliverToDriver passes a goal-capture payload to supervisor.send only when origin === "human", and runtimePromptInjector, which is what the workflow manager is wired with at src/server/index.ts:307, never supplies an origin at all. So the supervisor correctly declines to capture a workflow delivery.

The second door is not guarded. The delivery still reaches the Claude CLI, which fires UserPromptSubmit, and captureHookGoalPrompt forwards whatever the hook reports to captureAcceptedPrompt. Its only guard is isSeededLaunchEcho, which the code's own comment scopes to the launch echo at work-cycle generation zero. Everything after that is captured. The delivery path does record the text as machine-authored through rememberInjection(session.id, payload, "workflow"), but it does so after inject() has resolved, and the Goal pipeline never consults originOf in any case: only transcript-attribution.ts, scouts/prompt-collector.ts and retro-worthiness.ts read that origin memory.

captureAcceptedPrompt then writes prompt, focus and promptRevision on every call, but writes objective and text only when firstObjective is true. That asymmetry is deliberate and is exactly what makes the defect invisible on the card while still reaching the workflow.

src/server/registry.ts:7350 · src/server/registry.ts:7399 · src/server/registry.ts:7433 · src/server/sdk/deliver.ts:62 · src/server/index.ts:307 · src/server/workflows/manager.ts:5859 · src/server/injections.ts:115

One latent consequence worth naming. The reconciler may change the objective when it classifies a prompt as amend, replace or initial (src/server/goal/refiner.ts:299). Nothing has been promoted yet, which is why the cards are clean, but three workflow packets are sitting in that queue right now, and each one costs a refiner call to classify text this system wrote itself.

2. The overwritten Goal is the only input to acceptance criteria

intentFingerprintFields returns exactly { rawGoal, refinedGoal, decisions }, and that object is both the entire compaction prompt and the entire intent fingerprint. When rawGoal becomes a repair packet, the canonical acceptance criteria become a restatement of the complaint. The refined goal survived at a constant 72 bytes throughout this run, so a stable description of the work was available and simply was not the field being read.

src/server/workflows/context.ts:201 · src/server/workflows/context.ts:477 · src/server/workflows/context.ts:923

3. Because the fingerprint moves, criteria reuse never fires

reuseWorkflowContextCriteria exists precisely to hold criteria stable across preflight refinements, and it is gated on the child's intent fingerprint matching its parent's. On this run the fingerprint changed on all eleven submissions, so the optimisation never fired once: every submission paid for a fresh compaction call, and the criteria set drifted from four items to three to six to five to seven and finally to two. The author is asked to map coverage onto a target that moves underneath them.

src/server/workflows/context.ts:596 · src/server/workflows/manager.ts:6023

4. Repair packets also leak in as "human decisions"

transcriptDecision treats any user-role transcript turn whose origin is undefined as a human decision. Attribution is best-effort: it matches a delivery to a turn only when the delivery recorded a transcript anchor and the payload fingerprint still matches within a twelve-message window, and the origin memory is in-process and bounded. Whatever slips through becomes a decision, and decisions feed compaction. By round 8 the decision list held one real user sentence and seven workflow packets, several of which quoted an earlier packet under the heading "Original user goal".

src/server/workflows/context.ts:371 · src/server/workflows/context.ts:445 · src/server/injections.ts:80

5. Personas read the preflight's vocabulary and cannot see the answer

The Persona prompt renders the transcript verbatim as workflow-transcript, so every Persona reads the preflight's instruction "Declare and link an author-controlled coverage claim for this criterion". The same prompt builder contains zero references to coverage: it renders acceptance criteria, an image manifest, a text artifact manifest, Check evidence, the diff, the transcript and standards, but never canonicalCriteria or criterionMappings. So nmr-code-quality-judge was told a requirement exists and given no way to observe that it was met. It failed the submission five times on exactly that ground, while the frozen submission held five to eight coverage rows each time.

Polluted-goal submissions reported gaps 21 times out of 29; clean-goal submissions reported gaps 5 times out of 9. The sample is small and I would not lean on that ratio, but the mechanism does not depend on it.

Evidence really is re-collected every round

Confirming the premise in the question. Capture flips each staged row to reserved and binds it to that submission's group key; a later submission with a different group key selects only rows that are still staged. Re-staging an identical item short-circuits as a no-op, so it stays attached to the old submission and does not join the new one. Re-staging a changed item under the same client id throws "already reserved". The practical consequence is that an agent must invent a new id for every artifact every round, which is exactly the id pattern in the database.

The system already stores what it needs to answer "could this have been corrupted by the recent changes": every staged row carries sha256, bytes, source_locator and a repository scope, and every submission carries a repository fingerprint. Deciding whether an accepted artifact is still valid is a hash comparison, not a judgment call.

Recommendations: make the pipeline smaller, not taller

The instinct on finding this loop is to add a guard for each leak. That would be the wrong move: the loop exists because the pipeline already has two gates, two goal columns, two attribution mechanisms and a coverage vocabulary that only one of the gates understands. Every fix below either changes one field or removes a layer. None of them adds a component.

1 Read the durable objective, not the latest prompt. One field.

src/server/workflows/context.ts:923 currently resolves rawPrompt: clip(goal?.prompt ?? goal?.text ?? "", MAX_GOAL). Point it at goal.objective, the column whose stated purpose is "durable completion contract", with text as the fallback it already has.

That single substitution collapses most of this report:

  • Compaction stops seeing repair packets, so canonical criteria stop being derived from complaints.
  • feedback.ts:381 stops nesting packets under "Original user goal:", because it reads the same field.
  • The intent fingerprint stops changing every submission, so reuseWorkflowContextCriteria finally fires. Criteria become stable for the run without building anything to make them stable, and this run's 21 context calls become roughly 2.

It also needs no guard on the hook, no reordering of rememberInjection, and no new origin plumbing. Those were three separate fixes in my first draft; this replaces all of them. Whether a workflow packet lands in goal.prompt stops mattering to the workflow.

One line in src/server/workflows/context.ts. Worth a focused test pinning that a workflow delivery cannot change a run's intent fingerprint.

2 Stop mining the transcript for "human decisions". Delete code.

The decisions list is assembled from three sources: resolved workflow reviews, Foreman episodes, and humanTranscriptDecisions(contextTranscript). The first two are structured, durable and unambiguously human. The third treats any user-role turn whose origin is undefined as a decision, and its correctness depends on a transcript anchor, a twelve-message search window and a bounded in-process origin map all holding at once. When any of them misses, a packet becomes a decision and feeds compaction.

Drop the third source from the decisions list. Nothing is lost for review, because Personas already receive the full transcript separately as workflow-transcript. What narrows is only the input to criteria derivation, which is exactly where a stable, deliberately-authored list belongs. With item 1 this makes the intent fingerprint genuinely constant across a run.

Removes a call and lets transcriptDecision and humanTranscriptDecisions go with it. src/server/workflows/context.ts:371, :381, :953

3 Park criterion_mapped_v1. Remove the whole second gate.

This is the layer to delete rather than repair. Look at what the enforcing policy actually caught. Across every readiness-evaluated submission, 26 were held and 11 passed. On this run every single hold was missing_coverage or ambiguous_mapping, which means the manifest did not line up with the model's criteria list. Not one hold was "the proof is genuinely absent". The one real evidence gap on this run, the missing screenshot at 2.1, sailed through preflight as ready and was caught by the Test Evidence Auditor, which is the component that was already doing this job.

Publishing the next No-Mistakes Review version with evidenceReadinessPolicy: "off" is an append-only data change in src/server/workflows/builtin-workflows.ts. No migration, no deletion, no behaviour change to any earlier version, and the machinery stays on disk for any workflow that opts in later. In one move it removes:

  • a second gate with its own wait state, delivery kind and refinement-segment lineage;
  • a context_reconciliation model call on every submission;
  • the proof-class and proof-role vocabulary, which is the vocabulary the Personas read out of the transcript and then re-raised as a requirement they could not verify;
  • the need for recommendation 3 in my first draft entirely. There is no coverage to render to a Persona if there is no coverage.

The Test Evidence Auditor remains the single authority on whether evidence proves the claim, which is what the original design intended before a second opinion was inserted ahead of it.

4 Carry evidence forward inside a run. Widen one query.

Answering the question directly: no, we should not require fresh evidence on every submission, and fixing this does not need an inheritance subsystem. The reservation selector today is:

WHERE note_key = ? AND (state = 'staged' OR reserved_group_key = ?) AND (repository_scope = 'all' OR source_root = ?)

Widen it to also admit rows reserved by this run's previous submission, and re-verify each inherited row by comparing its stored sha256 against its source_locator before freezing it into the child. That is one query plus one hash comparison. The freeze path already copies bytes, so nothing new is needed downstream, and the "could recent changes have corrupted it" question is answered by the digest the row already carries rather than by judgment.

Two smaller changes in the same place finish it:

  • Turn the "already reserved" throw into a re-stage. An agent re-registering an artifact under the same id is expressing intent, and refusing it is what forced the g5-, g6-, r7-, r8- id churn.
  • Deduplicate by digest on freeze, so registering a sha256 that already exists reuses the stored blob. That alone reclaims 347,400 bytes down to 38,600 for this run's screenshot.

src/server/workflows/store.ts:8931 (selector), :4604 and :4622 (re-stage), src/server/workflows/images.ts:642 (freeze). The existing unchanged-evidence refusal at src/server/workflows/manager.ts:6194 already compares the repository fingerprint rather than the evidence, so inheriting evidence does not weaken it.

5 Only if a structural gate is still wanted: one deterministic rule

If item 3 feels like giving up a real protection, replace the whole coverage apparatus with the single rule that would have caught the one genuine evidence gap on this run: if the diff touches a UI surface and the submission freezes no image evidence, hold. Changed paths and workflow_submission_images are both already present at capture. No model call, no author manifest, no proof classes, no reconciliation, no new vocabulary for a Persona to misread. One predicate, deterministic, explainable in a sentence.

That is the honest scope of what a pre-review structural check can know. Everything beyond it is semantic, and semantic is the Auditor's job.

6 Two cheap assertions, so this cannot recur silently

  • Assert the run's intent fingerprint never changes mid-run. With items 1 and 2 it should be constant by construction, so this is a one-line invariant that would have failed loudly at submission 3.1 instead of costing five rounds.
  • Surface the disagreement that already has a name. docs/plans/criterion-mapped-evidence-preflight/plan.md lists "Auditor rejection after a preflight-ready result" as a metric for finding blind spots. It fired five consecutive times here and nothing acted on it. If item 3 is taken, this becomes moot; if the policy is kept anywhere, make it an operator-visible signal rather than a counter.

What this is worth, and what it costs

Items 1 through 4 are one field, one deletion, one policy value and one widened query. Together, on this run, they would have removed six of the eight failing verdicts and about 4.54 MB of the 6.29 MB of Persona review input, leaving the two genuine findings. Item 1 alone also cuts the per-submission context calls from two to roughly zero after the first.

The pipeline that comes out the other side is smaller than the one that went in: one gate instead of two, one goal field instead of two competing ones, one model call per run instead of two per submission, and evidence that persists across a round instead of being re-collected. The problem was never that preflight runs. It is that its output is fed back into its own input, and that a second gate was added in front of a judge who was already doing the work.

What I did not establish

  • I did not reproduce the Goal overwrite in a test. The chain is established from live data plus reading the code path, not from an instrumented run. Two of its links are now direct reads rather than inferences: the frozen context_json on each submission shows the packet as primaryGoal.rawPrompt, and the live session_goals row shows prompt and focus holding the packet while text and objective hold the real goal. The door is narrowed but not proven: the supervisor door is demonstrably closed for workflow deliveries (deliverToDriver passes a goal payload only for origin === "human", and runtimePromptInjector never passes an origin), which leaves the UserPromptSubmit hook via captureHookGoalPrompt as the remaining unguarded path, supported by the code's own note that both doors are live for a dispatched SDK session. I did not instrument a delivery to watch the hook fire. It also stops mattering under recommendation 1, which makes the workflow indifferent to what lands in goal.prompt.
  • I did not measure dollar cost. workflow_llm_calls.cost_usd is null for every row in this run, so all figures here are input and output bytes, not tokens or spend. Byte ratios are a reasonable proxy for relative spend within one model, and I have used them only that way.
  • I did not test the fixes. No code was changed. Item 4 in particular has a real design question I did not resolve: whether an inherited artifact should be presented to the Auditor as equal to a fresh one, or explicitly labelled as inherited so the Auditor can weigh its age. I recommend labelling, but that is a judgment, not a finding.
  • The correlation between goal pollution and preflight gaps is weak evidence. 21 of 29 against 5 of 9 on a 41-submission sample is directionally consistent and statistically unremarkable. The argument in this report rests on the mechanism and on the round-by-round verdict attribution, not on that ratio.
  • I did not audit other workflows. Only No-Mistakes Review v13 and v14 enforce the policy, and only run 55cdbfef was traced end to end. Four other runs show the same goal-pollution signature but were not analysed verdict by verdict.
  • I did not check whether the operator override path was ever used. workflow_submission_readiness_overrides exists and offers a documented escape hatch that nobody appears to have reached for on this run; whether that is because it is hard to find or simply was not wanted, I do not know.
