Extending the settings console to Foreman and Workflows

The Inspector and Shipping panels were redrawn as an ops console - controls in a narrow column, a per-item ledger in a wide one, under a strip of counts whose tiles are the filters. This plan takes that shape to the two remaining subsystem panels, and it is deliberately not "apply the same layout twice".

Source of truth: docs/plans/settings-ops-console/plan.md · phases: phase-1-foreman.md, phase-2-workflows.md

What the investigation changed

One finding per panel, each of which changes what the work is:

Foreman Shadow mode measures nothing you can read. The panel offers "Shadow - run the cheap tier alongside, measure it". The worker computes a typed Divergence and the entire sink is console.log. It is not persisted, not routable, and cannot be inferred from the stored episode, because shadowBoth returns tier: 2 for every shadow decision. This is strictly worse than the Inspector's dry run was: that at least stored its findings and merely rendered them badly.

Foreman The ledger data exists and is unreachable. foreman_episodes holds an append-only row per decision - disposition, author, tier, confidence, classification, latency - and the only read path is GET /api/sessions/:id/foreman-episodes, one session at a time. Nothing in db.ts selects across note_key.

Workflows Must NOT get a ledger. WorkflowRuns.tsx (~1,560 lines) is already a run list with paging, SSE reconciliation, per-run actions and status filter chips, and the Workflows page header already links into these settings. A run table here would be a second, worse copy that disagrees with the real one the first time either changes.

The shape is three separable things

#PieceWhat it needs to be honestForemanWorkflows
1Shared leaves - ConsoleCard, ConsoleSwitch, ConsoleStateNothing. Any settings panel can adopt these.yesyes
2The count strip - tiles that are also the filterRows, and a bucket() every row lands in exactly once, so tiles sum to rows.yesvariant
3The two-column splitA ledger worth the width that no other surface owns.yesno

A panel with no ledger keeps its single column. Giving it a wide empty half to look like its neighbours would be the layout imitating a shape rather than expressing one.

The one place the strip's contract is deliberately broken

On Inspector and Shipping the tiles are folded out of the rows, which is what makes "3 blocked" and the three rows you get when you click it the same question asked once. Workflows has no rows here - its numbers are fleet-wide SQL scalars - so its tiles navigate to the run list instead of filtering in place, and claim to sum to nothing. That difference lives in a separate component, not a boolean on the existing one, or the next person to touch it will "fix" the missing tally and be wrong.

Dependency graph

A line, not a fan: Phase 1 renames outbound-console.tsx to settings-console.tsx (89 class occurrences, 94 CSS rules), a whole-file rewrite of a module Phase 2 imports. Run them concurrently and they conflict.

Decisions

  • D1 - the vocabulary is renamed once, in Phase 1. The module's own header justifies oc- as "the two categories whose writes leave this machine". Foreman and Workflows are machine-scoped, so that stops being true the moment either adopts it.
  • D2 - Foreman's ledger gets one new read path, recentEpisodes(limit) + GET /api/foreman/episodes, the direct analogue of loadInspectorInspections(50). Not a new table, and not SSE - episodes carry pane captures and stay off the live channel deliberately.
  • D3 - the shadow measurement is persisted, in Phase 1. Two nullable columns and the three lines in shadowBoth that stop discarding the cheap verdict. This is the seam to cut on if Phase 1 must be smaller - but then shadow keeps promising a measurement it does not take.
  • D4 - Workflows depends on Foreman, for the rename, not the subject matter.

Constraints both phases inherit

  • Anchors are a public contract. settings-search.ts points at six of them and settings-sidebar-render.test.ts fails on a duplicate or an unknown prefix. ConsoleCard takes an anchor prop for exactly this.
  • null config is "unknown", never "off". Disabled inputs are not a statement about what is running.
  • The daemon reports resolutions the browser cannot see - Foreman's provider is config?.runner ?? status?.runner ?? "claude" because of an env layer the browser has no access to. Do not simplify it.
  • README in the same change, and grep styles.css for any className you remove. There is no unused-CSS check.

Verify against a real ledger, not a fixture. Both defects found while building the first two panels - a strip that ignored 49 of 50 rows, and an empty state reading "No pull request is findings right now" - were invisible in tests and obvious the moment the panel was pointed at the daemon's actual data. Neither phase is done on the strength of its diff.

Non-goals

  • A run table in the Workflows settings panel. WorkflowRuns.tsx owns that.
  • Putting Foreman on the SSE channel. SettingsStatus excludes it deliberately.
  • The topbar Foreman popover, which owns the in-the-moment knobs while the panel owns the durable posture.
  • A general design-system pass. This is two panels adopting one existing shape.
