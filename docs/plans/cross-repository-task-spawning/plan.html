Cross-repository task spawning from Mission MCP

Let an agent in repo A create a backlog task in repo B, or one coordinated task across both, using the repository-aware task model Mission Control already has.

Approved shape: add optional target and attachment selectors to create_task, accept a valid local main checkout without a new MC grant, preserve current-repo behavior by default, and keep Foreman's separate unattended-launch allowlist.

Outcome

An agent in repository A can call create_task and place a task in repository B, or create one task spanning A and B, without attaching them to the planning task or obtaining another Mission Control repository grant.

Omitting the selector preserves today's current-repo behavior. A supplied target must be a valid local main checkout. The repository host enforces push and pull-request authority later. Mission Control adds no push probe, token cache, or permission table.

Boundary being removed: the tool's hardcoded current working directory. The durable backlog, dependency graph, and multi-repo task model already support the result.

Approved decisions

  • Keep Foreman's repository allowlist for unattended backlog launches while allowing creation and manual dispatch in any valid target.
  • Expose both an alternate primary and attached repositories through create_task.
  • Continue into a repository-verified phased implementation plan and dependency-linked tasks.

Proposed product behavior

The existing tool gains repository? and additionalRepositories?. Each accepts an absolute checkout path or a unique repository directory name. The result echoes canonical primary and secondary paths.

create_task({
  title: "Implement the consumer migration",
  intent: "...",
  repository: "web-client",
  additionalRepositories: ["/workspace/contracts"],
  dependsOnCurrentSession: true
})

Repository selector resolution

  1. Omitted target uses the calling checkout and walks it back to its owner.
  2. An absolute path goes through resolveTaskRepoRoot, including valid paths outside workspace scans.
  3. A short name must uniquely match a listRepos() basename. Zero or multiple matches refuse with a corrective message.
  4. The full primary and secondary set passes through resolveTaskRepoSet.

This is addressing, not authorization. It creates no durable trust grant and performs no remote write.

Transport compatibility

Keep McpCreateTaskSchema and legacy POST /mcp/tasks selector-free for older bundles. Add McpCreateTaskV2Schema with optional targetRepository and additionalRepositories. Both preserve internal repoRoot as the caller checkout. Old clients keep current-repo behavior.

A selector-bearing call uses a new token-authenticated versioned creation endpoint. This is necessary because the older Zod object strips unknown fields instead of rejecting them. An older daemon has no versioned route and returns 404 without creating anything, so the daemon accepting the request validates and stores the repository set atomically. Current-repository calls keep the legacy route.

Server convergence

Extract the dashboard route's full-set, effective-harness, and multi-repo capability preparation into one helper used by dashboard and MCP creation. The MCP route retains current-session dependency attribution, then calls TaskManager.create with backlog: true, the server-resolved effective agent, and no caller-supplied model or effort opinion.

Phased-plan behavior

  • Same-repo phases omit the selector.
  • A repo B phase makes B primary and attaches source repo A when its phase file remains in A. A is marked context-only.
  • An inseparable A plus B phase becomes one multi-repo task with one PR per changed repo.
  • Every phase keeps dependsOnCurrentSession: true, so the planning PR merges before checkout provisioning.
  • Resolution or capability failure stops dependent task creation and reports every id already created.

The design preserves path-based instructions and goal-level intents. It does not paste phase Markdown or add a duplicate task-brief store.

Request-flow change

Foreman policy

Approved: keep the allowlist for unattended launches. Cross-repo creation and manual dispatch work without a repository grant. Foreman still auto-launches only where every target is trusted, preserving the separate boundary for local command execution before a push. No Foreman code or configuration migration is needed.

Multi-repo scope

Approved: expose the full repository set. Add primary targeting and attachments so phased planning can schedule inseparable work and retain access to source-plan files. The larger schema and capability surface closes the whole dashboard-only MCP gap without new persistence.

Compatibility and failure behavior

  • Omitted selectors remain equivalent at the task-manager boundary.
  • The MCP transport is additive and keeps the old caller repoRoot.
  • Selector-bearing calls use an atomic versioned creation route; current-repo calls keep the legacy route.
  • No database or Task wire migration is required.
  • The whole repo set and effective harness resolve before creation.
  • Task creation failure returns no id; phased planning stops before dependents.
  • Existing all-or-nothing provisioning, per-repo PR tracking, and completion remain authoritative.
  • Push failure stays ordinary task evidence. No speculative retry or permission inference is added.

Acceptance criteria

  1. An agent in A creates exactly one B task using a unique name or absolute path.
  2. Omission still targets A.
  3. Invalid, orphaned, duplicate, and ambiguous targets fail before storage.
  4. An old daemon has no versioned route, creates no legacy task, and cannot race support validation against storage.
  5. A B task can depend on the A planning session or task.
  6. One call creates B primary plus A attached under existing capability rules.
  7. Phased planning schedules other-repo work without pasting phase Markdown.
  8. Plan paths resolve only after the planning PR merge releases the task.
  9. The Board visibly names the selected repo set through Playwright.
  10. Git and GitHub enforce push authority at ship time; MC adds no grant table.
  11. Foreman keeps its submitted allowlist policy.

Non-goals

  • No remote-only target or automatic clone.
  • No stored GitHub token or permission cache.
  • No push, role, or branch-protection preflight.
  • No new task model, worktree path, or completion rule.
  • No new Pi multi-repo capability.
Selected follow-up: publish a repository-verified phased implementation plan, then schedule its implementation tasks behind the planning-session merge.
