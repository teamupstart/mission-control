# Phase 14: Setup, doctor and mod install (WP7)

Source: `plan.md` (6.5), `phased-plan.md`. Common rules: `phased-plan.md` section 3. Spec v18, 7.10a, 7.14.

**1. Outcome.** `mctl setup` and `mctl doctor` make a machine ready: they find `claude`, check that mods can load, stage the mod, install it, and install the Foreman LaunchAgent, with each failure named and its fix printed. Branches (S17): if `marketplace add` and `install --scope user` run without prompts on the machine, setup installs through them; if a managed policy blocks them, setup prints the cause, applies the `CLAUDE_CODE_PLUGIN_DIRS` fallback of plan 5.1 through the settings installer where permitted, names the policy owner to ask (Q19), finishes the other steps and exits 1. (S18) A restaged build is always picked up by the stale-version reinstall, whether or not `/reload-plugins` loads it in an open session.

**2. Entry and dependencies.** Direct prerequisites: P8 (mod to stage), P10 (client) and P13 (`mctl claude`, whose one detection call this phase switches). Soft spikes S5, S14, S17, S18, S20, recorded in Commonroom where they have been run. Soft spikes never block a merge: when no answer is recorded the phase uses the fallback in plan 5.1 and its pull request says which answers it used or that none was recorded. For P14 the fallback is: a check whose fact comes from the Claude Code documentation (the `mods-version` floor, `mods-user-switch`, `mods-managed-policy`, `mods-sideload-policy`, `mods-traffic` and `mods-can-load`) ships as warn until a recorded S17 or S20 answer confirms the fact on a machine, and documentation alone never permits fail; the checks that read this machine's own state at run time (`mod-enabled`, `mod-current` and `mod-calls`) fail as plan 6.5 lists without a spike answer; and the pull request lists every check shipped as warn for want of an answer. Raising such a check to fail after an answer is recorded is a small follow-up pull request that changes only the severity table in `src/server/environment/claude-mods.ts` and its test.

**3. Scope.** The commands `mctl setup` and `mctl doctor`: `src/cli/commands/setup.ts`, `doctor.ts`; every file in `src/cli/setup-steps/` except `agents.ts` (P15) and `codex.ts` (P7); `src/cli/claude-cli.ts` (one detection function: `MISSION_CLAUDE_BIN`, `PATH`, then known places, accepted only if `claude --version` runs and `claude plugin --help` lists `marketplace`); `src/server/mod-stage.ts`; `scripts/install-service.mjs`; the "Mods can load" step, with `src/server/environment/claude-mods.ts` and a `MANAGED_MOD_KEYS` allowlist beside `MANAGED_ENV_KEYS` in `src/server/environment/claude-managed.ts`; and `test/home-dispatch-claude-mods.test.ts`. One edit outside its own files: `src/cli/commands/claude.ts` (P13's) changes in the single place that resolves the `claude` binary to call this phase's detection function. Non-goals: agents step, Codex step, packaging (P16).

**4. Findings.** The mod ships only inside Mission Control (D44): staged at `{stateDir}/mod/` by writing a sibling folder and renaming, never copying onto the published path (CLAUDE.md native-addon rule). Install is `claude plugin marketplace add {stateDir}/mod` then `claude plugin install mission-control@mission-control --scope user`, each only when `claude plugin list` does not show it. No `claude` found means skip the mod step, finish the rest, exit 1 (D45). The mods checks come from local plan `8065dbe0-950a-4572-b358-8e5b5489e69b` revision 2, not the spec: cite the check names `mods-version`, `mods-user-switch`, `mods-managed-policy`, `mods-sideload-policy`, `mods-stale-env`, `mods-traffic`, `mods-can-load`, `mod-enabled`, `mod-current`, `mod-calls` and the severities in plan 6.5. Apply the merge rule of section 2: warn where S17 or S20 has not confirmed a fact.

**5. Steps.** Read spec 7.10a, 7.14 and plan 6.5. `mctl setup` and `mctl doctor` run every step in P2's list, including the `codex` step (P7) and the `agents` step (P15) once they have merged; a step that is still a P2 stub is skipped with the line `step not available in this build` and does not change the exit code. Implement detection, switch P13's `mctl claude` to it in that one place (P13 has already merged, so `claude.ts` exists), staging by rename, the checks (read-only probes, no tokens, setup never changes a switch except the mod's own enabled state), install, the version probe and stale-build reinstall, the LaunchAgent (print, bootout, wait, bootstrap; L18), and the doctor report. Version probe: after staging, compare the version `claude plugin list` shows for `mission-control@mission-control` with the staged `plugin.json` version. If they differ, run `claude plugin uninstall mission-control@mission-control`, re-add the marketplace if it is not listed, install again, and re-check in a fresh `claude` invocation. Never use `claude plugin update` (D47). There is no rollback: uninstalling removes the old install, and the staged folder already holds the new build. If the install after the uninstall fails, retry it once. If it still fails, the mod may be left uninstalled: print the cause and the two recovery commands (`claude plugin marketplace add {stateDir}/mod` and `claude plugin install mission-control@mission-control --scope user`), finish the other steps and exit 1. Doctor reports `mod-enabled` failed with the fix `run mctl setup`. The daemon and everything else keep working, and a session without the mod shows nothing. `--off` no longer unbinds tmux.

**6. Data and API.** Nothing on the dashboard calls the probes. No new daemon routes.

**7. Tests.** Every check against planted settings in a temporary home and a fixture managed root with a fake `claude` runner, planted files unchanged afterwards; staging by rename; detection order; `mctl claude` resolves `claude` through the shared detection (a `MISSION_CLAUDE_BIN` override and a binary outside `PATH` are both found), with the fake `claude` runner; install idempotence; exit codes; an upgrade test where the fake `claude` runner lists an older installed version, setup reinstalls, and the re-check shows the staged version; and the failure path where the uninstall succeeds and the install fails twice: setup retries once, prints both recovery commands, finishes the other steps, exits 1, and doctor reports `mod-enabled` failed. A run over the step list with the `codex` and `agents` steps still stubs: both are skipped with that line and the exit code is unchanged; with real steps registered they run.

**8. Merge and exit.** Setup and doctor run on a clean machine against fakes, and a restaged build is picked up (stale version detected, reinstalled, verified in a fresh invocation); smoke runs `claude plugin validate` when `claude` is installed. Tests cover the unprompted install, the policy-blocked install and the stale-build reinstall.

**9. Handoff.** After this phase `mctl claude` and `mctl setup` find `claude` the same way. P16 packages what P14 stages; P15 and P7 add their own steps to the list; P17 documents troubleshooting.

**10. Cross-phase audit.** `scripts/install-service.mjs` owned here only. The mods checks are owned here and not duplicated in P8 except the `mod-calls` smoke check.
