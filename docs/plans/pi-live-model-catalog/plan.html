Pi live model catalog

APPROVED · phased implementation and scheduling requested

Read the source investigation

Approved human decisions

  • Catalog presentation: mirror every model Pi reports available, grouped by provider.
  • Implementation follow-up: create a merge-aware phased plan and schedule its dependency-linked implementation tasks.

Outcome

Mission Control should source Pi model choices from the Pi installation and account it will actually launch, while remaining usable when discovery is unsupported or fails. Selecting a model continues through the existing safe provider/id persistence and launch path.

Evidence driving the proposal

  • src/shared/model.ts compiles four Pi choices into every picker.
  • Pi 0.84.2 reports 38 available models on this machine through both --list-models and RPC get_available_models.
  • Only three shipped rows overlap; 35 Pi-reported rows are missing.
  • The RPC probe returned structured JSON in under one second, used no session, and sent no prompt.
  • All 38 derived provider/id values pass the existing ModelIdSchema.
  • The server harness interface already identifies models as a future harness-owned capability.

Scope

In scopeOut of scope
Harness-owned model capability; structured Pi discovery; one browser catalog store; preserved default and saved values; visible fallbacks; server and Playwright coverageChanging persistence or launch; invoking all listed models; dynamic Claude/Codex sourcing in this change; per-model effort redesign; SQLite catalog persistence

Source and fallback decision

Use Pi RPC as the primary source. The adapter resolves the same Pi binary as dispatch, starts a short-lived no-session process with project-local resources disabled, sends one correlated command, allowlists presentation fields, constructs and validates provider/id, applies measured bounds, and exits without prompting a model.

The daemon keeps the last successful result in memory and deduplicates concurrent probes. Missing binary, unsupported command, no provider, invalid output, timeout, or child failure returns the last successful or shipped fallback. Each browser picker then merges its current off-catalog value. Discovery quality must never become a dispatch outage.

Changed request flow

Today the browser imports the static catalog directly. After the change, choice production crosses the daemon and the harness registry; selection persistence and launch remain unchanged.

Implementation sequence

1. Contract and harness ownership

Add bounded shared response types and a required server-side model capability. Claude and Codex answer with shipped data; Pi declares discovery plus fallback. Add exhaustive registry tests.

2. Pi structured discovery

Test valid RPC, unrelated events, malformed output, wrong IDs, timeout, excessive output, duplicates, unsafe IDs, empty availability, and non-zero exit. Implement exact argv spawning, field allowlisting, validation, and cleanup. Feature-detect by behavior.

3. Daemon route and cache

Add aggregate GET /api/harnesses/models, live/fallback status, last-success time, bounded diagnostics, concurrent-probe deduplication, and exhaustive response tests. Keep cache in memory.

4. Browser store and consumers

Fetch once through shared state and feed Harnesses, Dispatch, Schedules, Ensembles, and Foreman's per-harness backlog defaults. Preserve Harness default and saved values. Mirror every Pi-available model, group the complete result by provider, and show a compact fallback note.

5. End-to-end behavior and docs

Teach the fake Pi binary to answer the RPC probe, add a Playwright option-to-route-to-persisted-value test plus failure fallback, update documentation, and run the required typecheck, lint, build, smoke, and UI gates.

Compatibility and safety

  • Honor MISSION_PI_BIN through the existing resolver.
  • Never invoke a model, create a session, or expose raw auth/model objects.
  • Never load project-local Pi extensions from an arbitrary repository during discovery.
  • Bound time, bytes, rows, IDs, and deduplication before returning a collection.
  • Preserve saved off-catalog values and continue on fallback.

Verification

  • Unit tests: RPC framing, mapping, bounds, cleanup, and fallback.
  • Contract/HTTP tests: registry ownership and source/status responses.
  • React rendering: loading, live, fallback, and retained selection.
  • Playwright: dynamic Pi option, exact persisted ID, reload, and failure fallback through the fake binary.
  • No test reaches a real provider or spends model tokens.

Claims and assumptions

Static sourcing, structured account-aware RPC, no-session probing, and schema compatibility are verified. The operator approved mirroring every Pi-available model, grouped by provider. The safe collection bounds and remote dynamic-catalog refresh policy must be measured during implementation before constants are chosen.
