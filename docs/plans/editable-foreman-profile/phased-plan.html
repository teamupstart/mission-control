Editable Foreman profile

Two merge-aware implementation units preserve Foreman's existing storage and worker safety boundary, then add one fixed System profile to the Library without admitting it to workflows or ensembles.

Source and approved decisions

Authoritative source: docs/plans/editable-foreman-profile/plan.md.

  • Foreman is a fixed System guidance profile in Library -> Personas, not a workflow Persona.
  • One current exact-text document uses compare-and-swap saves, with no history or activation step.
  • Guidance stays on the current triage, review, queued verification, and prompted completion surfaces.
  • Typed model, posture, operational, and Trust controls keep their current owners.
  • Every implementation task is disabled and pinned to Codex gpt-5.6-sol at xhigh.

Repository findings

Storage already fits

The existing app-config value preserves built-in, custom, and intentional empty states. No migration or Persona row is needed.

The write contract is missing CAS

The current route has no revision guard and no stream body limit. Phase 1 owns strict operations, ETags, conflicts, and a schema-shaped limit.

The worker stays simple

It projects only text and already captures one value per evaluation. Expanded response metadata does not change prompt behavior.

Status already owns summaries

Resolved provider and four model roles are already polled. Only the guidance source joins status; document bytes stay out.

The route grammar already works

Persona asset ids are opaque, so foreman round-trips today. The Library selection model, not the router, needs the local branch.

Catalog separation is the eligibility rule

Workflow and ensemble consumers see only PersonaView[]. The System row is composed locally and never filtered back out downstream.

Owner links need explicit callbacks

App already owns transient Settings anchors, while ForemanBar owns its open state. Phase 2 adds one-shot navigation requests rather than duplicate controls.

Scheduling reconciliation. The plan tool creates an enabled Claude task by default. Mission Control normalized the session edge to the existing planning task and reported it already satisfied while this PR was open, so each task was updated and read back as disabled, Codex gpt-5.6-sol, and xhigh. Disabled state is the effective pre-merge gate.

Sizing and phase count

Estimated non-test production change: 570 to 880 lines. Phase 1 accounts for roughly 150 to 230 lines across shared and server contracts. Phase 2 accounts for 420 to 650 lines across the editor, Library composition, navigation, Settings summary, and styling.

Two phases keep the independently operable API boundary reviewable before the broad visible surface consumes it. A third phase would separate documentation or a partial UI from the behavior it supports and is not justified.

Merge order

  1. This planning PR publishes every source, render, index, and phase file. Both phase tasks stay disabled through merge because their normalized planning-task edges were already satisfied.
  2. A human enables Phase 1. It merges the shared/server contract after focused and full unit gates pass.
  3. A human enables Phase 2 after Phase 1 merges. It delivers the full UI after unit, build, smoke, browser, evidence, and documentation gates pass.

Cross-phase contracts

  • Phase 1 owns one shared view/update schema, source enum, opaque ETag, 409 body, body limit, and status source field. Phase 2 only consumes them.
  • The existing app-config key remains the sole durable source. Built-in, custom, and none stay distinct.
  • Exact bytes drive storage and ETags; prompt rendering keeps its existing trim behavior.
  • The 64,000-character editor meter follows the instruction schema, not the Persona editor's UTF-8 byte contract.
  • Document bytes stay out of SSE and status. The worker keeps one captured string per evaluation.
  • Foreman never enters PersonaView[], Persona APIs/events, workflow validation, published snapshots, or ensemble choices.
  • Settings and Trust remain the only typed configuration writers.
  • The authority summary opens the existing top-bar Foreman control and links to the existing Settings and Trust anchors.
  • A dirty conflict is never overwritten automatically. Reload adopts remote; Keep editing deliberately rebases the local draft onto the returned ETag.

Verification strategy

Phase 1

Focused storage, route, worker-client, status, and prompt tests, then typecheck, lint, and the full unit suite.

Phase 2

Focused render/routing/exclusion tests, typecheck, lint, full unit, build, smoke, a dedicated Playwright journey, and light/dark visual evidence attached to its PR.

The final browser journey covers canonical routing, fixed identity, edit and preview, exact save and reload, the existing top-bar Foreman control, Models and Trust navigation, intentional empty guidance, and reset to the built-in default. Evidence stays in e2e/.artifacts/ and is never committed.

Cross-phase audit

  • All persistence and runtime requirements belong to Phase 1; all visible behavior, owner links, exclusion proof, docs, and evidence belong to Phase 2.
  • The API boundary is independently useful, while no smaller UI or cleanup merge unit is warranted.
  • Phase 2 directly consumes Phase 1, so the serial dependency is real and there is no false concurrency claim.
  • Storage remains downgrade-readable, the worker still projects text, and the browser adds no Persona catalog member.
  • The already-satisfied planning-task edge is recorded honestly; verified disabled state prevents early execution, and Phase 2 still waits directly on Phase 1.
