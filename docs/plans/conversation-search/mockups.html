Find in conversation

Four approaches to searching inside a session's conversation window. All four do the thing a browser's find does - count the occurrences, highlight every one, and step between them - and all four are live in this page: type in any find box below and it really searches the transcript beside it. They differ in where the control lives, what it tells you about matches you cannot currently see, and how much they cost. D is the one to read last: it merges A and B, and it is what the recommendation lands on.

Every mockup is drawn with the shipping .transcript / .turn / .turn-text CSS lifted verbatim from src/web/styles.css, at the width a Console detail pane really gets. The frame is the Console/Board detail; the same component mounts on an expanded Card, so anything that only works at 720px wide is disqualified.

What the conversation window does today

And the one constraint every approach has to answer

TranscriptPanel renders a flat list of .turn rows into a .transcript-log scroll box (max-height: 340px on a card, taller in the Console). Four roles are drawn differently - you in blue, the agent in its own --agent-accent, Foreman in purple, and the harness's own plumbing turns in grey - plus folded tool runs rendered as .tool-chip rows.

Constraint 1 - the log is windowed. The stream opens with roughly the last 80 turns (INIT_LIMIT, capped at 512KB, src/server/transcript.ts); everything older exists only as a byte-anchored ?before= page the reader has explicitly scrolled back to, held in a module-level LRU outside React (lib/transcript-history.ts). So a find that walks the DOM and reports "3 results" when the session has said the word forty times is not a browser-parity find, it is a wrong count presented confidently - the worst of the three outcomes. Each approach below is graded partly on how it answers that.

Constraint 2 - two render modes. A turn's text is rendered either as raw text under white-space: pre-wrap or parsed through <Markdown>, depending on the useRichText() setting. The mockups below highlight by walking text nodes and injecting <mark>, which is fine for a static page - but React owns those nodes in the real app, and a streamed turn arriving would blow the marks away or trip the reconciler. The shipping version has to compute match ranges and render the segments in React. That is the same work for all four approaches, so it does not decide between them, but it is why "it's just a <mark>" underestimates approach A.

Constraint 3 - the chord. / is the session filter, ⌘K is the settings palette, and the 21 entries in ACTIONS have taken most single letters. ⌘F is free, is what every user already presses, and - because it carries a command modifier - is the one shape that can fire while the reply box has focus, via App's existing chordHasCommandModifier bypass. A bare letter could not.

What is not a constraint: there is no virtualization anywhere in src/web, so every held turn is a real DOM node and querySelectorAll + measured scroll work exactly as the existing scrollToEpisode already does.

Try it: hover any frame below and press ⌘F / Ctrl+F to open its find bar. Enter next, ⇧Enter previous, Esc close. Each is pre-seeded with pane so you can see the counts and highlights immediately. Try registry, tmux, wezterm, null or the for a high-count case.
A

Floating find bar

Browser parity. The bar floats over the top-right of the log.

Exactly Chrome's find, transplanted. ⌘F reveals a small bar pinned over the top-right corner of .transcript-log; it takes no layout, so nothing below it moves and the reading position is preserved to the pixel. Every hit is tinted, the current hit is solid, and the count reads 3 / 17. Enter / ⇧Enter and the chevrons walk the ring in document order, wrapping at both ends. Esc closes it, clears the highlights, and restores the scroll position it opened at.

When it is closed, the only trace is a quiet ⌘F Find button in the launcher strip the transcript already has, so the feature is reachable without a keyboard.

What it buys

  • Zero learning curve. It is the control every user has already used ten thousand times.
  • No layout shift. Opening find does not move the text you were reading, which matters most on the 340px card log.
  • Fits every mount. Card, Console detail, Board drill-in - one absolutely-positioned box, no width assumptions.
  • Cheapest to build. One component, one range-walk, one OVERLAY_IDS entry.

What it costs

  • It occludes content. 300×32px sits over the top-right of the log; on a card that is a real fraction of the reading area.
  • No sense of distribution. "7 / 41" tells you nothing about whether the other 34 are just above or 300 turns back.
  • Says nothing about the window. It counts the DOM. Everything before .transcript-older is silently missing from the total.
  • No scoping. A transcript is mostly tool output; searching error buries the two turns where someone said it.
B

Results rail

A docked bar plus a list of every match, in context, beside the log.

The bar docks above the log rather than floating, and a rail on the right lists every match with its surrounding sentence and the role that said it. Clicking a result jumps the log to it; Enter and the arrows still walk the ring, and the rail's selection tracks the current hit in both directions. Because each result carries a role, the rail can offer the one filter the other two approaches structurally cannot: You / Agent / Foreman / Tools.

That scoping is not a nicety. By volume a real Mission Control transcript is overwhelmingly folded tool output, so an unscoped find for a common word puts the two turns a human actually wrote somewhere in the middle of forty file paths. This is also the only shape that degrades gracefully to a server-side search: the rail is already a list of results with context, so results from beyond the loaded window are just more rows, and clicking one loads that region of the conversation.

What it buys

  • Answers "where?" not just "how many". You read all 17 matches at once and pick the one you meant, instead of pressing Enter 11 times.
  • Role scoping. The only shape that can separate what was said from what a tool printed.
  • The natural home for server-side search. Matches beyond the loaded window are just more rows in a list that already exists.
  • Nothing is occluded. Every pixel of the conversation stays readable.

What it costs

  • It takes 244px of width. On an expanded Card - the narrowest of the four mounts - that is not affordable, so this needs a fallback and now there are two find UIs.
  • Not browser parity. Reading a list is a different, slower gesture than Enter-Enter-Enter for the common "jump to the next one" case.
  • Most expensive. New component, new scroll box, snippet extraction, scope state, selection sync in two directions.
  • Layout shift on open unless the rail is always present, and an always-present empty rail is a permanent tax on reading.
C

Docked bar + scroll-track minimap

The bar takes a row; a 12px gutter shows where every match lives.

The bar docks into the launcher strip instead of floating, so it occludes nothing, and the scroll box grows a 12px overview ruler on its right edge - VS Code's minimap marks, or Chrome's own scrollbar ticks. Every match in the loaded conversation gets a tick at its proportional position; the current one is brighter and taller; a soft block shows where the viewport currently is. The ticks are clickable, so a match 40 turns back is one click rather than 12 presses of Enter.

It is also the approach that can be honest about the window cheaply: because the gutter is already a picture of "where the matches are", a dashed row underneath saying "9 more in older turns" with a Load button reads as part of the same picture rather than as a bolted-on caveat. What it buys

  • Distribution at a glance. "All 17 are in the last three turns" and "they are spread over the whole session" look completely different, instantly.
  • Random access without a list. A tick is a jump target, so far-away matches cost one click, at ~2% of the rail's width cost.
  • Occludes nothing and keeps browser-parity keys for the common case.
  • Makes the windowing honest in a way that reads as information rather than as an apology.

What it costs

  • Ticks get dense. At 340px tall with 60 matches the gutter saturates into a solid bar and stops meaning anything - it needs clustering, which is more code than it looks.
  • Layout shift on open. The docked row pushes the log down ~40px, moving the text you were reading.
  • Positions need remeasuring on resize, on markdown images loading, and on every streamed turn - a live session invalidates the ruler constantly.
  • No scoping. Same tool-output problem as A.
D

Floating bar + rail on demand

A merged with B. The rail exists only while find is open.

Closed, this is exactly approach A - one quiet ⌘F button in the launcher strip and not one pixel more. Open it and the floating bar appears and a results rail slides in beside the log, carrying B's context snippets and its You / Agent / Tools scoping. Close it and the rail leaves with it.

That single change - the rail is bound to the find session, not to the panel - removes B's worst property. B's rail is a permanent tax on reading a conversation you are not searching; D's costs nothing until you ask for it. The bar floats over the log rather than over the whole panel, which is what lets it sit in the same place with or without the rail.

It also turns B's disqualifying flaw into a graceful degradation. The rail RELOCATES on a narrow mount; it is never dropped. A 244px column beside a 430px Card would leave about 170px of conversation, so below the threshold the split becomes a column: the rail sits under the log and takes its space from the log's height instead of its width. It is still visible whenever find is open - that part does not bend - it is simply somewhere else. Both frames below are the same wiring and the same markup; only the axis changes, and it changes by container query rather than by anything hand-applied.

The rail's visibility is not a separate control. There is no button to collapse it while find stays open: the rail is visible exactly when find is open and gone exactly when it is closed, which is what makes it one state rather than two. A toggle would buy back the log's full width mid-search, but it would also mean "find is open" no longer tells you what you are looking at - and the closed state, which is the whole of D's argument, would stop being the only way to get the conversation back.

What it buys

  • A's closed state, B's open state. Costs nothing to read a conversation you are not searching, and gives full context when you are.
  • One implementation at every width. Narrow mounts reflow the rail under the log rather than dropping it - one chord, one match ring, one set of states, no parity trap.
  • Role scoping survives the merge, so the tool-output problem is still solved where there is room to solve it.
  • Still the natural home for server-side search - matches beyond the loaded window are more rows in a list that already exists.

What it costs

  • Opening find reflows the conversation. The log narrows by 244px and every line re-wraps - a bigger disturbance than C's one-row push.
  • Two layouts to design and test, and the container-query threshold between them is a new thing that can be wrong.
  • The stacked rail costs the log height, which is the scarcer axis on a Card - a 380px log becomes ~216px while find is open, and the rail still only shows two results at a time.
  • The bar still occludes - and worse where it can least afford to. At Console width it covers a corner; at Card width it spans the entire top row of the log, because there is no room for it to be narrower than the panel.
  • No distribution picture. The rail says which matches exist, not how they are spread across a long scroll-back - the one thing C's gutter gives.
The reflow is smaller than it looks, and here is why. Opening find is not a passive change to the page - the user has just asked to be taken somewhere, and the same keystroke scrolls the first hit to the middle of the log. The re-wrap lands underneath a jump they asked for, rather than yanking prose they were mid-sentence on. That is not true of a rail that is always present and re-wraps when it is not wanted, which is what makes D's timing different from B's rather than just smaller.

Recommendation

D, and it supersedes the earlier call for C

A is the honest minimum - but its two weaknesses are the two things that make find useful in an agent conversation specifically. Agent transcripts are long, dense, and mostly not written by a human, so "17 matches" without "and here is where they are" leaves the user pressing Enter until something looks right, and a count that quietly excludes everything before the scroll-back button is a confident lie.

B answers both, and is the only shape that can scope by speaker - but 244px taken permanently from every conversation, searched or not, is not affordable, and on an expanded Card it is not available at all.

D collapses that objection rather than trading against it. Binding the rail to the find session instead of to the panel means the closed state is exactly A - nothing taken from anyone who is not searching - and the open state is B. The narrow mount stops being a second find UI to keep in parity and becomes the same one on a different axis: the rail reflows under the log rather than beside it. That was the specific thing disqualifying B, and it is gone.

The invariant that makes it one feature instead of two is worth stating on its own, because everything above depends on it: the rail is visible exactly when find is open, at every width. It is never a separate control, never a preference, and never dropped to buy back space - the narrow mount moves it, the closed state removes it, and nothing else touches it. That is what lets "find is open" remain a single legible state rather than a family of them.

This supersedes the earlier recommendation of C, which was the best available answer only while B's width cost was assumed to be permanent. C's gutter is still the better answer to distribution - where matches sit across a long scroll-back - and that is a real question the rail answers worse. But it is the second question. The first is "which of these did I mean", and a list of contextual snippets answers it better than tick marks do. The two are also not exclusive: the gutter is ~40 lines of CSS and a measured loop over the same match model, so it can be added to D later as a third presentation without disturbing either.

The build order that falls out: the match model first, then A's bar as the only presentation, then D's rail in both its axes, then C's gutter if distribution turns out to matter in practice. Each step is shippable on its own and none of them rewrites the one before.

The threshold, and what it is measured on. It cannot be a viewport media query - the same 720px Console pane exists at every window size, and an expanded Card's width depends on the grid's column count. It has to be the panel's own width, so the mockup uses a container query (container-type: inline-size on the transcript, @container (max-width: 560px) for the stacked axis). That is a mechanism this codebase does not use yet, and adopting it is a real part of D's cost - but it is the only honest way to ask "how wide is this panel", and both D frames on this page are driven by it rather than by anything hand-applied. What remains open is where the number sits: 560px is a guess that wants checking against a real Board drill-in column, which is the narrowest surface that still shows a rail.
Five things the mockups settle, whichever shape wins.
The chord is ⌘F - free, universal, and the only shape that can fire from inside the reply box. It goes in ACTIONS (lib/keybindings.ts), which makes it rebindable and settings-searchable for free.
It is not an overlay. Registering in OVERLAY_IDS makes App's overlays.anyOpen stand every grid chord down - right for a modal, wrong for a bar inside a panel that does not own the screen.
Its Escape is its own, with stopPropagation, following the topbar filter's convention: first Escape clears the query, second closes.
The highlight gets a --find token rather than borrowing --attention, which already means "this session needs you". It is the first <mark> in the codebase.
.turn-role is excluded from the search - otherwise you matches the byline of every message you ever sent.
Open questions these mockups do not answer. Does a streamed turn arriving re-run the search and move the current-hit ring out from under the reader mid-read - and if it does not, is the count now stale? Does a folded tool run, which collapses several turns into one row with no individual node, need to unfold to show a hit inside it? And does find follow the reader across the Tab ladder - is finding in the Diff tab and the Files tab the same feature, or three?
